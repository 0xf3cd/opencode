<Callout type="tip">
  OpenCode може налагодити сам себе. Опишіть проблему й попросіть його скористатися цією сторінкою: він прочитає кроки
  нижче, перевірить свій сервіс і журнали та допоможе визначити причину.
</Callout>

OpenCode має клієнт-серверну архітектуру. Фоновий сервер керує сесіями, плагінами, дозволами та іншим станом
застосунку. Спершу з'ясуйте, де виникає проблема: у клієнті, у спільному сервері чи в конкретному проєкті.

## Перевірка фонового сервісу

Перегляньте інформацію про поточний сервер:

```bash
opencode service status
```

Переконайтеся, що його API працює справно:

```bash
opencode api get /api/info
```

Якщо сервіс завис або працює некоректно, перезапустіть його:

```bash
opencode service restart
```

Його також можна явно зупинити й запустити:

```bash
opencode service stop
opencode service start
```

<Callout type="note">
  Зазвичай OpenCode автоматично знаходить або запускає спільний фоновий сервіс. Команди `service` потрібні лише для
  діагностики його життєвого циклу.
</Callout>

## Дозвіл джерела браузера

Якщо браузерний клієнт з іншого джерела (origin) не може під'єднатися через CORS, додайте джерело клієнта до
конфігурації сервісу:

```bash
opencode service set cors http://192.168.1.10:3001
opencode service get cors
```

Вказуйте точне джерело HTTP або HTTPS, за потреби з портом, без шляху та скісної риски в кінці. Щоб дозволити кілька
джерел, передайте список через кому одним аргументом; пробіли навколо кожного джерела обрізаються:

```bash
opencode service set cors "http://192.168.1.10:3001, https://app.example.com"
```

`service get cors` виводить масив JSON. Видалити налаштований список можна так:

```bash
opencode service unset cors
```

Задання або видалення параметра конфігурації сервісу зупиняє фоновий сервіс. Під час наступного запуску він
застосує нову конфігурацію; щоб запустити його явно, використайте `opencode service start`.

Для сервера на передньому плані повторіть `--cors` для кожного додаткового дозволеного джерела:

```bash
opencode serve --cors http://192.168.1.10:3001 --cors https://app.example.com
```

З `serve --service` передані прапорці `--cors` перевизначають збережений список для цього процесу. Без цих прапорців
режим сервісу використовує збережений список. CORS не змінює адресу прослуховування й не обходить автентифікацію
сервера.

## Перевірка API

Команда `api` використовує локальне виявлення сервісу й процес автентифікації. Вона приймає або HTTP-метод і шлях, або
ID операції OpenAPI.

Усі ендпоінти та ID операцій наведено в [довіднику API](/api).

Тіло запиту JSON передавайте через `--data` або `-d`, а заголовки додавайте через `--header` або `-H`.

<Callout type="warning">
  Якщо сумісного справного сервісу немає, `opencode api` може запустити фоновий сервіс.
</Callout>

## Читання журналів

Установлені збірки записують журнали у файл:

```text
~/.local/share/opencode/log/opencode.log
```

Стежте за журналом, поки відтворюєте проблему:

```bash
tail -f ~/.local/share/opencode/log/opencode.log
```

Кожен рядок містить ID процесу `run` і поле `role`. Для активності сесій, провайдерів, плагінів, дозволів та
інструментів використовуйте `role=server`.

```bash
grep 'role=server' ~/.local/share/opencode/log/opencode.log
grep 'run=8fc3b1d5' ~/.local/share/opencode/log/opencode.log
```

## Профілі CPU та пам'яті

У macOS і Linux можна надіслати запущеному процесу OpenCode сигнал, щоб зібрати діагностичні дані. Отримайте PID
фонового сервера з ендпоінта перевірки стану:

```bash
opencode api get /api/info
```

Використайте `pid` із відповіді з одним із цих сигналів:

- `SIGPROF` записує десятисекундний профіль CPU:

  ```bash
  kill -SIGPROF <pid>
  ```

  Результат записується в каталог журналів як `cpu-<pid>-<timestamp>.cpuprofile`.

- `SIGUSR1` записує знімок пам'яті (heap):

  ```bash
  kill -SIGUSR1 <pid>
  ```

  Результат записується в каталог журналів як `heap-<pid>-<timestamp>.heapsnapshot`.

Перш ніж відкривати файл, дочекайтеся в `opencode.log` повідомлення `CPU profile written` або `heap snapshot written`.
Відповідний запис журналу містить повний шлях до файлу. Обидва типи файлів можна переглянути в Chrome DevTools.

<Callout type="note">
  Профілі за сигналом недоступні у Windows. Запис знімка пам'яті може призупинити процес і тимчасово збільшити
  споживання ним пам'яті.
</Callout>

## Файли сервісу

Спільний сервер реєструє себе у файлі:

```text
~/.local/state/opencode/service.json
```

Його приватна конфігурація сервісу зберігається окремо:

```text
~/.config/opencode/service.json
```

База даних зазвичай розташована тут:

```text
~/.local/share/opencode/opencode.db
```

Розташування бази даних можна перевизначити через `OPENCODE_DB`.

<Callout type="warning">
  Під час усунення проблем не видаляйте й не редагуйте файли сервісу чи базу даних. Керуйте демоном за допомогою
  команд `service`, а перш ніж досліджувати збережені дані сторонніми інструментами, зробіть резервну копію.
</Callout>

## Повідомлення про проблему

Повідомляючи про відтворювану проблему, додайте:

- вивід `opencode --version`;
- вивід `opencode service status`;
- найкоротшу послідовність кроків, що відтворює проблему;
- чи стосується проблема спільного сервісу, конкретного клієнта або одного проєкту;
- відповідні рядки журналу разом із полями `run` і `role`.

Перш ніж ділитися журналами, видаліть з них ключі API, заголовки авторизації, промпти, вміст файлів та інші
конфіденційні дані.

Про відтворювані проблеми повідомляйте в [GitHub Issues](https://github.com/anomalyco/opencode/issues).
