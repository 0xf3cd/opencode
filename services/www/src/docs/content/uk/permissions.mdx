---
title: "Дозволи"
---

Дозволи визначають, чи може агент виконати дію з певним ресурсом.

## Налаштування

Типова конфігурація: запитувати підтвердження перед запуском команд оболонки, дозволяти рутинний перегляд стану Git і
завжди блокувати push. Додайте ці впорядковані правила в `opencode.jsonc`:

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "permissions": [
    { "action": "shell", "resource": "*", "effect": "ask" },
    { "action": "shell", "resource": "git status *", "effect": "allow" },
    { "action": "shell", "resource": "git diff *", "effect": "allow" },
    { "action": "shell", "resource": "git push *", "effect": "deny" },
  ],
}
```

Діє останнє правило, що збігається, тому конкретні винятки йдуть після загального правила.

<Callout type="warning">
  V1 використовує інші назви полів і дій. У V2 пишіть `permissions`, `shell` і `subagent` замість `permission`, `bash`
  і `task`.
</Callout>

## Правила

Кожне правило потребує трьох рядкових полів:

| Поле | Значення |
| --- | --- |
| `action` | Дія дозволу інструмента |
| `resource` | Значення, що використовується: шлях, команда, URL-адреса, запит, ID навички або ID агента |
| `effect` | `allow`, `deny` або `ask` |

```jsonc
{
  "permissions": [
    { "action": "read", "resource": "*", "effect": "allow" },
    { "action": "read", "resource": "*.env", "effect": "deny" },
  ],
}
```

| Ефект | Результат |
| --- | --- |
| `allow` | Продовжити без запиту |
| `deny` | Заблокувати операцію |
| `ask` | Чекати на рішення від клієнта |

Якщо жодне правило не збігається, OpenCode використовує `ask`.

## Зіставлення

Дії та ресурси підтримують прості шаблони, що зіставляються з усім значенням:

| Шаблон | Збігається з |
| --- | --- |
| `*` | Нуль або більше символів, зокрема `/` |
| `?` | Рівно один символ |
| Інше | Сам цей символ |

```jsonc
{
  "permissions": [
    { "action": "edit", "resource": "packages/docs/*.mdx", "effect": "allow" },
  ],
}
```

Цей шаблон зіставляється з усім нормалізованим шляхом. Зворотні скісні риски нормалізуються до прямих, а у Windows
зіставлення нечутливе до регістру.

Шаблон оболонки, що закінчується на ` *`, також збігається з командою без аргументів:

```jsonc
{ "action": "shell", "resource": "git status *", "effect": "allow" }
```

Він збігається і з `git status`, і з `git status --short`.

OpenCode об'єднує правила по порядку й використовує останній збіг. Спочатку завантажується конфігурація з нижчим
пріоритетом, потім додаються глобальні правила, а наостанок — правила агента.

```jsonc
{
  "permissions": [
    { "action": "read", "resource": "*", "effect": "allow" },
    { "action": "read", "resource": "secrets/*", "effect": "deny" },
  ],
}
```

Операції можуть перевіряти кілька ресурсів — наприклад, патч, що зачіпає кілька файлів. Будь-який `deny` забороняє
операцію; інакше будь-який `ask` спричиняє запит; інакше операцію дозволено.

## Дії

У V2 назви дій — це рядки, тож плагіни можуть визначати нові дії. Вбудовані інструменти наразі використовують такі дії
та ресурси:

| Дія | Ресурс |
| --- | --- |
| `read` | Внутрішній шлях відносно розташування (Location) або канонічний абсолютний зовнішній шлях |
| `edit` | Цільовий шлях для `edit`, `write` і `patch` |
| `glob` | Запитаний glob-шаблон |
| `grep` | Запитаний регулярний вираз, а не шлях пошуку |
| `shell` | Рядок команди, виділений сканером; складені команди можуть дати кілька |
| `subagent` | ID цільового агента |
| `skill` | ID навички |
| `question` | `*` |
| `webfetch` | Запитана URL-адреса |
| `websearch` | Пошуковий запит |
| `external_directory` | Канонічна межа зовнішнього каталогу, зазвичай із `/*` у кінці |
| `<server>_<tool>` | `*` для інструмента MCP; непідтримувані символи в обох назвах замінюються на `_` |
| `execute` | `*`; визначає доступність Code Mode, а вкладені інструменти застосовують власні правила |

Наприклад, дозвольте одну навичку й забороніть усі інші:

```jsonc
{
  "permissions": [
    { "action": "skill", "resource": "*", "effect": "deny" },
    { "action": "skill", "resource": "effect", "effect": "allow" },
  ],
}
```

`doom_loop` і `lsp` наразі не є діями дозволів у V2 Core.

## Каталоги

Шлях поза активним розташуванням і поза його некореневим worktree проєкту потребує підтвердження `external_directory`
перед підтвердженням `read` або `edit`.

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "permissions": [
    { "action": "external_directory", "resource": "~/projects/reference/*", "effect": "allow" },
    { "action": "read", "resource": "~/projects/reference/*", "effect": "allow" },
    { "action": "edit", "resource": "~/projects/reference/*", "effect": "deny" },
  ],
}
```

Це стосується зовнішніх шляхів, які використовують `read`, `edit`, `write` і `patch`. Shell перевіряє свій зовнішній
робочий каталог і каталоги, визначені сканером, перш ніж перевіряти ресурси `shell`.

Для `external_directory`, `read` і `edit` початкові `~`, `~/`, `$HOME` або `$HOME/` розгортаються під час завантаження
конфігурації:

```jsonc
{ "action": "read", "resource": "$HOME/reference/*", "effect": "allow" }
```

Ресурси оболонки залишаються сирим текстом команди, і домашній каталог у них не розгортається.

<Callout type="warning">
  `shell` працює з тими самими повноваженнями щодо файлової системи, процесів і мережі, що й користувач хоста. Визначення
  каталогів із тексту команди працює за принципом «наскільки можливо», тому краще використовувати вузький список
  дозволених команд оболонки, ніж шаблони, що мають розпізнати кожну небезпечну команду.
</Callout>

Відносні шляхи змін можуть виходити за межі активного розташування, залишаючись усередині worktree його проєкту. Явні
зовнішні шляхи перед зіставленням перетворюються на канонічні, тому авторизуйте лише межі довірених каталогів.

## Сканер

Увімкніть експериментальний портативний сканер оболонки так:

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "experimental": {
    "portable_shell_scanner": true,
  },
}
```

Портативний сканер замінює сканер tree-sitter за замовчуванням; tree-sitter не використовується ні як резервний
варіант, ні для додаткової перевірки. Якщо портативний сканер не може проаналізувати команду, він повертає помилку
сканера, а не відмову в дозволі.

Цей прапорець змінює лише вибір парсера. Наявні правила дозволів, збережені шаблони підтверджень і визначення
каталогів за принципом «наскільки можливо» продовжують діяти. Додаткового режиму підтвердження чи загального обмеження
для невідомих каталогів немає.

## Значення за замовчуванням

Кожен агент, зокрема власний, починає з такої впорядкованої базової політики:

```jsonc
[
  { "action": "*", "resource": "*", "effect": "allow" },
  { "action": "external_directory", "resource": "*", "effect": "ask" },
  { "action": "read", "resource": "*.env", "effect": "ask" },
  { "action": "read", "resource": "*.env.*", "effect": "ask" },
  { "action": "read", "resource": "*.env.example", "effect": "allow" },
]
```

Вбудовані агенти додають до неї такі політики:

| Агент | Додаткова політика |
| --- | --- |
| `build` | Дозволяє запитання |
| `plan` | Дозволяє запитання; забороняє редагування, крім файлів у `~/.opencode/plan` |
| `general` | Забороняє запитання й запуск субагентів |
| `explore` | Забороняє все, крім читання, glob, grep, отримання вебсторінок і вебпошуку; запитує підтвердження для зовнішніх каталогів і читання `.env` |
| `title` | Забороняє всі дії |
| `summary` | Забороняє всі дії |
| `compaction` | Залишає базову політику |

OpenCode також дозволяє доступ до зовнішніх каталогів для своїх керованих каталогів виводу інструментів, виводу
оболонки, тимчасових файлів і глобальної конфігурації. Сама дія `read`, `edit` чи інша, як і раніше, підпорядковується
власним правилам. Пізніші глобальні правила й правила агентів можуть перевизначити ці значення за замовчуванням.

## Агенти

Спільні правила розміщуйте на верхньому рівні, а вужчі — в `agents.<id>.permissions`:

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "permissions": [
    { "action": "shell", "resource": "*", "effect": "ask" },
    { "action": "shell", "resource": "git status *", "effect": "allow" },
  ],
  "agents": {
    "reviewer": {
      "description": "Review code without changing it",
      "mode": "subagent",
      "permissions": [
        { "action": "edit", "resource": "*", "effect": "deny" },
      ],
    },
  },
}
```

Правила агента додаються після глобальних правил і не замінюють глобальний масив. Власний субагент використовує свої
дозволи, а не підмножину дозволів батьківського агента.

## Підтвердження

Коли правило дає `ask`, клієнти можуть відповісти так:

| Вибір | Відповідь | Результат |
| --- | --- | --- |
| Allow once | `once` | Підтвердити лише поточний запит |
| Allow always | `always` | Підтвердити запит і зберегти запропоновані інструментом шаблони для проєкту |
| Reject | `reject` | Відхилити цей та всі інші запити на дозвіл, що очікують у цій сесії |

Наприклад, якщо вибрати **Allow always** для `git status --short`, може зберегтися префікс команди оболонки, який
охоплює подальші команди `git status`:

```text
shell: git status * → allow
```

Збережені підтвердження — це постійні правила `allow` на рівні проєкту. Вони ніколи не перевизначають налаштований
`deny`. Шаблон для збереження пропонує інструмент: деякі пропонують `*`, shell — префікси команд, а навички й субагенти —
свої ID. Переглядайте широкі підтвердження й видаляйте ті, що більше не потрібні.

Відхиляючи запит, клієнти можуть додати відгук. Неінтерактивні клієнти мають самі вирішувати, як обробляти запити на
підтвердження; налаштовані правила `deny` діють завжди.

## Політики

[Політика](/policies) може остаточно заборонити перевірку дозволу після застосування цих правил і збережених
підтверджень. Вона перетворює `allow` або `ask` на `deny` і ніколи не надає доступу.

```jsonc
{
  "policies": [{ "action": "tool.use", "resource": "shell:sudo *", "effect": "deny" }],
}
```

Глобальні політики й політики, керовані через OpenCode Console, мають вищий пріоритет за конфігурацію проєкту — так
організація може заблокувати команду, яку дозволив би репозиторій.
