---
title: "Навички"
---

Створіть навичку (skill), щоб дати агенту інструкції для певного завдання, які можна використовувати повторно. Розмістіть файл `SKILL.md` у `.opencode/skills/<skill-id>` і опишіть у `description`, коли його використовувати.

```markdown title=".opencode/skills/git-release/SKILL.md"
---
name: Git Release
description: Prepare release notes, version bumps, and GitHub releases
---

## Workflow

1. Read `references/release-policy.md`.
2. Summarize merged changes since the previous tag.
3. Propose the version bump before changing files.
4. Run `scripts/changelog.ts` only after the user approves the version.
```

OpenCode пропонує цю навичку, коли вона доречна. Тоді агент може завантажити її інструкції інструментом `skill`, тож не потрібно додавати кожну навичку до кожного промпту.

## Створення

Зберігайте пов'язані скрипти, довідкові матеріали й шаблони поруч із `SKILL.md`:

```text
.opencode/skills/
└── git-release/
    ├── SKILL.md
    ├── scripts/
    │   └── changelog.ts
    └── references/
        └── release-policy.md
```

Шляхи, вказані всередині навички, відносні до каталогу з `SKILL.md`. Рекомендовано використовувати форму з каталогом, бо вона дає допоміжним файлам власний базовий каталог.

## Виявлення

OpenCode автоматично шукає навички в таких розташуваннях:

| Область                    | Джерела                                |
| -------------------------- | -------------------------------------- |
| Глобальна                  | `~/.config/opencode/skills`            |
| Глобальна (сумісність)     | `~/.claude/skills`, `~/.agents/skills` |
| Проєкт                     | `.opencode/skills`                     |
| Проєкт (сумісність)        | `.claude/skills`, `.agents/skills`     |

Для джерел проєкту OpenCode шукає від поточного каталогу до кореня проєкту й враховує відповідні каталоги на кожному рівні.

Кожне джерело може містити будь-яку з двох форм:

```text
skills/
├── review.md
└── git-release/
    └── SKILL.md
```

- Файли Markdown мають лежати в корені джерела, наприклад `skills/review.md`.
- Файли з назвою саме `SKILL.md` можуть бути на будь-якій глибині, наприклад `skills/git-release/SKILL.md`.

## Джерела

Додавайте інші локальні каталоги або HTTP-каталоги навичок через масив `skills` у будь-якому `opencode.json` чи `opencode.jsonc`:

```jsonc title="opencode.jsonc"
{
  "$schema": "https://opencode.ai/config.json",
  "skills": [
    "./team-skills",
    "~/shared/opencode-skills",
    "/opt/company-skills",
    "https://example.com/opencode/skills/",
  ],
}
```

| Значення | Розв'язання |
| -------- | ----------- |
| Відносний шлях | Відносно активного робочого каталогу OpenCode, а не файлу конфігурації |
| Шлях `~/` | Відносно домашнього каталогу поточного користувача |
| Абсолютний шлях | Використовується як є |
| URL-адреса `http://` або `https://` | Завантажується як HTTP-каталог |

Кожен знайдений файл конфігурації додає свої записи. Масиви `skills` об'єднуються, а не замінюються.

## Каталоги

HTTP-каталог — це базова URL-адреса з файлом `index.json`:

```json title="index.json"
{
  "skills": [
    {
      "name": "git-release",
      "version": "3",
      "files": ["git-release.md", "references/release-policy.md"]
    }
  ]
}
```

Для цього запису OpenCode завантажує кожен файл з `<base-url>/git-release/<file>`.

| Правило | Вимога |
| ------- | ------ |
| Шляхи | Мають бути безпечними, відносними й з того самого джерела (same-origin) |
| Файл входу | Додайте `SKILL.md` або `<name>.md`, наприклад `git-release.md` |
| Оновлення | Збільшуйте `version`, коли файли змінюються, щоб OpenCode оновив кеш |

У HTTP-каталозі віддавайте перевагу іменованій формі Markdown. Кожен завантажений каталог навички стає коренем джерела, тому `git-release.md` має ID `git-release`. Файл `SKILL.md` на кореневому рівні наразі у V2 має буквальний ID `SKILL`.

## Frontmatter

За допомогою frontmatter задайте назву навички й визначте, де вона з'являтиметься:

```markdown title="SKILL.md"
---
name: Git Release
description: Prepare a repository release
metadata:
  opencode/autoinvoke: false
---

Prepare the changelog, version bump, tag, and release notes.
```

| Поле                           | Поведінка                                                              |
| ------------------------------ | ---------------------------------------------------------------------- |
| `name`                         | Відображувана назва; за замовчуванням — ID, отриманий зі шляху         |
| `description`                  | Короткий опис, за яким навичку показують моделі                        |
| `metadata.opencode/autoinvoke` | Задайте `false`, щоб не включати навичку до списку, доступного моделі  |
| `disable-model-invocation`     | Задайте `true`, щоб отримати той самий ефект, що й `opencode/autoinvoke: false` |

Під час виконання всі поля frontmatter необов'язкові. Якщо модель має знаходити навичку, додайте зрозумілий `description`; навички без нього не пропонуються.

`opencode/autoinvoke: false` лише приховує навичку зі списку, доступного моделі. Навичка залишається зареєстрованою, і її можна завантажити явно за ID. Якщо задано і `disable-model-invocation`, і `opencode/autoinvoke`, перевагу має `opencode/autoinvoke`. V2 приймає поля для перенесення між інструментами, як-от `license` і `compatibility`, але не інтерпретує їх.

## ID

ID навички визначається шляхом до файлу. Поле frontmatter `name` — лише відображувана назва.

| Файл                              | ID            |
| --------------------------------- | ------------- |
| `<source>/git-release.md`         | `git-release` |
| `<source>/git-release/SKILL.md`   | `git-release` |
| `<source>/teams/release/SKILL.md` | `release`     |

ID точні й чутливі до регістру. Для переносних навичок використовуйте унікальний ID у нижньому регістрі в стилі kebab-case довжиною 1–64 символи і тримайте його узгодженим із назвою каталогу:

```text
^[a-z0-9]+(-[a-z0-9]+)*$
```

Наразі V2 не перевіряє ні відповідність цьому шаблону, ні рекомендовану довжину 1–64 символи, ні збіг `name` з назвою каталогу, ні максимальну довжину опису.

## Пріоритет

Навички вибираються за ID. Якщо два джерела визначають `git-release`, OpenCode завантажує навичку з джерела, зареєстрованого пізніше:

```text
~/.config/opencode/skills/git-release/SKILL.md  ← lower precedence
.opencode/skills/git-release/SKILL.md           ← loaded
```

Джерела реєструються від нижчого пріоритету до вищого:

1. Вбудовані навички
2. `.claude/skills`: спершу глобальний, потім від найвіддаленішого батьківського каталогу до поточного
3. `.agents/skills`: спершу глобальний, потім від найвіддаленішого батьківського каталогу до поточного
4. `~/.config/opencode/skills`
5. `.opencode/skills` проєкту — від кореня проєкту до поточного каталогу
6. Явні записи `skills` у конфігурації — за пріоритетом конфігурації та порядком у масиві

Уникайте однакових ID, якщо не збираєтеся перевизначити попередню навичку.

## Завантаження

На кожному кроці моделі OpenCode перелічує дозволені навички, які мають опис і не задають `opencode/autoinvoke` значення `false`. Список містить лише ID, назву й опис, а не повне тіло Markdown.

Модель завантажує навичку, викликаючи інструмент `skill` з її точним ID:

```json title="skill tool input"
{
  "id": "git-release"
}
```

Після цього OpenCode:

1. Вибирає поточне визначення для цього ID.
2. Перевіряє дозвіл `skill` вибраного агента.
3. Додає тіло Markdown без frontmatter до розмови.
4. Надає базовий каталог навички та до десяти шляхів допоміжних файлів як приклад.

Щоб завантажити навичку самостійно, згадайте її в промпті як `@skill-id`.

Вміст допоміжних файлів автоматично не завантажується. Агент читає їх, коли навичка йому це вказує. Перелік файлів доступний для навичок `SKILL.md` у каталогах; плоскі навички Markdown списку сусідніх файлів не отримують.

## Дозволи

Використовуйте дію `skill` і ID навички як ресурс. Правила застосовуються по черзі, і перемагає останнє правило, що збіглося:

```jsonc title="opencode.jsonc"
{
  "permissions": [
    { "action": "skill", "resource": "*", "effect": "allow" },
    { "action": "skill", "resource": "internal-*", "effect": "deny" },
    { "action": "skill", "resource": "experimental-*", "effect": "ask" },
  ],
}
```

| Ефект | Поведінка |
| ----- | --------- |
| `allow` | Пропонує та завантажує відповідні навички без підтвердження |
| `ask` | Пропонує відповідні навички й запитує підтвердження перед завантаженням |
| `deny` | Приховує відповідні навички від моделі й відхиляє їх завантаження |

Щоб застосувати ті самі правила лише до одного агента, розмістіть їх в `agents.<id>.permissions`.

## Усунення проблем

Наприклад, ID цієї навички — `release`, а не її назва з frontmatter `Git Release`:

```text
.opencode/skills/release/SKILL.md
                      └─ ID: release
```

Якщо навичка відсутня або завантажує неправильний вміст:

1. Переконайтеся, що файл — це або `*.md` на кореневому рівні, або вкладений файл з назвою саме `SKILL.md`.
2. Перевіряйте ID, отриманий зі шляху (з урахуванням регістру), а не `name` з frontmatter.
3. Додайте `description`, якщо модель має знаходити навичку.
4. Перевірте `opencode/autoinvoke` і дозволи `skill` вибраного агента.
5. Пошукайте пізніше джерело, яке визначає той самий ID.
6. Для HTTP-каталогів перевірте `index.json`, шляхи файлів з того самого джерела та змінене значення `version`.
