---
title: "Перехід з V1"
---

OpenCode 1 і OpenCode 2 використовують ту саму команду `opencode`, тому за замовчуванням їх більше не встановлюють
паралельно. Перед установленням V2 видаліть V1, установлену через менеджер пакетів; інсталятор V2 через curl замінює
бінарний файл V1.

## Несумісні зміни

У V2 є три навмисні несумісні зміни:

- [Плагіни](/build/plugins/migrate-v1) використовують новий API плагінів.
- [API сервера та клієнти](#server-api-and-clients) мають нові контракти.
- [Конфігурація термінального клієнта](/cli/config) переходить з багаторівневих файлів `tui.json(c)` до одного
  глобального файлу `cli.json` (міграція відбувається автоматично).

Підтримувана функціональність V1 поза цими областями має залишатися сумісною з V1. Деякі поля, які приймала схема V1,
ніколи не мали відповідника у V2 і навмисно ігноруються; їх перелічено в розділі
[Поля, що приймаються, але не підтримуються](#accepted-but-unsupported-fields).

Наявні підтримувані поля конфігурації сервера, визначення агентів і команд, навички та інші файли в `.opencode/` мають
і далі працювати без змін. Якщо підтримувана поведінка, описана в цьому посібнику, перестала працювати у V2, вважайте
це помилкою сумісності, а не очікуваною вимогою міграції.

<Callout type="tip">
  Якщо підтримувана функціональність V1 не працює у V2, скористайтеся порадами щодо повідомлення про проблеми в розділі
  [Усунення несправностей](/troubleshooting) і створіть issue про сумісність.
</Callout>

## Установлення V2

Установіть термінальний клієнт V2, дотримуючись [посібника із запуску в терміналі](/cli).

Переписувати все перед запуском V2 не потрібно. Практичний порядок міграції:

1. Залиште наявну конфігурацію та визначення у файлах.
2. Запустіть V2 і перевірте моделі, облікові дані, агентів, дозволи та сервери MCP.
3. Перенесіть плагіни, бо реалізації плагінів для V1 у V2 не працюють.
4. Перенесіть інтеграції, які викликають API сервера.
5. Коли будете готові, перетворіть конфігурацію на нативний формат V2. Цей крок необов'язковий.

Поки перевіряєте міграцію, збережіть копію налаштувань V1. V1 і V2 використовують ті самі розташування конфігурації,
тому не спрямовуйте V1 на файли, які ви вже перетворили на формат, що підтримує лише V2.

## Конфігурація

У цьому розділі описано як конфігурацію JSON/JSONC, так і визначення у файлах у `.opencode/`.

### Використання наявної конфігурації

V2 читає наявну системну, глобальну та проєктну конфігурацію з тих самих розташувань, що й V1:

```text
/Library/Application Support/opencode/opencode.json(c)
/etc/opencode/opencode.json(c)
%ProgramData%\opencode\opencode.json(c)
/Library/Managed Preferences/<user>/ai.opencode.managed.plist
/Library/Managed Preferences/ai.opencode.managed.plist
~/.config/opencode/opencode.json(c)
<project>/opencode.json(c)
<project>/.opencode/opencode.json(c)
```

V2 нормалізує підтримувані поля V1 і нативні поля V2 у пам'яті, не переписуючи вихідний файл. Наявна підтримувана
конфігурація V1 має працювати й далі, тож перетворювати її, щоб спробувати або впровадити V2, не потрібно.

Як і у V1, системна конфігурація та керовані параметри macOS мають найвищий пріоритет, тому їхні налаштування
перевизначають глобальні та проєктні файли. Їхні [політики](/policies#precedence), зокрема перенесені
`enabled_providers` і `disabled_providers`, також мають пріоритет над глобальними та проєктними політиками.
Перевизначення налаштування не може заборонити користувачам додавати провайдерів, сервери MCP, агентів чи плагіни, тому
обмеження, які встановлює адміністратор, задавайте через `policies`, а не через звичайні налаштування на кшталт
`permissions`.

### Міграція за допомогою OpenCode

Формат конфігурації V1 і далі підтримується. Нативний формат V2 необов'язковий: він робить деякі налаштування
явнішими та зручнішими.

Рекомендований спосіб міграції — попросити OpenCode оновити конфігурацію за вас:

```text
Migrate my OpenCode configuration, including file-based definitions, from the V1 format to the native V2 format.
Preserve its behavior and all unrelated settings.
```

OpenCode може переглянути весь файл, застосувати потрібні зміни з описаних нижче й не переписувати налаштування, які
змінювати не треба. Перетворювати все одразу не обов'язково: підтримувані поля V1 і нативні поля V2 можуть
співіснувати на верхньому рівні. Якщо обидві форми задають те саме канонічне значення, пріоритет має коректне нативне
значення V2 незалежно від порядку ключів у JSON.

Змішування на вкладених рівнях навмисно обмежене. OpenCode розпізнає змішані елементи V1 і V2 у `mcp`, `compaction` та
`experimental`, але не визначає формат рекурсивно всередині окремих агентів, провайдерів, команд чи моделей. Кожен такий
вкладений запис повністю записуйте в одному форматі. Підтримуваний синтаксис V1 сам по собі не викликає попереджень;
некоректні значення, непідтримувані застарілі поля та конфліктні значення V1/V2 спричиняють попередження, а не
пов'язані з ними коректні налаштування завантажуються далі.

### Спільний доступ

Застаріле булеве поле `autoshare` з V1 стає явною політикою `share`:

```jsonc
// V1
{ "autoshare": true }

// V2
{ "share": "auto" }
```

Використовуйте `"manual"`, `"auto"` або `"disabled"`. Якщо файл V1 уже використовує `share`, змінювати нічого не
потрібно.

### Дозволи та інструменти

У V1 дії дозволів згруповано за інструментами. У V2 використовується один упорядкований масив `permissions`, завдяки
чому пріоритет і винятки стають явними:

```jsonc
// V1
{
  "permission": {
    "bash": {
      "git push *": "ask"
    },
    "edit": "allow"
  },
  "tools": {
    "websearch": false
  }
}

// V2
{
  "permissions": [
    { "action": "shell", "resource": "git push *", "effect": "ask" },
    { "action": "edit", "resource": "*", "effect": "allow" },
    { "action": "websearch", "resource": "*", "effect": "deny" }
  ]
}
```

Змінилися й дії дозволів: `bash` тепер `shell`, `task` тепер `subagent`, а `write` і `patch` тепер `edit`. Формат
упорядкованих правил V2 описано в розділі [Дозволи](/permissions).

### Агенти та режими

Мапа `agent` в однині та застаріла мапа `mode` стають `agents`. Поля агентів стають узгодженішими з рештою конфігурації
V2:

```jsonc
// V1
{
  "agent": {
    "reviewer": {
      "prompt": "Review for correctness and missing tests.",
      "model": "anthropic/claude-sonnet-4-5",
      "variant": "high",
      "disable": false,
      "permission": {
        "edit": "deny"
      }
    }
  }
}

// V2
{
  "agents": {
    "reviewer": {
      "system": "Review for correctness and missing tests.",
      "model": "anthropic/claude-sonnet-4-5#high",
      "disabled": false,
      "permissions": [
        { "action": "edit", "resource": "*", "effect": "deny" }
      ]
    }
  }
}
```

`prompt` стає `system`, `disable` — `disabled`, а окреме поле `variant` приєднується до посилання на модель після `#`.
`temperature`, `top_p` і специфічні для провайдера `options` переносяться в `request.body`. `maxSteps` стає `steps`.
Записи зі старої мапи `mode` стають основними агентами.

### Знімки

Перейменуйте поле `snapshot` в однині на `snapshots`. Його булеве значення не змінюється:

```jsonc
// V1
{ "snapshot": false }

// V2
{ "snapshots": false }
```

### Медіа

Перейменуйте об'єкт `attachment` в однині на `media`. Вкладені налаштування зображень зберігають ті самі назви:

```jsonc
// V1
{ "attachment": { "image": { "auto_resize": true } } }

// V2
{ "media": { "image": { "auto_resize": true } } }
```

### Сервери MCP

V2 групує сервери в `mcp.servers`, замінює `enabled` протилежним за значенням `disabled` і розділяє тайм-аути за
призначенням:

```jsonc
// V1
{
  "mcp": {
    "playwright": {
      "type": "local",
      "command": ["npx", "@playwright/mcp"],
      "enabled": true,
      "timeout": 30000
    }
  }
}

// V2
{
  "mcp": {
    "servers": {
      "playwright": {
        "type": "local",
        "command": ["npx", "@playwright/mcp"],
        "disabled": false,
        "timeout": {
          "catalog": 30000,
          "execution": 30000
        }
      }
    }
  }
}
```

Поля OAuth для віддалених серверів записуються у snake_case: `clientId` стає `client_id`, `clientSecret` —
`client_secret`, `callbackPort` — `callback_port`, а `redirectUri` — `redirect_uri`. Значення `experimental.mcp_timeout`
з V1 також стає значенням за замовчуванням для `mcp.timeout.catalog` і `mcp.timeout.execution`. Див.
[Сервери MCP](/mcp-servers).

### Стиснення контексту

V2 групує бюджет токенів для збереженого контексту в `keep` і дає резерву зрозумілішу назву:

```jsonc
// V1
{
  "compaction": {
    "preserve_recent_tokens": 8000,
    "reserved": 20000
  }
}

// V2
{
  "compaction": {
    "keep": {
      "tokens": 8000
    },
    "buffer": 20000
  }
}
```

`auto` зберігає назву. У V2 немає нативних полів `tail_turns` і `prune`; обидва застарілі поля ігноруються з
попередженням. Натомість нещодавній контекст зберігається в межах бюджету токенів. Див.
[Стиснення контексту](/compaction).

### Навички

У V1 додаткові шляхи та URL-адреси навичок задаються окремо. У V2 вони об'єднані в один упорядкований масив:

```jsonc
// V1
{
  "skills": {
    "paths": ["./team-skills"],
    "urls": ["https://example.com/skills/"]
  }
}

// V2
{
  "skills": ["./team-skills", "https://example.com/skills/"]
}
```

Наявні файли навичок і автоматичне виявлення в `.opencode/skills/` не змінюються. Див. [Навички](/skills).

### Команди

Перейменуйте мапу `command` в однині на `commands`, а `subtask` — на `subagent`. Приєднайте окреме поле `variant` до
посилання на модель:

```jsonc
// V1
{
  "command": {
    "review": {
      "template": "Review the current changes.",
      "model": "anthropic/claude-sonnet-4-5",
      "variant": "high",
      "subtask": true
    }
  }
}

// V2
{
  "commands": {
    "review": {
      "template": "Review the current changes.",
      "model": "anthropic/claude-sonnet-4-5#high",
      "subagent": true
    }
  }
}
```

`template`, `description` і `agent` зберігають свої назви. Застаріле поле `subtask` і далі приймається; делеговані
команди тепер автоматично виконуються у фоні й повідомляють результати батьківській сесії. Наявні визначення команд
у Markdown і далі підтримуються. Див. [Команди](/commands).

### Посилання на каталоги

Перейменуйте застарілу мапу `reference` в однині на `references`:

```jsonc
// V1
{ "reference": { "docs": "../docs" } }

// V2
{ "references": { "docs": "../docs" } }
```

V1 уже приймає `references`, тому якщо файл використовує це поле, змінювати нічого не потрібно. Структура записів
не змінюється. Див. [Посилання на каталоги](/references).

### Провайдери

Перейменуйте мапу `provider` в однині на `providers`. V2 розділяє пакет середовища виконання, ендпоінт і параметри
запитів:

```jsonc
// V1
{
  "provider": {
    "acme": {
      "npm": "@ai-sdk/openai-compatible",
      "api": "https://llm.example.com/v1",
      "options": {
        "apiKey": "{env:ACME_API_KEY}"
      }
    }
  }
}

// V2
{
  "providers": {
    "acme": {
      "package": "aisdk:@ai-sdk/openai-compatible",
      "settings": {
        "baseURL": "https://llm.example.com/v1",
        "apiKey": "{env:ACME_API_KEY}"
      }
    }
  }
}
```

`npm` з V1 стає `package`, а пакети AI SDK отримують префікс `aisdk:`. `api` стає `settings.baseURL`. Поле `options`
провайдера розділяється на `settings`, `headers` і `body` залежно від ролі в запиті. `options.setCacheKey` стає
`compatibility.supportsPromptCacheKey` на рівні провайдера. Див. [Провайдери](/providers).

У V2 об'єднано два застарілі простори імен провайдерів:

| ID провайдера у V1         | Канонічний ID провайдера у V2 |
| -------------------------- | ----------------------------- |
| `azure-cognitive-services` | `azure`                       |
| `google-vertex-anthropic`  | `google-vertex`               |

Міграція однозначних полів V1 для провайдерів, агентів, команд і фільтрів провайдерів використовує ці канонічні ID.
Спільне поле верхнього рівня `model` зберігає точний ID провайдера, бо такий самий синтаксис коректний і в нативній
конфігурації V2; під час міграції застарілого вбудованого провайдера замініть у цьому полі ID на канонічний.

### Моделі та варіанти

Моделі, як і раніше, вкладені у свого провайдера, але кілька полів моделей стають явнішими:

- `id` стає `modelID`.
- `tool_call` і `modalities` стають `capabilities.tools`, `capabilities.input` і `capabilities.output`.
- `status` зі значенням `"deprecated"` стає `disabled: true`.
- Вартість кешу переноситься з `cache_read` і `cache_write` у `cache.read` і `cache.write`.
- Специфічні для провайдера `options` стають `settings`.
- Об'єкт variants з V1 стає масивом V2, де кожен елемент має `id`.

```jsonc
// V1
{
  "variants": {
    "high": {
      "reasoningEffort": "high"
    }
  }
}

// V2
{
  "variants": [
    {
      "id": "high",
      "settings": {
        "reasoningEffort": "high"
      }
    }
  ]
}
```

Повну нативну структуру моделі описано в розділі [Моделі](/models).

### Підтримувані поля без прямих нативних відповідників

Більшість полів, що зберігають ту саму структуру, зокрема `shell`, `model`, `default_agent`, `watcher`, `formatter`,
`instructions`, `enterprise` і `tool_output`, міграції не потребують.

V2 приймає та зберігає конфігурацію `lsp`, але не запускає мовні сервери, не надає інструментів LSP і не формує
діагностику LSP. Робочі процеси, що залежать від цих можливостей, замініть командами лінтера, перевірки типів або
компілятора вашого проєкту.

Фільтри провайдерів з V1 не мають прямих відповідників серед полів нативної конфігурації V2, але їхня поведінка
підтримується через [політики](/policies):

- `enabled_providers` стає внутрішньою політикою провайдерів, що за замовчуванням забороняє все, після якої йдуть
  дозволи для перелічених провайдерів.
- `disabled_providers` стає внутрішніми політиками заборони для перелічених провайдерів.
- `autoupdate` стає `update`: `false` відповідає `"disable"`, `"notify"` — `"notify"`, а `true` — `"auto"`.
- `small_model` стає вибором `model` для вбудованого агента `title`. У нативній конфігурації V2 використовуйте натомість
  `agents.title.model`.

Ці поля можна залишити в синтаксисі V1. OpenCode нормалізує їх без попереджень.

### Поля, що приймаються, але не підтримуються

Схема V1 також приймала поля, для яких у V2 немає підтримуваної поведінки. V2 ігнорує ці значення й виводить
попередження, щоб їх не сприймали як активну конфігурацію:

- `logLevel`: під час запуску OpenCode використовуйте `OPENCODE_LOG_LEVEL`.
- `server`: використовуйте сервіс V2 і явні параметри сервера; API сервера — навмисна несумісна зміна.
- `subagent_depth` на верхньому рівні: використовуйте натомість `experimental.subagent_depth`.
- `compaction.tail_turns` і `compaction.prune`: натомість V2 використовує `compaction.keep.tokens` і стиснення на основі
  контрольних точок.
- `name` агента в JSON-конфігурації V1.
- Запис MCP з V1, що містить лише `enabled` без `type`.
- Експериментальні поля V1 `batch_tool`, `openTelemetry`, `primary_tools` і `continue_loop_on_deny`.
- Поля провайдера V1 `id`, `whitelist` і `blacklist`.
- Поля моделі провайдера V1 `release_date`, `attachment`, `reasoning`, `temperature`, `experimental`, `status` зі
  значенням, відмінним від `deprecated`, і булеве `interleaved`.

Ці поля ігноруються навмисно, і це не регресія сумісності. Якщо V2 не зберігає поведінку, яку в інших частинах цього
посібника позначено як підтримувану, скористайтеся порадами щодо повідомлення про проблеми в розділі
[Усунення несправностей](/troubleshooting).

### Файли агентів

Файли агентів у V1 можуть лежати в `agent/`, `agents/`, `mode/` або `modes/`. V2 і далі виявляє всі чотири каталоги.
Рекомендоване розташування у V2:

```text
.opencode/agents/<name>.md
```

Файли в каталогах `mode/` або `modes/` з V1 описують основних агентів. Переносячи такий файл в `agents/`, додайте
у frontmatter `mode: primary`. Файли з `agent/` можна перенести в `agents/` без зміни ID, отриманого зі шляху.

Перетворюючи frontmatter на нативні поля V2:

- Залиште тіло Markdown як системні інструкції агента.
- Перейменуйте `prompt` на `system`, якщо воно трапляється в JSON-конфігурації; тілу файлу поле `system` не потрібне.
- Перейменуйте `disable` на `disabled`, а `permission` — на `permissions`.
- Об'єднайте `model` і `variant` у форматі `provider/model#variant`.
- Перенесіть `temperature`, `top_p` і специфічні для провайдера параметри в `request.body`.

V2 автоматично перетворює застарілий frontmatter агентів, тому ці зміни необов'язкові. Див. [Агенти](/agents).

### Файли команд

Файли команд у V1 можуть лежати в `command/` або `commands/`. V2 виявляє обидва каталоги. Рекомендоване розташування:

```text
.opencode/commands/<name>.md
```

Щоб зберегти назви команд, перенесіть файли з `command/` за тим самим відносним шляхом у `commands/`. Тіло Markdown
залишається шаблоном команди, а поля frontmatter `description` і `agent` зберігають назви. Перейменуйте `subtask` на
`subagent`, щоб використовувати нативну назву для делегування у фоні. Якщо у frontmatter є окремі поля `model` і
`variant`, допишіть варіант до моделі й видаліть `variant`:

```yaml
# V1
model: anthropic/claude-sonnet-4-5
variant: high
subtask: true

# V2
model: anthropic/claude-sonnet-4-5#high
subagent: true
```

Див. [Команди](/commands).

### Файли навичок

V2 виявляє навички як у `.opencode/skill/`, так і в `.opencode/skills/`. Рекомендована структура:

```text
.opencode/skills/<skill-id>/SKILL.md
```

Переносьте весь каталог навички, а не лише `SKILL.md`, щоб відносні скрипти, довідкові матеріали та інші допоміжні файли
залишалися доступними. Не змінюйте назву каталогу, щоб зберегти ID навички. Наявний frontmatter і тіло Markdown навичок
не потрібно переписувати для V2. Див. [Навички](/skills).

### Файли інструкцій

Наявні файли `AGENTS.md` залишаються на своїх місцях. V2 виявляє глобальний `~/.config/opencode/AGENTS.md` і файли
`AGENTS.md` у поточному каталозі та вище аж до домашнього. Для проєктів поза домашнім каталогом пошук зупиняється на
корені проєкту.

Якщо налаштування V1 покладалися на резервний варіант `CLAUDE.md`, перенесіть ці вказівки до відповідного `AGENTS.md`.
Наразі V2 виявляє лише `AGENTS.md`; оскільки поведінка V1, не пов'язана з API, має залишатися сумісною, також створіть
issue про сумісність і вкажіть дані відповідного проєкту. Див. [Інструкції](/instructions).

## Конфігурація термінального клієнта

V2 замінює багаторівневі файли `tui.json(c)` з V1 одним глобальним файлом конфігурації термінального клієнта:

```text
~/.config/opencode/cli.json
```

Цей файл належить термінальному клієнту; фоновий сервіс його не завантажує. Якщо `cli.json` немає, під час першого
запуску термінального клієнта V2 підтримувані глобальні налаштування з `tui.json` і збережені вподобання переносяться,
а файли V1 залишаються без змін. Локальна конфігурація клієнта на рівні проєкту не переноситься, бо конфігурація
клієнта у V2 глобальна. Актуальний довідник налаштувань клієнта див. у розділі [Налаштування CLI](/cli/config).

## Плагіни

Перейменуйте `plugin` на `plugins`. Замініть кортеж із пакета й параметрів на об'єкт:

```jsonc
// V1
{
  "plugin": ["opencode-example-plugin", ["./plugin/local.ts", { "enabled": true }]]
}

// V2
{
  "plugins": [
    "opencode-example-plugin",
    {
      "package": "./plugin/local.ts",
      "options": { "enabled": true }
    }
  ]
}
```

V2 виявляє локальні плагіни як у `.opencode/plugin/`, так і в `.opencode/plugins/`; для файлів V2 використовуйте
`.opencode/plugins/`.

<Callout type="warning">
  Реалізації плагінів для V1 у V2 не працюють. Перемістити файл або перейменувати його запис у конфігурації недостатньо.
</Callout>

Перенесіть точки входу, хуки, інструменти, події та експорти пакета за допомогою окремого
[посібника з міграції плагінів](/build/plugins/migrate-v1).

## API сервера та клієнти

OpenCode 2 має перероблений, зручніший API сервера та новий набір клієнтів. Інтеграції, які викликають API сервера V1,
потрібно перевести на API V2.

Для доступу до випущеного API V2 використовуйте пакет `@opencode/client`. Його ендпоінти, типи запитів і відповіді
описано в згенерованому [довіднику API](/api).

## Перевірка налаштувань

Перш ніж покладатися на V2 у щоденній роботі, перевірте в проєкті модель, облікові дані провайдера, агентів, дозволи,
сервери MCP і плагіни. Зберігайте налаштування V1, доки не переконаєтеся, що V2 поводиться так, як вам потрібно, і не
спрямовуйте V1 на конфігурацію, яку ви перетворили на нативний формат V2.
