## Додавання вкладень

Вкладіть локальний файл і попросіть OpenCode використати його у промпті. У десктопному або вебклієнті натисніть
**Attach file**, вставте файл або перетягніть його в поле промпту.

```text
Summarize the attached README.md and list the required setup steps.
```

Файли, вибрані у вікні вибору файлів десктопного застосунку, можуть мати загальний розмір до 20 MiB. Інші інтерфейси
можуть застосовувати нижчі ліміти на боці клієнта.

<Callout type="warning">
  Перш ніж вкладати зображення, виберіть модель, яка підтримує введення зображень. OpenCode може передати провайдеру
  підтримувані зображення, але провайдер і модель однаково застосовують власні обмеження щодо форматів, розмірів у
  пікселях, кількості та розміру файлів. Модель, яка працює лише з текстом, може відхилити запит.
</Callout>

## Синтаксис

У промптах і командах V2 вкладення описується полем `uri` та необов'язковими полями `name` і `description`:

```json
{
  "uri": "file:///home/me/project/src/server.ts",
  "name": "server.ts",
  "description": "HTTP server entrypoint"
}
```

Для файлу або каталогу, доступного серверу, використовуйте абсолютну URL-адресу `file:`. Для текстових файлів додатні
параметри `start` і `end` вибирають рядки (нумерація з одиниці).

```text
file:///home/me/project/src/server.ts?start=20&end=60
```

Щоб передати вміст безпосередньо, використайте URL-адресу `data:`:

```json
{
  "uri": "data:text/plain;base64,SGVsbG8sIE9wZW5Db2RlIQ==",
  "name": "greeting.txt"
}
```

URL-адреси вкладень HTTP і HTTPS не підтримуються. Про програмне надсилання промптів читайте у згенерованому
[довіднику API](/api).

## Формати

Поточні сесії V2 роблять видимими для моделі такі типи вкладень:

| Вхідні дані | Що отримує модель | Приклад |
| --- | --- | --- |
| Текстовий файл UTF-8 | Ім'я файлу та декодований текст | `README.md` |
| Каталог | Нерекурсивний список файлів і каталогів першого рівня | `file:///home/me/` |
| PNG, JPEG, GIF або WebP | Зображення | `diagram.png` |

SVG обробляється як текст. PDF, AVIF, BMP, аудіо, відео та інші бінарні вкладення промпту до запиту моделі не
потрапляють. Спершу перетворіть непідтримуваний бінарний файл на текст або підтримуване зображення — наприклад,
експортуйте сторінку PDF як `page-1.png`, а потім вкладіть її.

OpenCode читає кожне вкладення, перш ніж прийняти промпт. Він відхиляє некоректні URL-адреси, шляхи, які не вдається
прочитати, шляхи, що не є файлами чи каталогами, а також вкладення, розмір яких після декодування перевищує 20 MiB. Тип
медіа визначається за байтами, тому зміна імені файлу або типу медіа в URL-адресі `data:` не зробить непідтримуваний
бінарний файл видимим.

## Зображення

Налаштуйте нормалізацію зображень в `opencode.json` або `opencode.jsonc`:

```jsonc title="opencode.jsonc"
{
  "$schema": "https://opencode.ai/config.json",
  "media": {
    "image": {
      "auto_resize": true,
      "max_width": 2000,
      "max_height": 2000,
      "max_base64_bytes": 5242880,
    },
  },
}
```

Усі поля необов'язкові:

| Поле | За замовчуванням | Поведінка |
| --- | --- | --- |
| `auto_resize` | `true` | Змінює розмір зображення, що перевищує налаштований ліміт; якщо `false`, зображення відхиляється. |
| `max_width` | `2000` | Максимальна ширина в пікселях; має бути додатним цілим числом. |
| `max_height` | `2000` | Максимальна висота в пікселях; має бути додатним цілим числом. |
| `max_base64_bytes` | `5242880` | Максимальна кількість байтів зображення в кодуванні Base64; має бути додатним цілим числом. |

Наприклад, така конфігурація відхиляє зображення, ширші за 1200 пікселів, замість того щоб зменшувати їх:

```jsonc title="opencode.jsonc"
{
  "media": {
    "image": {
      "auto_resize": false,
      "max_width": 1200,
    },
  },
}
```

Ці налаштування застосовуються як до підтримуваних зображень, вкладених у промпти, так і до зображень, які повертає
вбудований інструмент `read`.

## Обробка

Інструмент `read` розпізнає PNG, JPEG, GIF і WebP за вмістом і читає до 20 MiB вихідних даних зображення. Він
перевіряє ширину, висоту й довжину в Base64 на відповідність налаштованим лімітам.

З `auto_resize: true` OpenCode зберігає пропорції та зменшує зображення до лімітів розміру. Потім він пробує дедалі
компактніші кодування PNG і JPEG, доки не вкладеться в ліміт Base64, тому тип медіа результату може змінитися.

```text
Input:  4000 × 2000 WebP
Limits: 2000 × 2000
Output: 2000 × 1000 PNG or JPEG
```

Якщо жодне кодування не вкладається в ліміт, обробка завершується помилкою. З `auto_resize: false` зображення, яке
перевищує будь-який ліміт, без змін спричиняє помилку; зображення, яке не вдається декодувати, також спричиняє помилку.

```text
Input:  2400 × 1600 JPEG
Limit:  max_width = 2000, auto_resize = false
Result: Image processing fails
```

Якщо засіб зміни розміру зображень недоступний, OpenCode передає оригінальне зображення без змін. Тож налаштування
зображень — це обмеження обробки, а не межа завантаження чи безпеки.

## Обмеження

| Обмеження | Значення або поведінка | Приклад |
| --- | --- | --- |
| Пряме вкладення | 20 MiB після декодування на кожен елемент; клієнти можуть встановлювати нижчі ліміти | Два файли по 12 MiB проходять ліміт на елемент |
| Вибір файлів у десктопному застосунку | 20 MiB загалом | Два файли по 12 MiB перевищують ліміт вибору |
| `max_base64_bytes` | Лише закодований Base64, без повної URL-адреси `data:` | `SGVsbG8=` рахується як 8 байтів |
| Ліміти провайдера для зображень | Застосовуються після обробки в OpenCode | Провайдер може відхилити прийняте зображення |
| Підтримка текстових вкладень моделлю | Мультимодальна модель не потрібна | `notes.txt` вставляється як текст промпту |
| Текстові ліміти `read` | Використовує окремі ліміти посторінкового читання й обрізання | Читайте великий журнал частинами |

Те, що клієнт прийняв файл, не гарантує, що його вміст дійде до моделі. Вкладення має бути у форматі, видимому моделі,
і відповідати лімітам як OpenCode, так і провайдера.
