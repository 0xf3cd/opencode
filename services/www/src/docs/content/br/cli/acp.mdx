`opencode acp` executa o OpenCode como um agente do [Agent Client Protocol](https://agentclientprotocol.com), para que
você possa usá-lo a partir de um cliente ACP como o Zed. Este exemplo adiciona o OpenCode ao Zed:

```json title="~/.config/zed/settings.json"
{
  "agent_servers": {
    "OpenCode": {
      "command": "opencode",
      "args": ["acp"]
    }
  }
}
```

Outros clientes ACP usam o mesmo comando e o mesmo argumento `acp`, mas o arquivo de configuração e os nomes dos campos
podem ser diferentes. Se um cliente gráfico não encontrar o `opencode`, defina `command` com o caminho absoluto exibido
por `which opencode`.

## Autenticação

O OpenCode usa as credenciais de provedor que já tem. Faça login em um terminal antes de iniciar o cliente ACP:

```bash
opencode auth login
```

O OpenCode oferece um único método de autenticação, `opencode-login`. Por padrão, ele é um método de autenticação do
agente. A requisição `authenticate` aceita apenas esse método e não coleta credenciais. Se um prompt falhar porque um
provedor exige autenticação, o OpenCode retorna o erro `auth_required` do ACP.

Se o cliente definir `clientCapabilities.auth.terminal` como `true`, o método de autenticação passa a ser um método de
autenticação por terminal:

```json
{
  "id": "opencode-login",
  "name": "Login with opencode",
  "description": "Run `opencode auth login` in the terminal",
  "type": "terminal",
  "args": ["--login"]
}
```

O cliente não deve enviar esse método para `authenticate`. Em vez disso, ele adiciona `--login` ao comando que inicia o
OpenCode, por exemplo `opencode acp --login`, e o executa em um terminal. O OpenCode executa o fluxo de
`opencode auth login` e encerra. O código de saída 0 indica que o login foi bem-sucedido. Em seguida, o cliente se
reconecta e envia `initialize` novamente.

Se o cliente definir `clientCapabilities._meta["terminal-auth"]` como `true`, o método de autenticação inclui o comando
de login:

```json
{
  "id": "opencode-login",
  "name": "Login with opencode",
  "description": "Run `opencode auth login` in the terminal",
  "_meta": { "terminal-auth": { "command": "opencode", "args": ["auth", "login"], "label": "OpenCode Login" } }
}
```

## Solução de problemas

`opencode acp` aguarda mensagens ACP no stdin, então parece travado quando você o executa diretamente em um terminal.
Inicie-o a partir de um cliente ACP.

Se o cliente informar que o processo encerrou ou gravou uma saída de protocolo inválida, adicione `--print-logs` antes de
`acp` nos argumentos do cliente. Assim, o OpenCode grava no stderr os logs do ACP e do servidor privado. O stdout
transporta apenas mensagens ACP.

```bash
opencode --print-logs acp
```

## Referência do protocolo

Esta seção é para quem desenvolve clientes ACP. Ela lista as partes do ACP que o OpenCode suporta e as chaves `_meta`
que o OpenCode adiciona. Clientes que não reconhecem essas chaves podem ignorá-las. A
[documentação do ACP](https://agentclientprotocol.com) define as mensagens.

### Transporte

O cliente inicia `opencode acp` como um processo filho. Os dois trocam mensagens JSON-RPC delimitadas por quebra de linha
pelo stdin e pelo stdout, usando a versão 1 do protocolo ACP.

`opencode acp` inicia um servidor OpenCode privado para uso próprio. Ele não se conecta ao serviço compartilhado em
segundo plano e não abre uma porta de rede para o ACP. Um único processo pode atender várias sessões ACP. Ele encerra
quando o cliente fecha o stdin.

### Capacidades

A resposta de `initialize` do OpenCode inclui estas capacidades do agente:

```json
{
  "loadSession": true,
  "mcpCapabilities": { "http": true, "sse": false },
  "promptCapabilities": { "embeddedContext": true, "image": true },
  "sessionCapabilities": {
    "additionalDirectories": {},
    "close": {},
    "delete": {},
    "fork": {},
    "list": {},
    "resume": {}
  }
}
```

O OpenCode lê estas capacidades do cliente:

| Capacidade                               | Efeito                                                                     |
| ---------------------------------------- | -------------------------------------------------------------------------- |
| `auth.terminal` definida como `true`     | O método de autenticação é um [método por terminal](#authentication).      |
| `elicitation.form`                       | O OpenCode faz [perguntas](#questions) como formulários.                   |
| `session.compaction`                     | O OpenCode informa a [compactação](#compaction) com as atualizações do ACP. |
| `_meta["terminal-auth"]` definida como `true` | O método de autenticação inclui o [comando de login](#authentication). |

### Sessões

O cliente define o diretório de trabalho ao criar uma sessão. O OpenCode usa a configuração desse diretório, incluindo
modelos, agentes, comandos, skills, instruções, plugins e servidores MCP.

- `cwd` deve ser um caminho absoluto. O OpenCode rejeita um `cwd` relativo com um erro de parâmetros inválidos.
- `session/load` reproduz as mensagens salvas. `session/resume` e `session/fork` não as reproduzem.
- Para carregar, retomar ou criar um fork de uma sessão, o cliente deve passar o diretório dessa sessão como `cwd`. O
  OpenCode rejeita um `cwd` diferente com um erro de parâmetros inválidos.
- `session/list` retorna até 100 sessões por página. Ele aceita um filtro `cwd` e um `cursor`.
- `session/close` interrompe o trabalho em andamento e desvincula a sessão do processo ACP. O OpenCode mantém a sessão
  salva.
- `session/delete` encerra um prompt ativo como `session/cancel` e depois remove a sessão. Excluir uma sessão que não
  existe é bem-sucedido.
- Uma sessão executa um prompt por vez. O OpenCode retorna um erro para um segundo `session/prompt` enquanto o primeiro
  estiver ativo.

### Cancelamento

`session/cancel` encerra o prompt ativo com `stopReason: "cancelled"`. Um `$/cancel_request` para a requisição do prompt
tem o mesmo efeito. O OpenCode rejeita as solicitações de permissão pendentes e informa como `failed` as chamadas de
ferramenta que não terminam depois de um cancelamento.

### Diretórios adicionais

O cliente pode passar `additionalDirectories` em `session/new`, `session/load`, `session/resume` e `session/fork`:

```json
{ "cwd": "/work/app", "additionalDirectories": ["/work/shared"], "mcpServers": [] }
```

- Cada entrada deve ser um caminho absoluto sem `*` nem `?`.
- O OpenCode permite acesso a diretórios externos dentro de cada raiz. As regras de permissão de leitura, edição e shell
  continuam valendo.
- A lista de cada requisição substitui a lista anterior da sessão, conforme especificado no
  [RFD de diretórios adicionais](https://agentclientprotocol.com/rfds/additional-directories).
- O OpenCode armazena essas concessões na sessão, então elas também valem quando outro cliente do OpenCode usa a sessão.
  Sessões filhas copiam as concessões quando o OpenCode as cria.

`session/list` retorna em `additionalDirectories` a lista armazenada de cada sessão.

### Opções de configuração

Novas sessões usam o modelo padrão e o agente primário do diretório. As respostas de `session/new`, `session/load`,
`session/resume` e `session/fork` incluem estas opções de configuração:

| ID       | Categoria       | Valores                                                                                     |
| -------- | --------------- | ------------------------------------------------------------------------------------------- |
| `model`  | `model`         | Modelos ativados, no formato `provider/model`. Um sufixo `/variant` também define o esforço. |
| `effort` | `thought_level` | As variantes do modelo e `default`. Presente apenas para modelos com variantes.             |
| `mode`   | `mode`          | Agentes primários visíveis.                                                                 |

`session/set_config_option` recebe valores do tipo string:

```json
{ "sessionId": "ses_123", "configId": "model", "value": "anthropic/claude-sonnet-4" }
```

`session/set_mode` também define o agente. O OpenCode envia `config_option_update` quando os modelos ou agentes
disponíveis mudam. Ele também envia essa atualização quando outro cliente altera o modelo ou o agente da sessão.

### Conteúdo do prompt

Os prompts podem conter texto, imagens, recursos incorporados e links de recursos. O OpenCode ignora blocos de áudio e
trata os demais blocos assim:

| Bloco                                                     | O que o OpenCode faz                                                                              |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `text`                                                    | Envia o bloco ao modelo.                                                                          |
| `text` com público apenas `assistant`                     | Envia o bloco ao modelo como contexto separado, fora da mensagem do usuário.                      |
| `text` com público apenas `user`                          | Deixa o bloco fora da entrada do modelo.                                                          |
| `image` com `data`                                        | Anexa a imagem ao prompt.                                                                         |
| `image` apenas com `uri`                                  | Trata o bloco como um link de recurso.                                                            |
| `resource` com `text`                                     | Insere o texto depois do caminho ou da URI do recurso.                                            |
| `resource` com `blob`                                     | Anexa o recurso se ele tiver um `mimeType`. Caso contrário, descarta-o.                           |
| `resource_link` para uma URI `file://`                    | Anexa o arquivo. Se o arquivo não existir ou não puder ser lido, envia um link Markdown no lugar. |
| `resource_link` para uma URI `zed://` com a query `path`  | Anexa o arquivo indicado em `path`.                                                               |
| `resource_link` para outra URI                            | Envia um link Markdown como `[spec](https://example.com/spec.md)`.                                |

O público vem das `annotations` do bloco. O OpenCode rejeita um bloco `image` que não tenha nem `data` nem `uri`. Este
bloco é contexto apenas para o modelo:

```json
{ "type": "text", "text": "Open file: src/app.ts", "annotations": { "audience": ["assistant"] } }
```

### Comandos

Depois de `session/new`, `session/load`, `session/resume` ou `session/fork`, o OpenCode envia
`available_commands_update` com os comandos do diretório e o comando integrado `compact`. Ele envia outra atualização
quando os comandos mudam.

```json
{
  "sessionUpdate": "available_commands_update",
  "availableCommands": [{ "name": "compact", "description": "Compact the session" }]
}
```

Se um prompt começar com `/` seguido do nome de um comando disponível, o OpenCode executa esse comando usando o restante
do texto como argumentos. Outros textos que começam com `/` são enviados como um prompt normal. `/compact` executa a
[compactação](/compaction).

### Servidores MCP

O cliente pode passar servidores MCP stdio e HTTP em `session/new`, `session/load`, `session/resume` e `session/fork`.
O OpenCode os adiciona ao diretório da sessão enquanto o processo `opencode acp` estiver ativo, então outras sessões
nesse diretório também podem usá-los. O OpenCode repassa os cabeçalhos HTTP e não usa OAuth para esses servidores. Ele
não anuncia MCP via SSE e não suporta MCP via ACP.

```json
{ "type": "http", "name": "docs", "url": "https://mcp.example.com", "headers": [] }
```

### Permissões

As solicitações de permissão oferecem três opções:

```json
[
  { "optionId": "once", "kind": "allow_once", "name": "Allow once" },
  { "optionId": "always", "kind": "allow_always", "name": "Always allow" },
  { "optionId": "reject", "kind": "reject_once", "name": "Reject" }
]
```

Quando uma solicitação altera arquivos, o OpenCode inclui conteúdo `diff` se conseguir gerar uma prévia da alteração.

### Perguntas

Se o cliente anunciar `elicitation.form`, o OpenCode faz perguntas com `elicitation/create` no modo de formulário. A
requisição inclui `toolCallId` quando o OpenCode enviou essa chamada de ferramenta como um `session/update` para esta
sessão.

```json
{
  "mode": "form",
  "sessionId": "ses_123",
  "toolCallId": "call_1",
  "message": "Which package manager?",
  "requestedSchema": {
    "type": "object",
    "properties": { "pm": { "type": "string", "oneOf": [{ "const": "bun", "title": "Bun" }] } },
    "required": ["pm"]
  }
}
```

- O OpenCode nunca envia formulários que possam coletar segredos.
- Se um campo aceitar uma resposta digitada além das opções, o schema adiciona uma propriedade string opcional
  `<key>_custom`. Em uma escolha única, uma resposta personalizada não vazia substitui a opção selecionada. Em uma
  escolha múltipla, o OpenCode a adiciona às opções selecionadas.
- Se o usuário recusar ou cancelar o formulário, o OpenCode cancela a pergunta.

Se o OpenCode não conseguir exibir uma pergunta, ele a cancela e instrui o modelo a continuar sem resposta.

### Compactação

Se o cliente anunciar `session.compaction`, o OpenCode informa a compactação com as atualizações `compaction_update` e
`compaction_summary_chunk` do RFD de [compactação de sessão](https://agentclientprotocol.com/rfds/session-compaction) do
ACP, que está em Preview. Quando o cliente carrega uma sessão, o OpenCode reproduz cada compactação concluída ou com falha
como uma única atualização.

```json
{
  "sessionUpdate": "compaction_update",
  "compactionId": "msg_123",
  "status": "completed",
  "summary": [{ "type": "text", "text": "..." }]
}
```

Os demais clientes recebem o [marcador de compactação](#compaction-marker). O mesmo vale para compactações de sessões
filhas.

### Uso

A resposta do prompt inclui `usage`, do RFD de [uso ao fim do turno](https://agentclientprotocol.com/rfds/end-turn-token-usage),
que ainda é um rascunho. `usage` soma as chamadas ao modelo feitas pelo prompt nesta sessão. Não inclui sessões filhas.

```json
{ "stopReason": "end_turn", "usage": { "inputTokens": 1200, "outputTokens": 340, "totalTokens": 1540 }, "_meta": {} }
```

Antes da resposta, o OpenCode envia `usage_update`, do RFD de
[uso da sessão](https://agentclientprotocol.com/rfds/session-usage). Ele só envia essa atualização se o prompt tiver
usado tokens e o OpenCode souber o tamanho do contexto do modelo. `cost` é o custo total da sessão em USD.

```json
{ "sessionUpdate": "usage_update", "used": 1540, "size": 200000, "cost": { "amount": 0.012, "currency": "USD" } }
```

### Sessões filhas

Enquanto um prompt é executado, o OpenCode envia as atualizações das sessões filhas como notificações `session/update` na
sessão do prompt. Cada atualização traz `_meta["opencode/child-session"]`. O OpenCode prefixa os IDs das chamadas de
ferramenta com `<childSessionId>:` e, se a sessão filha tiver título, prefixa também os títulos das chamadas de
ferramenta com ele.

```json
{
  "sessionUpdate": "tool_call",
  "toolCallId": "ses_child:call_1",
  "title": "Explore the codebase: src/app.ts",
  "_meta": {
    "opencode/child-session": { "id": "ses_child", "parentID": "ses_123", "depth": 1, "title": "Explore the codebase" }
  }
}
```

| Campo      | Tipo     | Descrição                                                                                           |
| ---------- | -------- | --------------------------------------------------------------------------------------------------- |
| `id`       | `string` | O ID da sessão filha.                                                                               |
| `parentID` | `string` | O ID da sessão pai da sessão filha.                                                                 |
| `depth`    | `number` | 1 para uma filha da sessão do prompt, 2 para uma filha dessa sessão filha, e assim por diante.      |
| `title`    | `string` | O título da sessão filha. O OpenCode o omite quando a sessão filha não tem título.                  |

As solicitações de permissão de uma sessão filha trazem a mesma chave em `toolCall._meta`. Depois que o prompt termina,
o OpenCode para de enviar atualizações das sessões filhas. As solicitações de permissão e as perguntas das sessões filhas
continuam chegando ao cliente.

### Status de nova tentativa

Quando uma chamada ao modelo falha e o OpenCode agenda uma nova tentativa, ele envia `session_info_update` com
`_meta["opencode/retry"]`. Quando a nova tentativa começa, o OpenCode envia `"opencode/retry": null`. Limpe qualquer
status de nova tentativa quando a resposta do prompt chegar.

```json
{
  "sessionUpdate": "session_info_update",
  "_meta": {
    "opencode/retry": {
      "attempt": 1,
      "nextRetryAt": "2026-10-02T12:00:05.000Z",
      "error": { "type": "provider.rate-limit", "message": "Rate limit exceeded", "status": 429 }
    }
  }
}
```

| Campo         | Tipo     | Descrição                                                                                         |
| ------------- | -------- | ------------------------------------------------------------------------------------------------- |
| `attempt`     | `number` | O número da tentativa.                                                                            |
| `nextRetryAt` | `string` | O horário da próxima tentativa, no formato ISO 8601.                                              |
| `error`       | `object` | Contém `type` e `message`. Também contém `status` e `response.body` se o provedor os tiver enviado. |

### Marcador de compactação

Se o cliente não anunciar `session.compaction`, o OpenCode informa o progresso da compactação como `session_info_update`
com `_meta["opencode/compaction"]`. O OpenCode sempre usa o marcador para compactações de sessões filhas.

```json
{
  "sessionUpdate": "session_info_update",
  "_meta": { "opencode/compaction": { "status": "started", "messageId": "msg_123", "reason": "auto" } }
}
```

| Campo       | Tipo     | Descrição                                                                                       |
| ----------- | -------- | ----------------------------------------------------------------------------------------------- |
| `status`    | `string` | `started`, `completed` ou `failed`. Uma compactação cancelada é `failed`.                       |
| `messageId` | `string` | Relaciona o início de uma compactação ao seu fim. Trate-o como uma chave opaca.                 |
| `reason`    | `string` | `auto` ou `manual`.                                                                             |
| `error`     | `object` | Presente quando `status` é `failed`. Tem o mesmo formato do `error` da [nova tentativa](#retry-status). |

O marcador não inclui um resumo. Uma compactação automática pode falhar sem um marcador `started`. Quando o cliente
carrega uma sessão, o OpenCode reproduz cada compactação concluída ou com falha como um único marcador.
