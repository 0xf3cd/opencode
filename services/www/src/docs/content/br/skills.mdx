---
title: "Skills"
---

Crie uma skill para dar a um agente instruções reutilizáveis para uma tarefa específica. Coloque um arquivo `SKILL.md`
em `.opencode/skills/<skill-id>` e descreva em `description` quando ela deve ser usada.

```markdown title=".opencode/skills/git-release/SKILL.md"
---
name: Git Release
description: Prepare release notes, version bumps, and GitHub releases
---

## Workflow

1. Read `references/release-policy.md`.
2. Summarize merged changes since the previous tag.
3. Propose the version bump before changing files.
4. Run `scripts/changelog.ts` only after the user approves the version.
```

O OpenCode anuncia essa skill quando ela é relevante. O agente pode então carregar as instruções com a ferramenta
`skill`, em vez de incluir todas as skills em todos os prompts.

## Criar

Mantenha scripts, referências e templates relacionados ao lado do `SKILL.md`:

```text
.opencode/skills/
└── git-release/
    ├── SKILL.md
    ├── scripts/
    │   └── changelog.ts
    └── references/
        └── release-policy.md
```

Os caminhos escritos dentro da skill são relativos ao diretório que contém o `SKILL.md`. A forma de diretório é a
recomendada, porque dá aos arquivos de apoio um diretório base próprio.

## Descoberta

O OpenCode procura automaticamente nestes locais:

| Escopo                    | Fontes                                 |
| ------------------------- | -------------------------------------- |
| Global                    | `~/.config/opencode/skills`            |
| Compatibilidade global    | `~/.claude/skills`, `~/.agents/skills` |
| Projeto                   | `.opencode/skills`                     |
| Compatibilidade de projeto | `.claude/skills`, `.agents/skills`    |

Nas fontes de projeto, o OpenCode procura a partir do diretório atual até a raiz do projeto e inclui os diretórios
correspondentes em todos os níveis.

Cada fonte pode conter qualquer uma das duas formas:

```text
skills/
├── review.md
└── git-release/
    └── SKILL.md
```

- Arquivos Markdown precisam estar na raiz da fonte, como `skills/review.md`.
- Arquivos com o nome exato `SKILL.md` podem estar em qualquer profundidade, como `skills/git-release/SKILL.md`.

## Fontes

Adicione outros diretórios locais ou catálogos HTTP com o array `skills` em qualquer `opencode.json` ou
`opencode.jsonc`:

```jsonc title="opencode.jsonc"
{
  "$schema": "https://opencode.ai/config.json",
  "skills": [
    "./team-skills",
    "~/shared/opencode-skills",
    "/opt/company-skills",
    "https://example.com/opencode/skills/",
  ],
}
```

| Valor | Resolução |
| ----- | --------- |
| Caminho relativo | A partir do diretório de trabalho ativo do OpenCode, não do arquivo de configuração |
| Caminho com `~/` | A partir do diretório home do usuário atual |
| Caminho absoluto | Usado como está escrito |
| URL `http://` ou `https://` | Carregada como catálogo HTTP |

Cada arquivo de configuração encontrado contribui com as próprias entradas. Os arrays `skills` são combinados, e não
substituídos.

## Catálogos

Um catálogo HTTP é uma URL base com um arquivo `index.json`:

```json title="index.json"
{
  "skills": [
    {
      "name": "git-release",
      "version": "3",
      "files": ["git-release.md", "references/release-policy.md"]
    }
  ]
}
```

Para essa entrada, o OpenCode baixa cada arquivo de `<base-url>/git-release/<file>`.

| Regra | Requisito |
| ----- | --------- |
| Caminhos | Precisam ser seguros, relativos e da mesma origem |
| Arquivo de entrada | Inclua `SKILL.md` ou `<name>.md`, como `git-release.md` |
| Atualizações | Incremente `version` quando os arquivos mudarem, para que o OpenCode atualize o cache |

Em um catálogo HTTP, prefira a forma de Markdown nomeado. Cada diretório de skill baixado vira uma raiz de fonte, então
`git-release.md` tem o ID `git-release`. Atualmente, na V2, um `SKILL.md` na raiz recebe literalmente o ID `SKILL`.

## Frontmatter

Use o frontmatter para dar nome à skill e controlar onde ela aparece:

```markdown title="SKILL.md"
---
name: Git Release
description: Prepare a repository release
metadata:
  opencode/autoinvoke: false
---

Prepare the changelog, version bump, tag, and release notes.
```

| Campo                          | Comportamento                                                          |
| ------------------------------ | ---------------------------------------------------------------------- |
| `name`                         | Nome de exibição; por padrão, é o ID derivado do caminho               |
| `description`                  | Resumo usado para apresentar a skill ao modelo                         |
| `metadata.opencode/autoinvoke` | Defina como `false` para omitir a skill da lista disponível ao modelo  |
| `disable-model-invocation`     | Defina como `true` para ter o mesmo efeito de `opencode/autoinvoke: false` |

Todo o frontmatter é opcional em tempo de execução. Adicione uma `description` clara quando o modelo precisar descobrir a
skill; skills sem descrição não são anunciadas.

`opencode/autoinvoke: false` apenas oculta a skill da lista disponível ao modelo. A skill continua registrada e ainda
pode ser carregada explicitamente pelo ID. Quando `disable-model-invocation` e `opencode/autoinvoke` estão definidos ao
mesmo tempo, `opencode/autoinvoke` prevalece. A V2 aceita campos de portabilidade, como `license` e `compatibility`, mas
não os interpreta.

## IDs

O caminho do arquivo determina o ID da skill. O `name` do frontmatter é só um rótulo de exibição.

| Arquivo                           | ID            |
| --------------------------------- | ------------- |
| `<source>/git-release.md`         | `git-release` |
| `<source>/git-release/SKILL.md`   | `git-release` |
| `<source>/teams/release/SKILL.md` | `release`     |

Os IDs são exatos e diferenciam maiúsculas de minúsculas. Para skills portáveis, use um ID único em kebab-case
minúsculo, com 1–64 caracteres, e mantenha-o igual ao nome do diretório:

```text
^[a-z0-9]+(-[a-z0-9]+)*$
```

Atualmente, a V2 não exige esse padrão, a recomendação de 1–64 caracteres, a correspondência entre `name` e o diretório
nem um tamanho máximo para a descrição.

## Precedência

As skills são selecionadas pelo ID. Se duas fontes definem `git-release`, a fonte registrada por último fornece a skill
que o OpenCode carrega:

```text
~/.config/opencode/skills/git-release/SKILL.md  ← lower precedence
.opencode/skills/git-release/SKILL.md           ← loaded
```

As fontes são registradas da menor para a maior precedência:

1. Skills integradas
2. `.claude/skills`, primeiro a global e depois do ancestral mais distante em direção ao diretório atual
3. `.agents/skills`, primeiro a global e depois do ancestral mais distante em direção ao diretório atual
4. `~/.config/opencode/skills`
5. `.opencode/skills` do projeto, da raiz do projeto em direção ao diretório atual
6. Entradas explícitas de `skills` na configuração, na ordem de prioridade da configuração e na ordem do array

Evite IDs duplicados, a menos que você queira sobrescrever uma skill anterior.

## Carregamento

A cada etapa do modelo, o OpenCode lista as skills permitidas que têm descrição e não definem `opencode/autoinvoke`
como `false`. A lista inclui apenas o ID, o nome e a descrição, não o corpo completo em Markdown.

O modelo carrega uma skill chamando a ferramenta `skill` com o ID exato:

```json title="skill tool input"
{
  "id": "git-release"
}
```

Em seguida, o OpenCode:

1. Seleciona a definição atual para esse ID.
2. Verifica a permissão `skill` do agente selecionado.
3. Adiciona à conversa o corpo em Markdown, sem o frontmatter.
4. Informa o diretório base da skill e uma amostra de até dez caminhos de arquivos de apoio.

Para carregar uma skill você mesmo, mencione-a no prompt como `@skill-id`.

O conteúdo dos arquivos de apoio não é carregado automaticamente. O agente os lê quando a skill pede. A amostra de
arquivos está disponível para skills `SKILL.md` em diretório; skills em Markdown simples não recebem uma lista dos
arquivos vizinhos.

## Permissões

Use a ação `skill` e o ID da skill como recurso. As regras são avaliadas em ordem, e a última regra correspondente
prevalece:

```jsonc title="opencode.jsonc"
{
  "permissions": [
    { "action": "skill", "resource": "*", "effect": "allow" },
    { "action": "skill", "resource": "internal-*", "effect": "deny" },
    { "action": "skill", "resource": "experimental-*", "effect": "ask" },
  ],
}
```

| Efeito | Comportamento |
| ------ | ------------- |
| `allow` | Anuncia e carrega as skills correspondentes sem pedir aprovação |
| `ask` | Anuncia as skills correspondentes e pede confirmação antes de carregá-las |
| `deny` | Oculta do modelo as skills correspondentes e recusa o carregamento |

Coloque as mesmas regras em `agents.<id>.permissions` para aplicá-las a um único agente.

## Solução de problemas

Por exemplo, o ID desta skill é `release`, e não o nome `Git Release` definido no frontmatter:

```text
.opencode/skills/release/SKILL.md
                      └─ ID: release
```

Se uma skill não aparece ou carrega o conteúdo errado:

1. Confirme que o arquivo é um `*.md` na raiz ou um arquivo aninhado com o nome exato `SKILL.md`.
2. Verifique o ID derivado do caminho, que diferencia maiúsculas de minúsculas, e não o `name` do frontmatter.
3. Adicione uma `description` se o modelo precisar descobrir a skill.
4. Verifique `opencode/autoinvoke` e as permissões `skill` do agente selecionado.
5. Procure uma fonte posterior que defina o mesmo ID.
6. Em catálogos HTTP, verifique o `index.json`, se os caminhos dos arquivos são da mesma origem e se o `version` mudou.
