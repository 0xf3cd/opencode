---
title: "Skills"
---

Créez un skill pour fournir à un agent des instructions réutilisables pour une tâche précise. Placez un fichier
`SKILL.md` dans `.opencode/skills/<skill-id>` et indiquez dans `description` quand l'utiliser.

```markdown title=".opencode/skills/git-release/SKILL.md"
---
name: Git Release
description: Prepare release notes, version bumps, and GitHub releases
---

## Workflow

1. Read `references/release-policy.md`.
2. Summarize merged changes since the previous tag.
3. Propose the version bump before changing files.
4. Run `scripts/changelog.ts` only after the user approves the version.
```

OpenCode signale ce skill à l'agent lorsqu'il est pertinent. L'agent peut alors charger ses instructions avec l'outil
`skill`, au lieu d'ajouter tous les skills à chaque prompt.

## Création

Placez les scripts, références et modèles associés à côté de `SKILL.md` :

```text
.opencode/skills/
└── git-release/
    ├── SKILL.md
    ├── scripts/
    │   └── changelog.ts
    └── references/
        └── release-policy.md
```

Les chemins écrits dans le skill sont relatifs au répertoire qui contient `SKILL.md`. La forme répertoire est recommandée,
car elle donne aux fichiers annexes un répertoire de base qui leur est propre.

## Découverte

OpenCode recherche automatiquement dans ces emplacements :

| Portée                  | Sources                                |
| ----------------------- | -------------------------------------- |
| Globale                 | `~/.config/opencode/skills`            |
| Globale (compatibilité) | `~/.claude/skills`, `~/.agents/skills` |
| Projet                  | `.opencode/skills`                     |
| Projet (compatibilité)  | `.claude/skills`, `.agents/skills`     |

Pour les sources de projet, OpenCode remonte du répertoire courant jusqu'à la racine du projet et inclut les répertoires
correspondants à chaque niveau.

Chaque source peut contenir l'une ou l'autre forme :

```text
skills/
├── review.md
└── git-release/
    └── SKILL.md
```

- Les fichiers Markdown doivent se trouver à la racine de la source, par exemple `skills/review.md`.
- Les fichiers nommés exactement `SKILL.md` peuvent se trouver à n'importe quelle profondeur, par exemple
  `skills/git-release/SKILL.md`.

## Sources

Ajoutez d'autres répertoires locaux ou catalogues HTTP avec le tableau `skills` dans n'importe quel fichier
`opencode.json` ou `opencode.jsonc` :

```jsonc title="opencode.jsonc"
{
  "$schema": "https://opencode.ai/config.json",
  "skills": [
    "./team-skills",
    "~/shared/opencode-skills",
    "/opt/company-skills",
    "https://example.com/opencode/skills/",
  ],
}
```

| Valeur | Résolution |
| ------ | ---------- |
| Chemin relatif | Par rapport au répertoire de travail actif d'OpenCode, et non au fichier de configuration |
| Chemin `~/` | Par rapport au répertoire personnel de l'utilisateur courant |
| Chemin absolu | Utilisé tel quel |
| URL `http://` ou `https://` | Chargée comme catalogue HTTP |

Chaque fichier de configuration découvert apporte ses entrées. Les tableaux `skills` sont combinés, et non remplacés.

## Catalogues

Un catalogue HTTP est une URL de base qui expose un fichier `index.json` :

```json title="index.json"
{
  "skills": [
    {
      "name": "git-release",
      "version": "3",
      "files": ["git-release.md", "references/release-policy.md"]
    }
  ]
}
```

Pour cette entrée, OpenCode télécharge chaque fichier depuis `<base-url>/git-release/<file>`.

| Règle | Exigence |
| ----- | -------- |
| Chemins | Doivent être sûrs, relatifs et de même origine |
| Fichier d'entrée | Incluez `SKILL.md` ou `<name>.md`, par exemple `git-release.md` |
| Mises à jour | Incrémentez `version` lorsque les fichiers changent pour qu'OpenCode actualise son cache |

Dans un catalogue HTTP, privilégiez la forme Markdown nommée. Chaque répertoire de skill téléchargé devient une racine
de source : `git-release.md` a donc l'ID `git-release`. Dans V2, un `SKILL.md` placé à la racine a actuellement l'ID
littéral `SKILL`.

## Frontmatter

Utilisez le frontmatter pour nommer le skill et contrôler où il apparaît :

```markdown title="SKILL.md"
---
name: Git Release
description: Prepare a repository release
metadata:
  opencode/autoinvoke: false
---

Prepare the changelog, version bump, tag, and release notes.
```

| Champ                          | Comportement                                                                 |
| ------------------------------ | ---------------------------------------------------------------------------- |
| `name`                         | Nom d'affichage ; par défaut, l'ID dérivé du chemin                          |
| `description`                  | Résumé utilisé pour présenter le skill au modèle                             |
| `metadata.opencode/autoinvoke` | Définissez-le sur `false` pour retirer le skill de la liste proposée au modèle |
| `disable-model-invocation`     | Définissez-le sur `true` pour obtenir le même effet que `opencode/autoinvoke: false` |

Au runtime, tout le frontmatter est facultatif. Ajoutez une `description` claire si le modèle doit découvrir le skill :
les skills qui n'en ont pas ne sont pas proposés.

`opencode/autoinvoke: false` masque seulement le skill dans la liste proposée au modèle. Le skill reste enregistré et
peut toujours être chargé explicitement par son ID. Si `disable-model-invocation` et `opencode/autoinvoke` sont tous deux
définis, `opencode/autoinvoke` l'emporte. V2 accepte des champs de portabilité comme `license` et `compatibility`, mais
ne les interprète pas.

## ID

Le chemin du fichier détermine l'ID du skill. Le champ de frontmatter `name` n'est qu'un libellé d'affichage.

| Fichier                           | ID            |
| --------------------------------- | ------------- |
| `<source>/git-release.md`         | `git-release` |
| `<source>/git-release/SKILL.md`   | `git-release` |
| `<source>/teams/release/SKILL.md` | `release`     |

Les ID sont exacts et sensibles à la casse. Pour des skills portables, utilisez un ID unique en kebab-case minuscule de 1
à 64 caractères, identique au nom du répertoire :

```text
^[a-z0-9]+(-[a-z0-9]+)*$
```

Pour l'instant, V2 n'impose ni ce motif, ni la longueur recommandée de 1 à 64 caractères, ni la correspondance entre
`name` et le répertoire, ni une longueur maximale de description.

## Priorité

Les skills sont sélectionnés par ID. Si deux sources définissent `git-release`, c'est la source enregistrée en dernier
qui fournit le skill chargé par OpenCode :

```text
~/.config/opencode/skills/git-release/SKILL.md  ← lower precedence
.opencode/skills/git-release/SKILL.md           ← loaded
```

Les sources sont enregistrées de la priorité la plus basse à la plus élevée :

1. Skills intégrés
2. `.claude/skills`, d'abord la source globale, puis de l'ancêtre le plus éloigné vers le répertoire courant
3. `.agents/skills`, d'abord la source globale, puis de l'ancêtre le plus éloigné vers le répertoire courant
4. `~/.config/opencode/skills`
5. `.opencode/skills` du projet, de la racine du projet vers le répertoire courant
6. Entrées explicites `skills` de la configuration, selon la priorité de configuration et l'ordre du tableau

Évitez les ID en double, sauf si vous voulez remplacer un skill défini plus tôt.

## Chargement

À chaque étape du modèle, OpenCode liste les skills autorisés qui ont une description et ne définissent pas
`opencode/autoinvoke` sur `false`. La liste contient uniquement l'ID, le nom et la description, pas le corps Markdown
complet.

Le modèle charge un skill en appelant l'outil `skill` avec son ID exact :

```json title="skill tool input"
{
  "id": "git-release"
}
```

OpenCode effectue alors les opérations suivantes :

1. Il sélectionne la définition actuelle pour cet ID.
2. Il vérifie la permission `skill` de l'agent sélectionné.
3. Il ajoute le corps Markdown, sans le frontmatter, à la conversation.
4. Il fournit le répertoire de base du skill et un échantillon de dix chemins de fichiers annexes au maximum.

Pour charger un skill vous-même, mentionnez-le dans votre prompt sous la forme `@skill-id`.

Le contenu des fichiers annexes n'est pas chargé automatiquement. L'agent les lit lorsque le skill le lui demande.
L'échantillon de fichiers est disponible pour les skills `SKILL.md` en forme répertoire ; les skills Markdown simples ne
reçoivent pas de liste des fichiers voisins.

## Permissions

Utilisez l'action `skill` avec l'ID du skill comme ressource. Les règles s'appliquent dans l'ordre, et la dernière règle
correspondante l'emporte :

```jsonc title="opencode.jsonc"
{
  "permissions": [
    { "action": "skill", "resource": "*", "effect": "allow" },
    { "action": "skill", "resource": "internal-*", "effect": "deny" },
    { "action": "skill", "resource": "experimental-*", "effect": "ask" },
  ],
}
```

| Effet | Comportement |
| ----- | ------------ |
| `allow` | Propose et charge les skills correspondants sans approbation |
| `ask` | Propose les skills correspondants et demande une confirmation avant de les charger |
| `deny` | Masque les skills correspondants au modèle et refuse leur chargement |

Placez les mêmes règles sous `agents.<id>.permissions` pour ne les appliquer qu'à un seul agent.

## Dépannage

Par exemple, l'ID de ce skill est `release`, et non son nom de frontmatter `Git Release` :

```text
.opencode/skills/release/SKILL.md
                      └─ ID: release
```

Si un skill est introuvable ou charge le mauvais contenu :

1. Vérifiez que le fichier est soit un `*.md` à la racine, soit un fichier imbriqué nommé exactement `SKILL.md`.
2. Vérifiez l'ID dérivé du chemin, sensible à la casse, plutôt que le champ de frontmatter `name`.
3. Ajoutez une `description` si le modèle doit découvrir le skill.
4. Vérifiez `opencode/autoinvoke` et les permissions `skill` de l'agent sélectionné.
5. Recherchez une source ultérieure qui définit le même ID.
6. Pour les catalogues HTTP, vérifiez `index.json`, que les chemins de fichiers sont de même origine et que `version` a
   bien été modifié.
