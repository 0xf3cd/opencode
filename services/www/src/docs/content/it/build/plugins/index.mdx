title: "Panoramica"
---

I plugin possono modificare il comportamento di OpenCode e aggiungere nuove funzionalità. Per modificare l'interfaccia da
terminale, crea un [plugin CLI](/build/plugins/cli).

Devi migrare un plugin esistente di OpenCode 1? Segui la [guida alla migrazione dei plugin V1](/build/plugins/migrate-v1).

```ts title=".opencode/plugins/example/index.ts"
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "example",
  async setup(ctx) {
    await ctx.storage.set("loaded", true)
  },
})
```

I plugin in `.opencode/plugins/` vengono caricati automaticamente, come l'esempio locale qui sopra. Per caricare pacchetti
pubblicati o directory di plugin che si trovano altrove, aggiungili a `plugins` in `opencode.json(c)`:

```jsonc title="opencode.jsonc"
{
  "$schema": "https://opencode.ai/config.json",
  "plugins": [
    "opencode-acme-plugin",
    "opencode-acme-plugin@1.2.0",
    "@acme/opencode-plugin",
    "./plugins/local",
    "../shared/plugin",
    "/absolute/path/plugin",
    "file:///home/me/plugins/local",
    {
      "package": "@acme/opencode-plugin",
      "options": {
        "agent": "reviewer",
        "strict": true,
      },
    },
  ],
}
```

Consulta [Configurare i plugin](/plugins) per altre opzioni di caricamento e configurazione.

## Ciclo di vita

`setup` viene eseguito quando il plugin viene caricato. Può restituire una funzione di pulizia, eseguita quando il plugin
viene scaricato.

```ts
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "example",
  setup(ctx) {
    console.log(`loaded in OpenCode ${ctx.app.version}`)
    return () => console.log("unloaded")
  },
})
```

### Contesto

Il contesto del plugin è essenzialmente un [client del server OpenCode](/build/client). I suoi metodi di lettura e di
azione usano gli stessi input e le stesse risposte del client. In più, aggiunge metodi riservati ai plugin per
trasformazioni, hook di runtime, ricaricamenti, registrazioni e opzioni del plugin.

```ts
setup(ctx) {
  console.log(ctx.app.version)
}
```

`ctx.location` descrive la posizione in cui è caricata questa istanza del plugin. Include `directory`, il campo opzionale
`workspaceID` e i metadati di `project` (`id`, `directory` e `canonical`). È disponibile sia nei plugin Promise sia nei
plugin Effect. Si tratta della posizione dell'istanza del plugin, non della posizione di ogni sessione a cui può accedere
o di ogni evento che riceve.

```ts
setup(ctx) {
  console.log(ctx.location.directory)
  console.log(ctx.location.project.canonical)
}
```

### Opzioni

Passa le opzioni del plugin usando la forma a oggetto in `opencode.json(c)`.

```jsonc title="opencode.jsonc"
{
  "plugins": [
    {
      "package": "./plugins/company",
      "options": {
        "strict": true,
      },
    },
  ],
}
```

Leggi questi valori da `ctx.options` durante `setup`.

```ts title="plugins/company/index.ts"
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "company",
  setup(ctx) {
    const strict = ctx.options.strict === true
  },
})
```

## Trasformazioni

Le trasformazioni sono modifiche sincrone allo stato di dominio di OpenCode e ciascuna si basa sulle registrazioni
precedenti nello stesso dominio. Le letture dai registri, come `ctx.model.list()`, riflettono tutte le registrazioni
effettuate fino a quel momento, anche durante il setup dei plugin; il raggruppamento all'avvio unisce solo le notifiche di
aggiornamento e non ritarda mai ciò che una lettura restituisce. Le API di stato delle risorse riportano comunque lo
stato delle risorse in esecuzione: una definizione registrata non significa che la sua connessione o altre operazioni
sulla risorsa siano state completate.

Le sorgenti forniscono provider e definizioni immutabili dei modelli tramite `ctx.provider.transform`.

```ts title="plugins/models/index.ts"
import { Model, Plugin, Provider } from "@opencode/plugin"

export default Plugin.define({
  id: "company.models",
  async setup(ctx) {
    const providerID = Provider.ID.make("acme")
    const models = [{ ...Model.Info.default(providerID, Model.ID.make("reasoner")), name: "Acme Reasoner" }]
    await ctx.provider.transform((editor) => {
      editor.add({
        info: {
          ...Provider.Info.empty(providerID),
          name: "Acme",
          activation: "enabled",
          package: "@opencode/ai/providers/openai-compatible",
          settings: { baseURL: "http://127.0.0.1:8000/v1" },
        },
        models,
      })
    })

    const available = await ctx.model.list()
  },
})
```

Qualsiasi registrazione, rimozione o chiamata a `reload()` segna il registro come modificato; la lettura successiva lo
ricostruisce riapplicando su un valore nuovo ogni trasformazione attiva, nell'ordine di registrazione. Mantieni le
trasformazioni leggere e ripetibili. Un valore che hai già letto non viene mai modificato dalle ricostruzioni successive.

Dopo aver risolto le trasformazioni dei provider e la loro disponibilità, OpenCode materializza i modelli dei provider
attivi e riapplica in ordine ogni trasformazione dei modelli. Una policy sui modelli può esaminare l'intera raccolta di
candidati, comprese le sorgenti appena aggiornate.

```ts title="plugins/model-budget/index.ts"
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "company.model-budget",
  async setup(ctx) {
    await ctx.model.transform((editor) => {
      editor
        .list()
        .filter((model) => model.cost.some((tier) => tier.output > 20))
        .forEach((model) => {
          editor.remove(model.providerID, model.id)
        })
    })
  },
})
```

Gli input catturati non vengono osservati automaticamente. Carica i dati esterni prima del callback sincrono, poi chiama
`reload()` quando quegli input cambiano. Qui `loadFromSource()` restituisce voci
`{ info: Provider.Info, models: readonly Model.Info[] }`.

```ts title="plugins/models/index.ts"
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "company.models",
  async setup(ctx) {
    const source = { providers: await loadFromSource() }

    await ctx.provider.transform((editor) => {
      source.providers.forEach((provider) => editor.add(provider))
    })

    const refresh = async () => {
      source.providers = await loadFromSource()
      await ctx.provider.reload()
    }

    const timer = setInterval(() => void refresh().catch(console.error), 60_000)
    return () => clearInterval(timer)
  },
})
```

Le modifiche ai provider invalidano l'intero risultato dei modelli attivi, quindi la policy sul prezzo di output continua
a filtrare i modelli aggiornati. Usa `ctx.model.reload()` quando cambia solo un input catturato da una trasformazione dei
modelli.

## API

### Agenti

Leggi tutti gli agenti o recuperane uno tramite ID.

```ts
const agents = await ctx.agent.list()
const build = await ctx.agent.get({ agentID: "build" })
```

Registra una trasformazione per esaminare, aggiornare o rimuovere agenti, oppure per selezionare l'agente predefinito.

```ts
await ctx.agent.transform((editor) => {
  const agents = editor.list()
  const build = editor.get("build")

  editor.default("build")
  editor.update("build", (agent) => {
    agent.description = "Builds features and fixes bugs"
  })
  editor.remove("legacy")
})
```

Ricarica gli agenti quando cambia lo stato esterno usato da una trasformazione.

```ts
await ctx.agent.reload()
```

### Provider

Leggi i provider disponibili o esamina i metadati di un provider tramite ID.

```ts
const providers = await ctx.provider.list()
const provider = await ctx.provider.get({ providerID: "anthropic" })
```

Le trasformazioni dei provider modificano le impostazioni dei provider e le definizioni di origine. Le letture
dall'editor includono i provider inattivi ed espongono definizioni immutabili; `models.update` modifica una copia di
proprietà di un modello di origine.

```ts
await ctx.provider.transform((editor) => {
  editor.update("anthropic", (provider) => {
    provider.headers = { ...provider.headers, "x-company": "engineering" }
  })
  editor.models.update("anthropic", "claude-sonnet-4-5", (model) => {
    model.name = "Team Sonnet"
  })
  editor.models.remove("anthropic", "legacy-model")
  editor.remove("legacy-provider")
})
```

Sostituisci l'inventario di origine di un provider con `models.set`, poi ricarica quando cambiano le definizioni
catturate.

```ts
const source = { models: await loadModels() }
await ctx.provider.transform((editor) => {
  editor.models.set("acme", source.models)
})

source.models = await loadModels()
await ctx.provider.reload()
```

Per il rilevamento specifico di un account, passa come `sourceConnection` la connessione usata per caricare
l'inventario. OpenCode esclude quel provider mentre è selezionata un'altra connessione, finché il plugin non pubblica
l'inventario aggiornato.

```ts
const connection = await ctx.integration.connection.active("acme")
if (!connection) return
const inventory = await loadInventory(connection)
await ctx.provider.transform((editor) => {
  editor.add({ info: inventory.provider, models: inventory.models, sourceConnection: connection })
})
```

### Modelli

Leggi i modelli disponibili e la selezione predefinita.

```ts
const models = await ctx.model.list()
const selected = await ctx.model.default()
```

Le trasformazioni dei modelli modificano l'intera raccolta di candidati dei provider attivi. I candidati disabilitati
restano modificabili finché tutte le trasformazioni non sono terminate; `update` può aggiungere un modello solo sotto un
provider disponibile.

```ts
await ctx.model.transform((editor) => {
  editor.list("anthropic").forEach((model) => {
    editor.update(model.providerID, model.id, (draft) => {
      draft.enabled = draft.capabilities.tools
    })
  })
  editor.default.set("anthropic", "claude-sonnet-4-5")
  editor.remove("anthropic", "legacy-model")
})
```

I callback modificano gli override grezzi dei modelli. I valori predefiniti del provider vengono uniti una sola volta,
quando OpenCode conferma il risultato; le letture senza modifiche riusano quel risultato. `editor.provider` espone le
definizioni di origine immutabili, compresi i template inattivi, anziché l'output delle trasformazioni dei modelli.

```ts
await ctx.model.transform((editor) => {
  const source = editor.provider.get("anthropic")?.models.get("claude-sonnet-4-5")
  if (!source) return
  editor.update("anthropic", source.id, (model) => {
    model.limit.context = Math.min(model.limit.context, source.limit.context)
  })
})

await ctx.model.reload()
```

### Integrazioni

Leggi le integrazioni ed esamina le credenziali attive.

```ts
const integrations = await ctx.integration.list()
const github = await ctx.integration.get({ integrationID: "github" })
const connection = await ctx.integration.connection.active("github")
const credential = connection ? await ctx.integration.connection.resolve(connection) : undefined
```

Collega le integrazioni con una chiave API.

```ts
await ctx.integration.connect.key({
  integrationID: "github",
  key: process.env.GITHUB_TOKEN!,
})
```

Avvia, esamina, completa o annulla un tentativo di connessione OAuth.

```ts
const attempt = await ctx.integration.oauth.connect({ integrationID: "github", methodID: "oauth" })
const status = await ctx.integration.oauth.status({ integrationID: "github", attemptID: attempt.data.attemptID })
await ctx.integration.oauth.complete({ integrationID: "github", attemptID: attempt.data.attemptID, code })
await ctx.integration.oauth.cancel({ integrationID: "github", attemptID: attempt.data.attemptID })
```

Le connessioni basate su comandi espongono lo stesso flusso di avvio, stato e annullamento.

```ts
const attempt = await ctx.integration.command.connect({ integrationID: "acme", methodID: "cli" })
const status = await ctx.integration.command.status({ integrationID: "acme", attemptID: attempt.data.attemptID })
await ctx.integration.command.cancel({ integrationID: "acme", attemptID: attempt.data.attemptID })
```

Registra una trasformazione per esaminare le integrazioni e gestirne i metodi di autenticazione.

```ts
await ctx.integration.transform((editor) => {
  const integrations = editor.list()
  const acme = editor.get("acme")

  editor.update("acme", (integration) => {
    integration.name = "Acme"
  })
  editor.method.update({
    integrationID: "acme",
    method: { id: "cli", type: "command", label: "Sign in with Acme CLI", command: ["acme", "login"] },
  })

  const methods = editor.method.list("acme")
  const legacy = methods.find((method) => method.type === "command" && method.id === "legacy")
  if (legacy) editor.method.remove("acme", legacy)
  editor.remove("legacy")
})
```

Ricarica le integrazioni quando cambia lo stato esterno usato da una trasformazione.

```ts
await ctx.integration.reload()
```

### MCP

Elenca i server MCP e il loro stato di connessione attuale.

```ts
const servers = await ctx.mcp.list()
```

I plugin gestiscono i server MCP solo tramite trasformazioni. Usa `editor.set` per aggiungere o sostituire un server,
`editor.update` per modificarne la configurazione ed `editor.remove` per rimuoverlo. Esamina la configurazione con
`editor.list` ed `editor.get`.

```ts
await ctx.mcp.transform((editor) => {
  const servers = editor.list()
  const docs = editor.get("docs")
  editor.set("docs", { type: "remote", url: "https://mcp.example.com" })
  editor.update("docs", (server) => {
    server.disabled = false
  })
  editor.remove("legacy")
})
```

Imposta `disabled: true` in una trasformazione per disabilitare un server e disconnetterlo, oppure `disabled: false` per
abilitarlo e consentire a OpenCode di connettersi. OpenCode allinea il ciclo di vita dei server alla configurazione
trasformata.

Chiama `reload()` quando cambia lo stato esterno usato da una trasformazione, per riapplicare le trasformazioni e
riallineare i server.

```ts
await ctx.mcp.reload()
```

### Permessi

Esamina o risolvi le richieste di permesso in sospeso.

```ts
const pending = await ctx.permission.list({ sessionID })
const request = await ctx.permission.get({ sessionID, requestID })
await ctx.permission.reply({ sessionID, requestID, reply: "once" })
```

Sostituisci le regole dei permessi a livello di sessione. Vengono valutate dopo le regole dell'agente e prevale l'ultima
regola corrispondente. Le sessioni figlie ereditano le regole in vigore al momento della loro creazione.

```ts
await ctx.permission.rules({
  sessionID,
  permissions: [{ action: "edit", resource: "/path/to/original/checkout/**", effect: "deny" }],
})
```

### Sessioni

Crea o leggi una sessione.

```ts
const created = await ctx.session.create({ title: "Review" })
const session = await ctx.session.get({ sessionID })
const messages = await ctx.session.context({ sessionID })
```

Cambia l'agente o il modello usato dalle richieste successive.

```ts
await ctx.session.switchAgent({ sessionID, agent: "build" })
await ctx.session.switchModel({ sessionID, model: { providerID: "anthropic", id: "claude-sonnet-4-5" } })
```

Invia prompt dell'utente, richieste di generazione temporanee, comandi o messaggi sintetici.

```ts
const prompt = await ctx.session.prompt({ sessionID, text: "Review the current changes" })
const generated = await ctx.session.generate({ sessionID, prompt: "Summarize this project" })
const command = await ctx.session.command({ sessionID, command: "review", arguments: "--staged" })
const synthetic = await ctx.session.synthetic({ sessionID, text: "Deployment completed" })
```

Rinomina una sessione, interrompila o attendine il completamento.

### Strumenti

Leggi gli strumenti attualmente registrati, dopo l'applicazione di tutte le trasformazioni, al di fuori di un callback di
trasformazione. Ogni strumento ha un `id` che contiene il suo nome effettivo.

```ts
const tools = await ctx.tool.list()
const read = tools.find((tool) => tool.id === "read")
```

Registra, aggiorna e rimuovi strumenti con una trasformazione sincrona, anche nei plugin Promise. Carica i dati esterni
prima della registrazione o del ricaricamento. Una registrazione valida successiva sovrascrive lo strumento con lo stesso
nome effettivo.

```ts
const registration = await ctx.tool.transform((editor) => {
  editor.namespace({
    name: "acme",
    description: "Customer account tools",
  })
  editor.add({
    name: "greeting",
    description: "Create a greeting",
    input: {
      type: "object",
      properties: { name: { type: "string" } },
      required: ["name"],
      additionalProperties: false,
    },
    options: { namespace: "acme", codemode: true },
    execute: async (input, context) => {
      await context.progress({ status: "greeting" })
      return { content: `Hello ${(input as { name: string }).name}!` }
    },
  })
})
```

Gli executor degli strumenti Promise ricevono `context.signal`. Passalo alle operazioni annullabili, come `fetch`, così
l'arresto della sessione interrompe anche l'operazione sottostante.

```ts
execute: async ({ url }, context) => {
  const response = await fetch(url, { signal: context.signal })
  return { content: await response.text() }
}
```

Chiama `reload()` dopo aver modificato i dati di origine catturati dal callback. Il ricaricamento riapplica le
trasformazioni attive senza cambiarne l'ordine; non riesegue il setup del plugin.

```ts
await ctx.tool.reload()
```

Usa `list()` e `get()` per esaminare gli strumenti attualmente presenti nell'editor. Gli strumenti hanno un `id` che
contiene il loro nome effettivo e `get()` restituisce `undefined` quando quell'ID non è presente. Usa `update` e `remove`
con il nome effettivo dello strumento, namespace incluso (`acme_greeting` nell'esempio sopra). I punti nei namespace e i
caratteri non supportati nei nomi degli strumenti diventano `_`. I nomi inesistenti vengono ignorati; per creare uno
strumento serve `add` con una definizione completa. Gli aggiornamenti mantengono nome e namespace. Per sostituire schemi
o opzioni assegnane di nuovi, anziché modificare i valori annidati. Gli aggiornamenti non validi vengono registrati nel
log e lasciano intatta la definizione precedente.

```ts
await ctx.tool.transform((editor) => {
  editor.update("acme_greeting", (tool) => {
    tool.description = "Greet the user by name"
  })
  editor.remove("acme_obsolete")
})
```

Aggiornamenti e rimozioni vengono riapplicati in ordine insieme alle aggiunte, anche dopo gli aggiornamenti del catalogo
MCP. Eliminando la loro registrazione, quelle modifiche vengono rimosse e il risultato viene ricostruito dalle
trasformazioni rimanenti.

Elimina (dispose) una registrazione per rimuoverne la trasformazione e ricostruire il risultato da quelle rimanenti,
facendo riemergere qualsiasi definizione precedente che aveva sovrascritto. L'eliminazione è idempotente e anche lo
scaricamento del plugin elimina le sue registrazioni.

```ts
await registration.dispose()
```

Ogni richiesta al modello cattura uno snapshot stabile ed eseguibile degli strumenti. Trasformazioni, ricaricamenti ed
eliminazioni successivi influiscono sugli snapshot futuri, non sulle definizioni, sulle descrizioni dei namespace di Code
Mode o sugli executor già catturati. Gli executor che fanno riferimento (tramite closure) a dati modificabili del plugin
continuano a vedere quei dati; cattura un valore all'interno della trasformazione quando deve restare legato a quella
definizione.

### VCS


Registra con una trasformazione un provider VCS limitato a una posizione. Un provider che corrisponde al tipo di


directory esista e non contenga un repository prima di chiamarlo, poi rileva di nuovo il progetto. I nuovi formati di
repository richiedono comunque un supporto al rilevamento che va oltre questo callback.

### Worktree

Registra una strategia per i worktree locali usando il normale ciclo di vita del plugin. In questo esempio il modulo di
implementazione gestisce la validazione delle opzioni e le operazioni `create`, `remove` e `list` del backend.

```ts title="plugins/worktrees/index.ts"
import { Plugin } from "@opencode/plugin"
import { makeStrategy } from "./strategy"

export default Plugin.define({
  id: "company.worktrees",
  async setup(ctx) {
    const strategy = makeStrategy(ctx.options)
    await ctx.worktree.transform((editor) => {
      editor.add(strategy)
    })
  },
})
```

Carica il plugin tramite `plugins` e configura separatamente la destinazione comune:

```jsonc title="opencode.jsonc"
{
  "worktree": { "directory": "../worktrees" },
  "plugins": [{ "package": "./plugins/worktrees", "options": {} }],
}
```

- Aggiungere una strategia la seleziona automaticamente. Prevale l'ultima registrazione attiva; non serve alcuna
  configurazione per scegliere la strategia.
- Eliminare la sua registrazione o scaricare il plugin ripristina l'implementazione precedente e, in ultima istanza, la
  strategia Git inclusa.
- `reload()` riapplica le trasformazioni quando cambiano gli input catturati; non riesegue il setup del plugin.
- In caso di errore durante la creazione non c'è un nuovo tentativo tramite Git. I worktree esistenti mantengono il
  proprietario registrato anche quando cambia la strategia predefinita.
- Le strategie gestiscono directory locali. Il provisioning di workspace remoti non fa parte di questa interfaccia.

#### Operazioni

Il contesto del plugin espone le stesse operazioni sui worktree basate sul progetto disponibili nel client. Ogni
operazione richiede un `projectID`. `list` legge solo l'inventario salvato, compresi i checkout noti dello stesso
progetto; non carica la configurazione, non avvia plugin e non rileva modifiche nel filesystem.

```ts
const projectID = ctx.location.project.id
const created = await ctx.worktree.create({ projectID, name: "task" })
const inventory = await ctx.worktree.list({ projectID })
await ctx.worktree.refresh({ projectID })
await ctx.worktree.remove({ projectID, directory: created.directory, force: false })
```

La creazione carica configurazione e plugin dalla directory `canonical` salvata del progetto e usa la strategia da essi
selezionata. Accetta facoltativamente una `directory` padre, una sorgente `from`, un `branch` di partenza e un `name`.
Per impostazione predefinita la sorgente è il checkout canonico, e un override di `from` deve appartenere a quel
progetto. La scelta della sorgente non cambia la radice della configurazione. Un ref di partenza, se fornito, deve essere
supportato dalla strategia selezionata; l'operazione di snapshot nativa di Rift, ad esempio, non offre un'opzione per
selezionare il ref.

La creazione e l'aggiornamento attendono l'attivazione dei plugin del checkout canonico. Le chiamate effettuate durante
il setup dei plugin di quel checkout vedono le registrazioni effettuate fino a quel momento e non attendono la propria
attivazione.

La rimozione carica la configurazione canonica e ne attiva i plugin, poi usa la strategia registrata per il worktree
anziché quella predefinita selezionata al momento. Se il proprietario registrato non è disponibile, si verifica un
errore. La destinazione del worktree può trovarsi altrove:

```ts
await ctx.worktree.remove({
  directory: "/worktrees/task",
  projectID,
  force: false,
})
```

Se il proprietario manca, la rimozione fallisce invece di ripiegare su Git. Una strategia può lanciare
`new Worktree.OperationError({ message: "Uncommitted changes", forceRequired: true })`, importando `Worktree` da
`@opencode/plugin`, per richiedere la conferma della rimozione forzata senza dipendere dagli errori di Core o di Git.

L'aggiornamento carica la configurazione canonica e chiede a tutte le strategie disponibili di trovare i worktree nelle
radici dei checkout noti. Unisce i risultati, mantiene la proprietà registrata ed elimina le directory mancanti. Se una
sorgente di rilevamento fallisce, l'errore viene registrato nel log e le altre sorgenti proseguono. Le directory
esistenti restano salvate anche se nessuna strategia disponibile le segnala. Osserva `worktree.updated` e chiama di nuovo
`list` per leggere l'inventario modificato.

```ts
await ctx.worktree.refresh({ projectID })
```

#### Riferimento API

Le implementazioni ricevono una destinazione suggerita dopo la gestione dei nomi e delle collisioni. Restituisci da
`create` la directory effettiva: può essere diversa quando un backend richiede una propria struttura. OpenCode risolve il
percorso restituito e lo usa per l'inventario, i comandi di avvio e il risultato dell'API. La directory restituita deve
esistere.

Le strategie che scelgono un'altra destinazione gestiscono lì le collisioni di nomi. OpenCode crea comunque la directory
padre suggerita prima di chiamare la strategia. `list` deve riportare solo le directory di proprietà della strategia,
più eventuali radici di repository.


I callback Promise devono rispettare l'annullamento tramite `signal`. I callback Effect restituiscono Effect e usano

il registro del checkout canonico. Gli adattatori di configurazione di Core alimentano quel registro con le impostazioni
delle directory.

## Hook

Gli hook intercettano le operazioni in corso. Registra un hook sul relativo dominio ed elimina la registrazione
restituita quando non serve più.

```ts
const registration = await ctx.session.hook("context", () => {})
await registration.dispose()
```

Più plugin possono registrare lo stesso hook. OpenCode li esegue nell'ordine dei plugin, quindi gli hook successivi
vedono le modifiche apportate da quelli precedenti.

### Sessioni

Gli hook di sessione intercettano l'ammissione dei prompt, le chiamate al modello, l'HTTP nativo e i nuovi tentativi.

#### Ammissione dei prompt

Intercetta i prompt in arrivo dall'utente prima della risoluzione di allegati e skill e prima dell'ammissione
persistente nella inbox:

```ts
await ctx.session.hook("prompt", (event) => {
  event.prompt.text = event.prompt.text.replaceAll("company-secret", "[redacted]")
  event.prompt.files ??= []
  event.prompt.files.push({ uri: "file:///project/policy.md" })
  event.metadata = { ...event.metadata, source: "company-policy" }
  event.delivery = "queue"
})
```

L'hook riceve una bozza modificabile di sua proprietà:

- `prompt` contiene `text`, `files`, le menzioni di agenti in `agents` e le `skills` selezionate.
- `metadata` contiene i metadati di ammissione definiti dall'applicazione.
- `delivery` è `"steer"` per impostazione predefinita e può essere cambiato in `"queue"`.
- Gli ID di sessione e di messaggio sono di sola lettura; un hook non può reindirizzare l'ammissione.

File e skill aggiunti da un hook seguono il normale percorso di risoluzione e validazione. Quando riscrivi il testo,
aggiorna o rimuovi gli offset `mention` degli allegati che non corrispondono più. Le menzioni di agenti non cambiano
l'agente attivo della sessione.

Gli hook dei prompt vengono eseguiti alle seguenti condizioni:

- Gli hook vengono eseguiti nell'ordine di registrazione, dopo che i plugin della posizione della sessione sono pronti.
- I comandi che inviano tramite `session.prompt` eseguono l'hook.
- Messaggi sintetici, messaggi della shell, controlli di compattazione e controlli di spostamento non lo eseguono.
- L'hook viene eseguito una sola volta durante l'ammissione, non prima di ogni chiamata al modello.
- Non è possibile limitare l'hook a un provider, perché la risoluzione del modello avviene dopo l'ammissione.

Le modifiche diventano l'input utente canonico salvato. Se la preparazione fallisce o viene interrotta, OpenCode non
ammette il prompt.

Rendi gli hook dei prompt sicuri rispetto ai nuovi tentativi. Non costituiscono un confine per effetti collaterali
eseguiti esattamente una volta:

- Ritentare con un ID già in attesa o consegnato restituisce l'ammissione originale senza rieseguire gli hook.
- Invii concorrenti possono eseguire gli hook più di una volta, ma prevale solo la prima ammissione riuscita.
- Gli hook dei prompt trasformano l'input e non espongono un'API di rifiuto tipizzata.

#### Richieste al modello

Modifica le istruzioni di sistema, i messaggi, gli strumenti o le opzioni della richiesta già assemblati, subito prima
dell'invio al modello. Ogni tipo di richiesta emessa da una sessione ha il proprio hook, così un plugin può trattare in
modo diverso il ciclo dell'agente e le richieste ausiliarie:

- `context` viene eseguito per il ciclo dell'agente, comprese le continuazioni dovute agli strumenti.
- `compaction` viene eseguito per i riepiloghi di checkpoint. `messages` è la trascrizione da riassumere; OpenCode
  aggiunge il proprio prompt di riepilogo dopo l'esecuzione degli hook. Imposta `result` per registrare tu stesso la
  compattazione e saltare la chiamata al modello; accetta gli stessi campi di un messaggio di compattazione completato.
- `generate` viene eseguito per le chiamate temporanee a `ctx.session.generate`.
- `title` viene eseguito per la generazione del titolo. Non ha `agent` né `tools`. Imposta `result` per fornire tu
  stesso il titolo.

```ts
await ctx.session.hook("context", (event) => {
  event.system.push({ type: "text", text: "Keep the review focused on correctness." })
  delete event.tools.write
  event.options.temperature = 0.2
  event.options.maxTokens = 8_000
})

await ctx.session.hook("compaction", async (event) => {
  event.result = { summary: await summarize(event.messages) }
})
```

Le modifiche riguardano solo la chiamata al modello in uscita, non la cronologia salvata né la configurazione. Un hook che
deve applicarsi a ogni richiesta va registrato per ciascun tipo.

Gli override delle richieste seguono queste regole:

- `options` parte vuoto a ogni chiamata al modello; non contiene le impostazioni del modello già risolte.
- Le chiavi tipizzate sono impostazioni di generazione; qualsiasi altra chiave viene passata al protocollo selezionato
  come opzione del provider.
- Gli hook vengono eseguiti nell'ordine di registrazione e vedono gli override applicati dagli hook precedenti.
- Gli override delle richieste hanno la precedenza sui valori predefiniti del modello, che a loro volta hanno la
  precedenza sui valori predefiniti della route.
- Gli oggetti delle opzioni del provider vengono uniti in modo ricorsivo; array e valori scalari sostituiscono i valori
  precedenti.
- Eliminare un override o impostarlo su `undefined` ripristina i valori predefiniti configurati, invece di rimuoverli.
- Le sovrapposizioni al corpo HTTP grezzo vengono applicate dopo la conversione nel protocollo e possono sovrascrivere i
  campi risultanti.

#### Opzioni del provider

Le opzioni del provider usano i nomi semantici delle opzioni del protocollo selezionato, non i campi grezzi del corpo
HTTP. Limita le impostazioni specifiche di un provider al provider corrispondente. Ad esempio, OpenAI Responses usa
`reasoningEffort`:

```ts
await ctx.session.hook(
  "context",
  (event) => {
    event.options.reasoningEffort = "high"
  },
  { providerID: "openai" },
)
```

Le opzioni di generazione dipendono dal protocollo e dal modello selezionati:

- `maxTokens` è il limite semantico dei token di output.
- Gemini supporta `topK`; OpenAI Responses non lo espone.

#### Richiesta al modello

Modifica le impostazioni della richiesta al modello e, facoltativamente, limita l'hook a un provider. L'evento contiene lo
stesso `kind` degli hook HTTP descritti più avanti.

```ts
await ctx.session.hook(
  "model.request",
  (event) => {
    event.headers["x-plugin"] = "review"
  },
  { providerID: "anthropic" },
)
```

#### HTTP nativo

Modifica le richieste o le risposte native del provider. I loro corpi sono stream leggibili una sola volta: clona o
sostituisci un corpo prima di leggerlo.

Entrambi gli hook vengono eseguiti per ogni richiesta emessa da una sessione. `event.kind` indica il flusso che l'ha
emessa: `"primary"` per il ciclo dell'agente, `"compaction"` per i riepiloghi di checkpoint, `"title"` per la
generazione del titolo e `"generate"` per le chiamate temporanee a `ctx.session.generate`. Usalo al posto dell'ID
dell'agente per distinguere le richieste ausiliarie.

```ts
await ctx.session.hook("http.request", (event) => {
  event.request.headers.set("x-session-id", event.sessionID)
  if (event.kind === "title") event.request.headers.set("x-priority", "background")
})

await ctx.session.hook("http.response", (event) => {
  event.response = new Response(event.response.body, {
    status: event.response.status,
    headers: { ...Object.fromEntries(event.response.headers), "x-plugin": "review" },
  })
})
```

#### WebSocket nativo (sperimentale)

I provider che trasmettono in streaming su WebSocket aprono una connessione per sessione e la riusano tra le richieste,
quindi `http.request` e `http.response` non vedono mai quel traffico. L'hook `experimental.ws.handshake` viene eseguito
una volta per ogni chiamata al modello, prima che venga selezionata la connessione. Contiene gli stessi `sessionID`,
`agent`, `model` e `kind` degli hook HTTP, più `url` e `headers` della connessione. Modificare `url` o `headers` cambia il
socket usato dalla richiesta, quindi un bearer token ruotato riapre la connessione.

Gli hook HTTP vengono comunque eseguiti per ogni richiesta HTTP, compresa quella su cui ripiega una route WebSocket.

```ts
await ctx.session.hook(
  "experimental.ws.handshake",
  async (event) => {
    event.headers.authorization = `Bearer ${await mintToken(event.url)}`
    delete event.headers["api-key"]
  },
  { providerID: "azure" },
)
```

`experimental.ws.send` ed `experimental.ws.receive` espongono i frame stessi: sono l'equivalente WebSocket della modifica
del corpo di una richiesta o risposta HTTP. `send` viene eseguito dopo che il driver del provider ha costruito un frame in
uscita e prima che venga scritto; `receive` viene eseguito su ogni frame in entrata prima che il driver lo veda. Entrambi
contengono il frame come stringa e inviano il contenuto di `frame` al ritorno dell'hook.

OpenCode non valida i frame riscritti. Il driver tiene traccia dello stato in base alle risposte del provider, quindi una
riscrittura che cambia il significato del protocollo è responsabilità del plugin, esattamente come un corpo HTTP
riscritto.

```ts
await ctx.session.hook(
  "experimental.ws.send",
  (event) => {
    const body = JSON.parse(event.frame)
    if (body.type === "response.create") body.metadata = { ...body.metadata, session: event.sessionID }
    event.frame = JSON.stringify(body)
  },
  { providerID: "openai" },
)

await ctx.session.hook("experimental.ws.receive", (event) => {
  if (event.frame.includes('"type":"error"')) console.error(event.frame)
})
```

Questi hook sono sperimentali e i loro nomi o la loro struttura potrebbero cambiare.

#### Policy dei nuovi tentativi

Sovrascrivi la decisione di ritentare dopo un errore del provider o sostituiscine il ritardo in millisecondi. L'hook
viene eseguito dopo che OpenCode ha classificato l'errore e proposto la propria policy, ma prima che venga pianificato un
nuovo tentativo. Non espone il modo in cui OpenCode esegue internamente il tentativo successivo.

```ts
await ctx.session.hook("retry", (event) => {
  if (event.error.status === 429) {
    event.decision = { retry: true, delay: 10_000 }
    return
  }
  if (event.error.type === "provider.invalid-request" && event.attempt === 2) {
    event.decision = { retry: true, delay: 0 }
    return
  }
  if (event.attempt >= 3) event.decision = { retry: false }
})
```

Gli hook dei nuovi tentativi possono cambiare la `decision` iniziale di OpenCode, rendendo ritentabile un errore
definitivo o bloccando un nuovo tentativo proposto.

Le decisioni sui nuovi tentativi seguono queste regole:

- Più hook vengono eseguiti nell'ordine di registrazione e quelli successivi vedono la decisione corrente.
- Il numero massimo di tentativi integrato resta un limite invalicabile.
- `attempt` è il tentativo fisico in esame. La richiesta iniziale è `1`, quindi il primo nuovo tentativo è `2`.
- I ritardi non validi, come `NaN`, infinito o valori negativi, ripiegano sul ritardo calcolato.
- Il recupero dal superamento del contesto è separato, perché compatta la conversazione anziché ritentare la stessa
  richiesta.

#### Riferimento API delle sessioni

```ts
import type { SessionPrompt } from "@opencode/plugin/promise/session"

interface SessionHooks {
  prompt: SessionPrompt
  context: SessionContextHook
  compaction: SessionContextHook & { result?: SessionCompactionResult }
  generate: SessionContextHook

interface SessionWebSocketReceiveHook {
  readonly sessionID: string
  readonly agent: string
  readonly model: { providerID: string; id: string; variant?: string }

}

interface SessionRetryHook {
```

### Permessi

Esamina le decisioni sui permessi dopo la valutazione delle regole configurate e prima che un'azione venga eseguita o
che venga pubblicata una richiesta di permesso.

```ts
await ctx.permission.hook("evaluate", async (event) => {
  if (event.action === "read") return

  const messages = await ctx.session.context({ sessionID: event.sessionID })
  const review = await ctx.generate.text({
    model: { providerID: "anthropic", id: "claude-sonnet-4-6" },
    prompt: buildSafetyPrompt({ messages, action: event.action, resources: event.resources }),
  })
  const decision = parseDecision(review.text)

  event.effect = decision.effect
  event.message = decision.reason
})
```

Gli hook dei permessi seguono queste regole:

- Gli hook vengono eseguiti per le decisioni `allow` e `ask`.
- Un `deny` configurato esplicitamente è definitivo e non invoca l'hook.
- Un hook può cambiare `effect` in `allow`, `ask` o `deny`.
- `message` compare in una richiesta di permesso inoltrata all'utente oppure diventa il motivo del rifiuto.

#### Riferimento API

```ts
interface PermissionEvaluation {
  readonly sessionID: string
  readonly agent?: string
  readonly action: string
  readonly resources: readonly string[]
  readonly metadata?: Record<string, unknown>
  readonly source?: { type: "tool"; messageID: string; id: string }
  effect: "allow" | "ask" | "deny"
  message?: string
}
```

### Strumenti

Esamina o sostituisci l'input di uno strumento prima dell'esecuzione.

```ts
await ctx.tool.hook("execute.before", (event) => {

```

Esamina i risultati riusciti o gli errori dopo l'esecuzione.

```ts
await ctx.tool.hook("execute.after", (event) => {
  if (event.status === "completed") event.result = { ...event.result, metadata: { observed: true } }
  if (event.status === "error") console.error(event.error.message)
})
```

## Pubblicazione

Un plugin distribuito come pacchetto usa lo stesso export default di un plugin locale. Un manifest minimo è:

```json title="package.json"
{
  "name": "opencode-acme-plugin",
  "version": "1.0.0",
  "type": "module",
  "exports": {
    ".": "./src/index.ts",
    "./rpc": "./src/rpc.ts"
  },
  "dependencies": {
    "@opencode/plugin": "latest"
  }
}
```

L'export `./rpc` è facoltativo; includilo quando pubblichi un [contratto RPC](/build/plugins/rpc) condiviso che altri
plugin e client possono importare senza caricare la tua implementazione.

Usa versioni compatibili con la release di OpenCode a cui ti rivolgi e testa il pacchetto installato, non solo una copia
collegata nel workspace. Pubblica un aggiornamento compatibile del plugin quando adotti un contratto API più recente.

## Supporto per V1

Un plugin può supportare V1 e V2 dallo stesso punto di ingresso del pacchetto. Esporta come default un unico oggetto con
una funzione `server()` per V1 e una funzione `setup()` per V2:

```ts title="src/index.ts"
import { Plugin } from "@opencode/plugin"

export default {
  ...Plugin.define({
    id: "example",
    async setup(ctx) {
      await ctx.tool.hook("execute.before", () => {
        console.log("A tool is about to run")
      })
    },
  }),
  async server() {
    return {
      "tool.execute.before": async () => {
        console.log("A tool is about to run")
      },
    }
  },
}
```

- V1 chiama `server()` e usa gli hook restituiti.
- V2 legge `id` e `setup()` dall'export default (oppure `effect()` per i plugin Effect), ignorando `server()`.
- Mantieni ciascuna implementazione sulla propria API: condividere un export non converte gli hook V1 in hook V2.
- Espandi `Plugin.define(...)` nell'oggetto esportato, così la definizione V2 viene verificata dal type checker
  separatamente da `server()`.

La forma a oggetto per V1 è supportata in OpenCode `1.18.29`. Le release V1 precedenti potrebbero invece aspettarsi export
di funzioni; testa il pacchetto installato con la release V1 più vecchia che intendi supportare e con V2.
