---
title: "Skill"
---

Crea una skill per fornire a un agente istruzioni riutilizzabili per un compito specifico. Inserisci un file `SKILL.md` in `.opencode/skills/<skill-id>` e indica in `description` quando usarla.

```markdown title=".opencode/skills/git-release/SKILL.md"
---
name: Git Release
description: Prepare release notes, version bumps, and GitHub releases
---

## Workflow

1. Read `references/release-policy.md`.
2. Summarize merged changes since the previous tag.
3. Propose the version bump before changing files.
4. Run `scripts/changelog.ts` only after the user approves the version.
```

OpenCode segnala questa skill al modello quando è pertinente. L'agente può quindi caricarne le istruzioni con lo strumento `skill`, invece di aggiungere ogni skill a ogni prompt.

## Creazione

Tieni script, riferimenti e modelli correlati accanto a `SKILL.md`:

```text
.opencode/skills/
└── git-release/
    ├── SKILL.md
    ├── scripts/
    │   └── changelog.ts
    └── references/
        └── release-policy.md
```

I percorsi scritti all'interno della skill sono relativi alla directory che contiene `SKILL.md`. La forma a directory è consigliata perché offre ai file di supporto una directory di base riservata.

## Rilevamento

OpenCode cerca automaticamente in queste posizioni:

| Ambito                        | Origini                                |
| ----------------------------- | -------------------------------------- |
| Globale                       | `~/.config/opencode/skills`            |
| Globale (compatibilità)       | `~/.claude/skills`, `~/.agents/skills` |
| Progetto                      | `.opencode/skills`                     |
| Progetto (compatibilità)      | `.claude/skills`, `.agents/skills`     |

Per le origini di progetto, OpenCode cerca dalla directory corrente fino alla radice del progetto e include le directory corrispondenti a ogni livello.

Ogni origine può contenere entrambe le forme:

```text
skills/
├── review.md
└── git-release/
    └── SKILL.md
```

- I file Markdown devono trovarsi nella radice dell'origine, ad esempio `skills/review.md`.
- I file che si chiamano esattamente `SKILL.md` possono trovarsi a qualsiasi profondità, ad esempio `skills/git-release/SKILL.md`.

## Origini

Aggiungi altre directory locali o cataloghi HTTP con l'array `skills` in qualsiasi `opencode.json` o `opencode.jsonc`:

```jsonc title="opencode.jsonc"
{
  "$schema": "https://opencode.ai/config.json",
  "skills": [
    "./team-skills",
    "~/shared/opencode-skills",
    "/opt/company-skills",
    "https://example.com/opencode/skills/",
  ],
}
```

| Valore | Risoluzione |
| ----- | ---------- |
| Percorso relativo | Rispetto alla directory di lavoro attiva di OpenCode, non al file di configurazione |
| Percorso `~/` | Rispetto alla home directory dell'utente corrente |
| Percorso assoluto | Usato così com'è |
| URL `http://` o `https://` | Caricato come catalogo HTTP |

Ogni file di configurazione trovato contribuisce con le proprie voci. Gli array `skills` vengono combinati, non sostituiti.

## Cataloghi

Un catalogo HTTP è un URL di base con un file `index.json`:

```json title="index.json"
{
  "skills": [
    {
      "name": "git-release",
      "version": "3",
      "files": ["git-release.md", "references/release-policy.md"]
    }
  ]
}
```

Per questa voce, OpenCode scarica ogni file da `<base-url>/git-release/<file>`.

| Regola | Requisito |
| ---- | ----------- |
| Percorsi | Devono essere sicuri, relativi e della stessa origine |
| File principale | Includi `SKILL.md` o `<name>.md`, ad esempio `git-release.md` |
| Aggiornamenti | Incrementa `version` quando i file cambiano, così OpenCode aggiorna la cache |

In un catalogo HTTP preferisci la forma Markdown con nome. Ogni directory di skill scaricata diventa una radice di origine, quindi `git-release.md` ha l'ID `git-release`. Al momento, in V2 un `SKILL.md` al livello radice ha letteralmente l'ID `SKILL`.

## Frontmatter

Usa il frontmatter per assegnare un nome alla skill e controllare dove compare:

```markdown title="SKILL.md"
---
name: Git Release
description: Prepare a repository release
metadata:
  opencode/autoinvoke: false
---

Prepare the changelog, version bump, tag, and release notes.
```

| Campo                          | Comportamento                                                                     |
| ------------------------------ | --------------------------------------------------------------------------------- |
| `name`                         | Nome visualizzato; per impostazione predefinita è l'ID derivato dal percorso      |
| `description`                  | Riepilogo usato per presentare la skill al modello                                |
| `metadata.opencode/autoinvoke` | Impostalo su `false` per escludere la skill dall'elenco disponibile al modello    |
| `disable-model-invocation`     | Impostalo su `true` per ottenere lo stesso effetto di `opencode/autoinvoke: false` |

A runtime tutto il frontmatter è facoltativo. Aggiungi una `description` chiara se il modello deve poter trovare la skill: le skill senza descrizione non vengono segnalate.

`opencode/autoinvoke: false` nasconde la skill solo dall'elenco disponibile al modello. La skill resta registrata e può comunque essere caricata esplicitamente tramite ID. Se sono impostati sia `disable-model-invocation` sia `opencode/autoinvoke`, prevale `opencode/autoinvoke`. V2 accetta campi di portabilità come `license` e `compatibility`, ma non li interpreta.

## ID

Il percorso del file determina l'ID della skill. Il campo `name` del frontmatter è solo un'etichetta visualizzata.

| File                              | ID            |
| --------------------------------- | ------------- |
| `<source>/git-release.md`         | `git-release` |
| `<source>/git-release/SKILL.md`   | `git-release` |
| `<source>/teams/release/SKILL.md` | `release`     |

Gli ID sono esatti e distinguono tra maiuscole e minuscole. Per le skill portabili, usa un ID univoco in kebab-case minuscolo di 1–64 caratteri e mantienilo allineato al nome della directory:

```text
^[a-z0-9]+(-[a-z0-9]+)*$
```

Al momento V2 non impone questo schema, la lunghezza consigliata di 1–64 caratteri, la corrispondenza tra `name` e la directory né una lunghezza massima della descrizione.

## Precedenza

Le skill vengono selezionate per ID. Se due origini definiscono `git-release`, la skill caricata da OpenCode è quella dell'origine registrata per ultima:

```text
~/.config/opencode/skills/git-release/SKILL.md  ← lower precedence
.opencode/skills/git-release/SKILL.md           ← loaded
```

Le origini vengono registrate dalla precedenza più bassa alla più alta:

1. Skill integrate
2. `.claude/skills`, prima quella globale e poi dall'antenato più lontano verso la directory corrente
3. `.agents/skills`, prima quella globale e poi dall'antenato più lontano verso la directory corrente
4. `~/.config/opencode/skills`
5. `.opencode/skills` di progetto, dalla radice del progetto verso la directory corrente
6. Voci esplicite `skills` della configurazione, secondo la priorità della configurazione e l'ordine nell'array

Evita ID duplicati, a meno che tu non voglia sovrascrivere una skill precedente.

## Caricamento

A ogni passaggio del modello, OpenCode elenca le skill consentite che hanno una descrizione e non impostano `opencode/autoinvoke` su `false`. L'elenco include solo ID, nome e descrizione, non l'intero corpo Markdown.

Il modello carica una skill chiamando lo strumento `skill` con il suo ID esatto:

```json title="skill tool input"
{
  "id": "git-release"
}
```

OpenCode quindi:

1. Seleziona la definizione corrente per quell'ID.
2. Verifica il permesso `skill` dell'agente selezionato.
3. Aggiunge alla conversazione il corpo Markdown, senza frontmatter.
4. Fornisce la directory di base della skill e un campione di massimo dieci percorsi di file di supporto.

Per caricare tu stesso una skill, menzionala nel prompt come `@skill-id`.

Il contenuto dei file di supporto non viene caricato automaticamente: l'agente lo legge quando la skill gli indica di farlo. Il campione di file è disponibile per le skill `SKILL.md` basate su directory; le skill Markdown semplici non ricevono l'elenco dei file vicini.

## Permessi

Usa l'azione `skill` e l'ID della skill come risorsa. Le regole vengono valutate in ordine e prevale l'ultima regola corrispondente:

```jsonc title="opencode.jsonc"
{
  "permissions": [
    { "action": "skill", "resource": "*", "effect": "allow" },
    { "action": "skill", "resource": "internal-*", "effect": "deny" },
    { "action": "skill", "resource": "experimental-*", "effect": "ask" },
  ],
}
```

| Effetto | Comportamento |
| ------ | -------- |
| `allow` | Segnala e carica le skill corrispondenti senza approvazione |
| `ask` | Segnala le skill corrispondenti e chiede conferma prima di caricarle |
| `deny` | Nasconde le skill corrispondenti al modello e ne rifiuta il caricamento |

Inserisci le stesse regole in `agents.<id>.permissions` per applicarle a un solo agente.

## Risoluzione dei problemi

Ad esempio, l'ID di questa skill è `release`, non il nome `Git Release` indicato nel frontmatter:

```text
.opencode/skills/release/SKILL.md
                      └─ ID: release
```

Se una skill manca o carica il contenuto sbagliato:

1. Verifica che il file sia un `*.md` al livello radice oppure un file annidato che si chiama esattamente `SKILL.md`.
2. Controlla l'ID derivato dal percorso, che distingue tra maiuscole e minuscole, e non il `name` del frontmatter.
3. Aggiungi una `description` se il modello deve poter trovare la skill.
4. Controlla `opencode/autoinvoke` e i permessi `skill` dell'agente selezionato.
5. Cerca un'origine successiva che definisca lo stesso ID.
6. Per i cataloghi HTTP, verifica `index.json`, che i percorsi dei file siano della stessa origine e che `version` sia stata modificata.
