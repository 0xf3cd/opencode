title: "ย้ายจาก V1"
---

OpenCode 1 และ OpenCode 2 ใช้คำสั่ง `opencode` เหมือนกัน และโดยค่าเริ่มต้นจะไม่ติดตั้งคู่กันอีกต่อไป ให้ถอนการติดตั้ง V1 ที่ติดตั้งผ่านตัวจัดการแพ็กเกจก่อนติดตั้ง V2 ส่วนตัวติดตั้ง V2 แบบ curl จะแทนที่ไบนารีของ V1 ให้เอง

## การเปลี่ยนแปลงที่ไม่เข้ากันกับเวอร์ชันเดิม

V2 มีการเปลี่ยนแปลงที่ไม่เข้ากันกับเวอร์ชันเดิม (breaking change) โดยตั้งใจ 3 ข้อ:

- [ปลั๊กอิน](/build/plugins/migrate-v1)ใช้ API ปลั๊กอินแบบใหม่
- [API ของเซิร์ฟเวอร์และไคลเอนต์](#server-api-and-clients)มีสัญญา (contract) ใหม่
- [การกำหนดค่าไคลเอนต์เทอร์มินัล](/cli/config)ย้ายจากไฟล์ `tui.json(c)` ที่ซ้อนกันหลายชั้นไปเป็นไฟล์ `cli.json` ส่วนกลางไฟล์เดียว (ย้ายให้อัตโนมัติ)

ฟังก์ชันของ V1 ที่รองรับนอกเหนือจากส่วนเหล่านี้ตั้งใจให้ยังคงเข้ากันได้กับ V1 ฟิลด์บางตัวที่ schema ของ V1 ยอมรับไม่เคยมีสิ่งที่เทียบเท่าใน V2 และจะถูกละเว้นโดยตั้งใจ ดูรายการได้ที่[ฟิลด์ที่ยอมรับแต่ไม่รองรับ](#accepted-but-unsupported-fields)

ฟิลด์การกำหนดค่าเซิร์ฟเวอร์ที่รองรับอยู่แล้ว นิยามเอเจนต์ นิยามคำสั่ง สกิล และไฟล์อื่น ๆ ใน `.opencode/` ควรทำงานต่อได้โดยไม่ต้องแก้ไข หากพฤติกรรมที่รองรับตามที่อธิบายในคู่มือนี้ใช้งานไม่ได้ใน V2 ให้ถือว่าเป็นบั๊กด้านความเข้ากันได้ ไม่ใช่สิ่งที่ต้องแก้ไขเองตามปกติของการย้าย

<Callout type="tip">
  หากฟังก์ชันของ V1 ที่รองรับใช้งานไม่ได้ใน V2 ให้ทำตามแนวทางการรายงานปัญหาใน[การแก้ไขปัญหา](/troubleshooting) และแจ้งปัญหาด้านความเข้ากันได้
</Callout>

## ติดตั้ง V2

ติดตั้งไคลเอนต์เทอร์มินัลของ V2 ตาม[คู่มือเริ่มต้นใช้งานเทอร์มินัล](/cli)

คุณไม่จำเป็นต้องเขียนทุกอย่างใหม่ก่อนเริ่มใช้ V2 ขั้นตอนการย้ายที่ใช้ได้จริงมีดังนี้:

1. เก็บการกำหนดค่าและนิยามแบบไฟล์ที่มีอยู่ไว้ตามเดิม
2. เริ่ม V2 แล้วตรวจสอบโมเดล ข้อมูลรับรอง เอเจนต์ สิทธิ์ และเซิร์ฟเวอร์ MCP
3. พอร์ตปลั๊กอิน เพราะโค้ดปลั๊กอินของ V1 ไม่ทำงานใน V2
4. พอร์ตอินทิเกรชันที่เรียก API ของเซิร์ฟเวอร์
5. แปลงการกำหนดค่าเป็นรูปแบบเนทีฟของ V2 เมื่อพร้อม ขั้นตอนนี้ไม่บังคับ

เก็บสำเนาการตั้งค่า V1 ไว้ระหว่างตรวจสอบการย้าย V1 และ V2 ใช้ตำแหน่งการกำหนดค่าเดียวกัน จึงไม่ควรให้ V1 ใช้ไฟล์ที่แปลงเป็นรูปแบบเนทีฟที่ใช้ได้เฉพาะ V2 แล้ว

## การกำหนดค่า

ส่วนนี้ครอบคลุมทั้งการกำหนดค่าแบบ JSON/JSONC และนิยามแบบไฟล์ภายใต้ `.opencode/`

### ใช้การกำหนดค่าที่มีอยู่

V2 อ่านการกำหนดค่าระดับระบบ ส่วนกลาง และโปรเจกต์ที่มีอยู่จากตำแหน่งเดียวกับ V1:

```text
/Library/Application Support/opencode/opencode.json(c)
/etc/opencode/opencode.json(c)
%ProgramData%\opencode\opencode.json(c)
/Library/Managed Preferences/<user>/ai.opencode.managed.plist
/Library/Managed Preferences/ai.opencode.managed.plist
~/.config/opencode/opencode.json(c)
<project>/opencode.json(c)
<project>/.opencode/opencode.json(c)
```

V2 อ่านจากตำแหน่งเหล่านี้ และปรับฟิลด์ของ V1 ที่รองรับและฟิลด์เนทีฟของ V2 ให้เป็นรูปแบบเดียวกันในหน่วยความจำ โดยไม่เขียนทับไฟล์ต้นฉบับ การกำหนดค่า V1 ที่รองรับตั้งใจให้ใช้งานต่อได้ คุณจึงไม่ต้องแปลงการกำหนดค่าเพื่อทดลองหรือเริ่มใช้ V2

เช่นเดียวกับ V1 การกำหนดค่าระดับระบบและ managed preferences บน macOS มีลำดับความสำคัญสูงสุด การตั้งค่าเหล่านี้จึงแทนที่ไฟล์ส่วนกลางและไฟล์โปรเจกต์ [นโยบาย](/policies#precedence)ของการกำหนดค่าเหล่านี้ รวมถึง `enabled_providers` และ `disabled_providers` ที่ย้ายมา ก็มีลำดับสูงกว่านโยบายส่วนกลางและนโยบายโปรเจกต์ด้วย การแทนที่การตั้งค่าไม่สามารถห้ามผู้ใช้เพิ่มผู้ให้บริการ เซิร์ฟเวอร์ MCP เอเจนต์ หรือปลั๊กอินได้ ดังนั้นให้กำหนดข้อจำกัดที่ผู้ดูแลระบบบังคับใช้เป็น `policies` แทนการตั้งค่าทั่วไปอย่าง `permissions`

### ให้ OpenCode ย้ายให้

รูปแบบการกำหนดค่าของ V1 ยังคงรองรับ รูปแบบเนทีฟของ V2 เป็นทางเลือก ซึ่งทำให้การตั้งค่าหลายอย่างชัดเจนและใช้งานสะดวกขึ้น

วิธีย้ายที่แนะนำคือให้ OpenCode อัปเดตการกำหนดค่าให้:

```text
Migrate my OpenCode configuration, including file-based definitions, from the V1 format to the native V2 format.
Preserve its behavior and all unrelated settings.
```

OpenCode ตรวจดูไฟล์ทั้งหมด ปรับใช้การเปลี่ยนแปลงที่เกี่ยวข้องด้านล่าง และหลีกเลี่ยงการเขียนใหม่ในส่วนที่ไม่ต้องเปลี่ยนได้ การแปลงไม่จำเป็นต้องทำทีเดียวทั้งหมด เพราะฟิลด์ของ V1 ที่รองรับและฟิลด์เนทีฟของ V2 อยู่ร่วมกันที่ระดับบนสุดได้ เมื่อทั้งสองรูปแบบตั้งค่าเดียวกัน ค่าเนทีฟของ V2 ที่ถูกต้องจะมีลำดับความสำคัญสูงกว่าเสมอ ไม่ว่าคีย์ใน JSON จะเรียงอย่างไร

การผสมรูปแบบในระดับซ้อนมีขอบเขตจำกัดโดยตั้งใจ OpenCode รู้จักสมาชิกแบบ V1 และ V2 ที่ผสมกันภายใน `mcp`, `compaction` และ `experimental` แต่จะไม่อนุมานรูปแบบแบบเรียกซ้ำภายในเอเจนต์ ผู้ให้บริการ คำสั่ง หรือโมเดลแต่ละรายการ ให้เขียนรายการซ้อนเหล่านี้แต่ละรายการด้วยรูปแบบเดียวทั้งหมด ไวยากรณ์ V1 ที่รองรับจะไม่แสดงคำเตือนใด ๆ ส่วนค่าที่ผิดรูปแบบ ฟิลด์เดิมที่ไม่รองรับ และค่า V1/V2 ที่ขัดแย้งกันจะแสดงคำเตือน ขณะที่การตั้งค่าอื่นที่ถูกต้องยังโหลดต่อได้ตามปกติ

### การแชร์

บูลีน `autoshare` ของ V1 ที่เลิกใช้แล้วจะกลายเป็นนโยบาย `share` แบบระบุชัดเจน:

```jsonc
// V1
{ "autoshare": true }

// V2
{ "share": "auto" }
```

ใช้ `"manual"`, `"auto"` หรือ `"disabled"` หากไฟล์ V1 ใช้ `share` อยู่แล้ว ก็ไม่ต้องเปลี่ยนอะไร

### สิทธิ์และเครื่องมือ

V1 จัดกลุ่มผลของสิทธิ์ตามเครื่องมือ ส่วน V2 ใช้อาร์เรย์ `permissions` แบบเรียงลำดับเพียงอาร์เรย์เดียว ทำให้ลำดับความสำคัญและข้อยกเว้นชัดเจน:

```jsonc
// V1
{
  "permission": {
    "bash": {
      "git push *": "ask"
    },
    "edit": "allow"
  },
  "tools": {
    "websearch": false
  }
}

// V2
{
  "permissions": [
    { "action": "shell", "resource": "git push *", "effect": "ask" },
    { "action": "edit", "resource": "*", "effect": "allow" },
    { "action": "websearch", "resource": "*", "effect": "deny" }
  ]
}
```

action ของสิทธิ์ก็เปลี่ยนด้วย: `bash` เปลี่ยนเป็น `shell` `task` เปลี่ยนเป็น `subagent` และ `write` กับ `patch` เปลี่ยนเป็น `edit` ดูรูปแบบกฎแบบเรียงลำดับของ V2 ได้ที่[สิทธิ์](/permissions)

### เอเจนต์และโหมด

แมป `agent` แบบเอกพจน์และแมป `mode` ที่เลิกใช้แล้วจะกลายเป็น `agents` ฟิลด์ของเอเจนต์สอดคล้องกับส่วนอื่นของการกำหนดค่า V2 มากขึ้น:

```jsonc
// V1
{
  "agent": {
    "reviewer": {
      "prompt": "Review for correctness and missing tests.",
      "model": "anthropic/claude-sonnet-4-5",
      "variant": "high",
      "disable": false,
      "permission": {
        "edit": "deny"
      }
    }
  }
}

// V2
{
  "agents": {
    "reviewer": {
      "system": "Review for correctness and missing tests.",
      "model": "anthropic/claude-sonnet-4-5#high",
      "disabled": false,
      "permissions": [
        { "action": "edit", "resource": "*", "effect": "deny" }
      ]
    }
  }
}
```

`prompt` เปลี่ยนเป็น `system` `disable` เปลี่ยนเป็น `disabled` และ `variant` ที่แยกไว้จะต่อท้ายการอ้างอิงโมเดลหลัง `#` ส่วน `temperature`, `top_p` และ `options` เฉพาะผู้ให้บริการย้ายไปอยู่ใต้ `request.body` `maxSteps` เปลี่ยนเป็น `steps` และรายการจากแมป `mode` เดิมจะกลายเป็นเอเจนต์หลัก

### สแนปช็อต

เปลี่ยนชื่อฟิลด์ `snapshot` แบบเอกพจน์เป็น `snapshots` ค่าบูลีนไม่เปลี่ยน:

```jsonc
// V1
{ "snapshot": false }

// V2
{ "snapshots": false }
```

### สื่อ

เปลี่ยนชื่อออบเจกต์ `attachment` แบบเอกพจน์เป็น `media` การตั้งค่ารูปภาพที่ซ้อนอยู่ใช้ชื่อเดิม:

```jsonc
// V1
{ "attachment": { "image": { "auto_resize": true } } }

// V2
{ "media": { "image": { "auto_resize": true } } }
```

### เซิร์ฟเวอร์ MCP

V2 จัดกลุ่มเซิร์ฟเวอร์ไว้ใต้ `mcp.servers` แทนที่ `enabled` ด้วย `disabled` ที่มีความหมายกลับกัน และแยกค่าหมดเวลาตามวัตถุประสงค์:

```jsonc
// V1
{
  "mcp": {
    "playwright": {
      "type": "local",
      "command": ["npx", "@playwright/mcp"],
      "enabled": true,
      "timeout": 30000
    }
  }
}

// V2
{
  "mcp": {
    "servers": {
      "playwright": {
        "type": "local",
        "command": ["npx", "@playwright/mcp"],
        "disabled": false,
        "timeout": {
          "catalog": 30000,
          "execution": 30000
        }
      }
    }
  }
}
```

ฟิลด์ OAuth ของเซิร์ฟเวอร์ระยะไกลใช้ snake case: `clientId` เปลี่ยนเป็น `client_id` `clientSecret` เปลี่ยนเป็น `client_secret` `callbackPort` เปลี่ยนเป็น `callback_port` และ `redirectUri` เปลี่ยนเป็น `redirect_uri` ค่า `experimental.mcp_timeout` ของ V1 ก็จะกลายเป็นค่าเริ่มต้นของ `mcp.timeout.catalog` และ `mcp.timeout.execution` ด้วย ดู[เซิร์ฟเวอร์ MCP](/mcp-servers)

### การบีบอัดบริบท

V2 จัดกลุ่มงบประมาณโทเค็นของบริบทที่คงไว้ไว้ใต้ `keep` และตั้งชื่อส่วนสำรองให้ชัดเจนขึ้น:

```jsonc
// V1
{
  "compaction": {
    "preserve_recent_tokens": 8000,
    "reserved": 20000
  }
}

// V2
{
  "compaction": {
    "keep": {
      "tokens": 8000
    },
    "buffer": 20000
  }
}
```

`auto` ใช้ชื่อเดิม V2 ไม่มีฟิลด์ `tail_turns` หรือ `prune` แบบเนทีฟ ฟิลด์เดิมทั้งสองจะถูกละเว้นพร้อมคำเตือน บริบทล่าสุดจะคงไว้ตามงบประมาณโทเค็นแทน ดู[การบีบอัดบริบท](/compaction)

### สกิล

V1 แยกพาธและ URL ของสกิลเพิ่มเติมออกจากกัน ส่วน V2 รวมทั้งสองไว้ในอาร์เรย์แบบเรียงลำดับเพียงอาร์เรย์เดียว:

```jsonc
// V1
{
  "skills": {
    "paths": ["./team-skills"],
    "urls": ["https://example.com/skills/"]
  }
}

// V2
{
  "skills": ["./team-skills", "https://example.com/skills/"]
}
```

ไฟล์สกิลที่มีอยู่และการค้นพบอัตโนมัติใน `.opencode/skills/` ไม่เปลี่ยนแปลง ดู[สกิล](/skills)

### คำสั่ง

เปลี่ยนชื่อแมป `command` แบบเอกพจน์เป็น `commands` และ `subtask` เป็น `subagent` แล้วนำ `variant` ของโมเดลที่แยกไว้ไปต่อกับการอ้างอิงโมเดล:

```jsonc
// V1
{
  "command": {
    "review": {
      "template": "Review the current changes.",
      "model": "anthropic/claude-sonnet-4-5",
      "variant": "high",
      "subtask": true
    }
  }
}

// V2
{
  "commands": {
    "review": {
      "template": "Review the current changes.",
      "model": "anthropic/claude-sonnet-4-5#high",
      "subagent": true
    }
  }
}
```

`template`, `description` และ `agent` ใช้ชื่อเดิม `subtask` แบบเดิมยังคงยอมรับ คำสั่งที่มอบหมายงานต่อจะรันในเบื้องหลังโดยอัตโนมัติและรายงานผลกลับไปยังเซสชันหลัก นิยามคำสั่งแบบ Markdown ที่มีอยู่ยังคงรองรับ ดู[คำสั่ง](/commands)

### ไดเรกทอรีอ้างอิง

เปลี่ยนชื่อแมป `reference` แบบเอกพจน์ที่เลิกใช้แล้วเป็น `references`:

```jsonc
// V1
{ "reference": { "docs": "../docs" } }

// V2
{ "references": { "docs": "../docs" } }
```

V1 ยอมรับ `references` อยู่แล้ว หากไฟล์ใช้ชื่อนี้อยู่ก็ไม่ต้องเปลี่ยน รายการไดเรกทอรีอ้างอิงยังใช้โครงสร้างเดิม ดู[ไดเรกทอรีอ้างอิง](/references)

### ผู้ให้บริการ

เปลี่ยนชื่อแมป `provider` แบบเอกพจน์เป็น `providers` V2 แยกแพ็กเกจรันไทม์ endpoint และการตั้งค่าคำขอออกจากกัน:

```jsonc
// V1
{
  "provider": {
    "acme": {
      "npm": "@ai-sdk/openai-compatible",
      "api": "https://llm.example.com/v1",
      "options": {
        "apiKey": "{env:ACME_API_KEY}"
      }
    }
  }
}

// V2
{
  "providers": {
    "acme": {
      "package": "aisdk:@ai-sdk/openai-compatible",
      "settings": {
        "baseURL": "https://llm.example.com/v1",
        "apiKey": "{env:ACME_API_KEY}"
      }
    }
  }
}
```

`npm` ของ V1 เปลี่ยนเป็น `package` และแพ็กเกจ AI SDK จะได้รับคำนำหน้า `aisdk:` ส่วน `api` เปลี่ยนเป็น `settings.baseURL` `options` ของผู้ให้บริการจะแยกเป็น `settings`, `headers` และ `body` ตามบทบาทในคำขอ และ `options.setCacheKey` จะกลายเป็น `compatibility.supportsPromptCacheKey` ของผู้ให้บริการ ดู[ผู้ให้บริการ](/providers)

V2 รวมเนมสเปซผู้ให้บริการแบบเดิม 2 รายการ:

| ID ผู้ให้บริการใน V1 | ID ผู้ให้บริการหลักใน V2 |
| -------------------------- | ------------------------ |
| `azure-cognitive-services` | `azure`                  |
| `google-vertex-anthropic`  | `google-vertex`          |

การย้ายฟิลด์ผู้ให้บริการ เอเจนต์ คำสั่ง และตัวกรองผู้ให้บริการของ V1 ที่ไม่กำกวมจะใช้ ID หลักเหล่านี้ ส่วนฟิลด์ `model` ระดับบนสุดที่ใช้ร่วมกันจะคง ID ผู้ให้บริการไว้ตามเดิมทุกตัวอักษร เพราะไวยากรณ์เดียวกันนี้ใช้ได้ในการกำหนดค่าเนทีฟของ V2 ด้วย เมื่อย้ายผู้ให้บริการในตัวแบบเดิม ให้อัปเดตฟิลด์นี้เป็น ID หลัก

### โมเดลและ variant

โมเดลยังคงซ้อนอยู่ใต้ผู้ให้บริการ แต่ฟิลด์ของโมเดลหลายตัวชัดเจนขึ้น:

- `id` เปลี่ยนเป็น `modelID`
- `tool_call` และ `modalities` เปลี่ยนเป็น `capabilities.tools`, `capabilities.input` และ `capabilities.output`
- `status` ที่เป็น `"deprecated"` เปลี่ยนเป็น `disabled: true`
- ค่าใช้จ่ายแคชย้ายจาก `cache_read` และ `cache_write` ไปเป็น `cache.read` และ `cache.write`
- `options` เฉพาะผู้ให้บริการเปลี่ยนเป็น `settings`
- ออบเจกต์ variants ของ V1 เปลี่ยนเป็นอาร์เรย์ของ V2 โดยแต่ละรายการมี `id`

```jsonc
// V1
{
  "variants": {
    "high": {
      "reasoningEffort": "high"
    }
  }
}

// V2
{
  "variants": [
    {
      "id": "high",
      "settings": {
        "reasoningEffort": "high"
      }
    }
  ]
}
```

ดูโครงสร้างโมเดลแบบเนทีฟฉบับสมบูรณ์ได้ที่[โมเดล](/models)

### ฟิลด์ที่รองรับแต่ไม่มีฟิลด์เนทีฟที่ตรงกันโดยตรง

ฟิลด์ส่วนใหญ่ที่คงโครงสร้างเดิม เช่น `shell`, `model`, `default_agent`, `watcher`, `formatter`, `instructions`, `enterprise` และ `tool_output` ไม่ต้องย้าย

V2 ยอมรับและเก็บการกำหนดค่า `lsp` ไว้ แต่ไม่รัน language server ไม่เปิดเครื่องมือ LSP และไม่สร้างผลวินิจฉัย (diagnostics) ของ LSP ให้แทนที่เวิร์กโฟลว์ที่พึ่งพาความสามารถเหล่านี้ด้วยคำสั่ง lint, typecheck หรือคอมไพเลอร์ของโปรเจกต์

ตัวกรองผู้ให้บริการของ V1 ไม่มีฟิลด์การกำหนดค่าเนทีฟของ V2 ที่ตรงกันแบบหนึ่งต่อหนึ่ง แต่พฤติกรรมยังคงรองรับผ่าน[นโยบาย](/policies):

- `enabled_providers` จะกลายเป็นนโยบายผู้ให้บริการภายในที่ปฏิเสธโดยค่าเริ่มต้น ตามด้วยการอนุญาตผู้ให้บริการที่ระบุ
- `disabled_providers` จะกลายเป็นนโยบายปฏิเสธภายในสำหรับผู้ให้บริการที่ระบุ
- `autoupdate` เปลี่ยนเป็น `update`: `false` แมปเป็น `"disable"` `"notify"` แมปเป็น `"notify"` และ `true` แมปเป็น `"auto"`
- `small_model` จะกลายเป็นการเลือก `model` ของเอเจนต์ `title` ในตัว การกำหนดค่าเนทีฟของ V2 ควรใช้ `agents.title.model` แทน

คุณเก็บฟิลด์เหล่านี้ไว้ในไวยากรณ์ V1 ได้ OpenCode จะปรับให้เป็นรูปแบบเดียวกันโดยไม่แสดงคำเตือน

### ฟิลด์ที่ยอมรับแต่ไม่รองรับ

schema ของ V1 ยังยอมรับฟิลด์ที่ไม่มีพฤติกรรมที่รองรับใน V2 V2 จะละเว้นค่าเหล่านี้และแสดงคำเตือน เพื่อไม่ให้เข้าใจผิดว่าเป็นการกำหนดค่าที่มีผลอยู่:

- `logLevel`: ใช้ `OPENCODE_LOG_LEVEL` เมื่อเริ่ม OpenCode
- `server`: ใช้บริการของ V2 และตัวเลือกเซิร์ฟเวอร์แบบระบุชัดเจน API ของเซิร์ฟเวอร์เป็น breaking change โดยตั้งใจ
- `subagent_depth` ระดับบนสุด: ใช้ `experimental.subagent_depth` แทน
- `compaction.tail_turns` และ `compaction.prune`: V2 ใช้ `compaction.keep.tokens` และการบีบอัดบริบทแบบ checkpoint แทน
- `name` ของเอเจนต์ในการกำหนดค่า JSON ของ V1
- รายการ MCP ของ V1 ที่มีเพียงการเปิดใช้งานโดยไม่มี `type`
- ฟิลด์ทดลองของ V1 ได้แก่ `batch_tool`, `openTelemetry`, `primary_tools` และ `continue_loop_on_deny`
- ฟิลด์ผู้ให้บริการของ V1 ได้แก่ `id`, `whitelist` และ `blacklist`
- ฟิลด์โมเดลของผู้ให้บริการใน V1 ได้แก่ `release_date`, `attachment`, `reasoning`, `temperature`, `experimental`, `status` ที่ไม่ใช่ `deprecated` และ `interleaved` แบบบูลีน

การละเว้นฟิลด์เหล่านี้เป็นความตั้งใจ ไม่ใช่การถดถอยด้านความเข้ากันได้ หาก V2 ไม่คงพฤติกรรมที่ระบุว่ารองรับไว้ในส่วนอื่นของคู่มือนี้ ให้ทำตามแนวทางการรายงานปัญหาใน[การแก้ไขปัญหา](/troubleshooting)

### ไฟล์เอเจนต์

ไฟล์เอเจนต์ของ V1 อาจอยู่ใน `agent/`, `agents/`, `mode/` หรือ `modes/` V2 ยังค้นพบได้ทั้งสี่ไดเรกทอรี ตำแหน่งที่แนะนำใน V2 คือ:

```text
.opencode/agents/<name>.md
```

ไฟล์ในไดเรกทอรี `mode/` หรือ `modes/` ของ V1 แทนเอเจนต์หลัก เมื่อย้ายไฟล์เหล่านี้ไปไว้ใน `agents/` ให้เพิ่ม `mode: primary` ใน frontmatter ส่วนไฟล์ใน `agent/` ย้ายไปไว้ใน `agents/` ได้โดยไม่เปลี่ยน ID ที่ได้จากพาธ

เมื่อแปลง frontmatter เป็นฟิลด์เนทีฟของ V2:

- เก็บเนื้อหา Markdown ไว้เป็นคำแนะนำระบบของเอเจนต์
- เปลี่ยนชื่อ `prompt` เป็น `system` เมื่อปรากฏในการกำหนดค่า JSON ส่วนเนื้อหาของไฟล์ไม่ต้องมีฟิลด์ `system`
- เปลี่ยนชื่อ `disable` เป็น `disabled` และ `permission` เป็น `permissions`
- รวม `model` และ `variant` เป็น `provider/model#variant`
- ย้าย `temperature`, `top_p` และตัวเลือกเฉพาะผู้ให้บริการไปไว้ใต้ `request.body`

V2 แปลง frontmatter ของเอเจนต์แบบเดิมให้อัตโนมัติ การแก้ไขเหล่านี้จึงไม่บังคับ ดู[เอเจนต์](/agents)

### ไฟล์คำสั่ง

ไฟล์คำสั่งของ V1 อาจอยู่ใน `command/` หรือ `commands/` V2 ค้นพบได้ทั้งสองไดเรกทอรี ตำแหน่งที่แนะนำคือ:

```text
.opencode/commands/<name>.md
```

ย้ายไฟล์จาก `command/` ไปยังพาธสัมพัทธ์เดียวกันใต้ `commands/` เพื่อคงชื่อคำสั่งไว้ เนื้อหา Markdown ยังเป็นเทมเพลตของคำสั่ง และ frontmatter `description` กับ `agent` ใช้ชื่อเดิม เปลี่ยนชื่อ `subtask` เป็น `subagent` เพื่อใช้ชื่อเนทีฟสำหรับการมอบหมายงานในเบื้องหลัง หาก frontmatter มีฟิลด์ `model` และ `variant` แยกกัน ให้ต่อ variant ท้ายโมเดลแล้วลบ `variant` ออก:

```yaml
# V1
model: anthropic/claude-sonnet-4-5
variant: high
subtask: true

# V2
model: anthropic/claude-sonnet-4-5#high
subagent: true
```

ดู[คำสั่ง](/commands)

### ไฟล์สกิล

V2 ค้นพบสกิลได้ทั้งจาก `.opencode/skill/` และ `.opencode/skills/` โครงสร้างที่แนะนำคือ:

```text
.opencode/skills/<skill-id>/SKILL.md
```

ย้ายไดเรกทอรีสกิลทั้งไดเรกทอรี ไม่ใช่แค่ `SKILL.md` เพื่อให้สคริปต์ ไฟล์อ้างอิง และไฟล์ประกอบอื่น ๆ ที่อ้างด้วยพาธสัมพัทธ์ยังใช้งานได้ คงชื่อไดเรกทอรีไว้เพื่อรักษา ID ของสกิล frontmatter และเนื้อหา Markdown ของสกิลที่มีอยู่ไม่ต้องเขียนใหม่สำหรับ V2 ดู[สกิล](/skills)

### ไฟล์คำแนะนำ

ไฟล์ `AGENTS.md` ที่มีอยู่อยู่ที่เดิมได้ V2 ค้นพบ `~/.config/opencode/AGENTS.md` ส่วนกลาง และไฟล์ `AGENTS.md` ตามตำแหน่งตั้งแต่ไดเรกทอรีปัจจุบันขึ้นไปจนถึงโฮมไดเรกทอรี สำหรับโปรเจกต์ที่อยู่นอกโฮมไดเรกทอรี การค้นหาจะหยุดที่รากของโปรเจกต์

หากการตั้งค่า V1 พึ่งพา `CLAUDE.md` เป็นไฟล์สำรอง ให้ย้ายแนวทางนั้นไปไว้ใน `AGENTS.md` ที่เกี่ยวข้อง ปัจจุบัน V2 ค้นพบเฉพาะ `AGENTS.md` และเนื่องจากพฤติกรรมของ V1 ที่ไม่ใช่ API ตั้งใจให้เข้ากันได้ ให้แจ้งปัญหาด้านความเข้ากันได้พร้อมรายละเอียดของโปรเจกต์ที่ได้รับผลกระทบด้วย ดู[คำแนะนำ](/instructions)

## การกำหนดค่าไคลเอนต์เทอร์มินัล

V2 แทนที่ไฟล์ `tui.json(c)` แบบซ้อนหลายชั้นของ V1 ด้วยไฟล์กำหนดค่าไคลเอนต์เทอร์มินัลส่วนกลางไฟล์เดียว:

```text
~/.config/opencode/cli.json
```

ไฟล์นี้เป็นของไคลเอนต์เทอร์มินัล บริการเบื้องหลังจะไม่โหลดไฟล์นี้ เมื่อไม่มี `cli.json` การเริ่มไคลเอนต์เทอร์มินัล V2 ครั้งแรกจะย้ายการตั้งค่าใน `tui.json` ส่วนกลางที่รองรับและค่ากำหนดที่บันทึกไว้ โดยไม่แก้ไขไฟล์ของ V1 การกำหนดค่าไคลเอนต์ระดับโปรเจกต์จะไม่ถูกย้าย เพราะการกำหนดค่าไคลเอนต์ของ V2 เป็นแบบส่วนกลาง ดูข้อมูลอ้างอิงการตั้งค่าไคลเอนต์ปัจจุบันได้ที่[การตั้งค่า CLI](/cli/config)

## ปลั๊กอิน

เปลี่ยนชื่อ `plugin` เป็น `plugins` และแทนที่ทูเพิลแพ็กเกจกับตัวเลือกด้วยออบเจกต์:

```jsonc
// V1
{
  "plugin": ["opencode-example-plugin", ["./plugin/local.ts", { "enabled": true }]]
}

// V2
{
  "plugins": [
    "opencode-example-plugin",
    {
      "package": "./plugin/local.ts",
      "options": { "enabled": true }
    }
  ]
}
```

V2 ค้นพบปลั๊กอินภายในเครื่องได้ทั้งจาก `.opencode/plugin/` และ `.opencode/plugins/` ให้ใช้ `.opencode/plugins/` สำหรับไฟล์ของ V2

<Callout type="warning">
  โค้ดปลั๊กอินของ V1 ไม่ทำงานใน V2 การย้ายไฟล์หรือเปลี่ยนชื่อรายการในการกำหนดค่าเพียงอย่างเดียวไม่เพียงพอ
</Callout>

พอร์ต entrypoint, hook, เครื่องมือ, อีเวนต์ และ export ของแพ็กเกจตาม[คู่มือการย้ายปลั๊กอิน](/build/plugins/migrate-v1)

## API ของเซิร์ฟเวอร์และไคลเอนต์

OpenCode 2 มี API ของเซิร์ฟเวอร์ที่ปรับปรุงใหม่ให้ใช้งานสะดวกขึ้น และมีชุดไคลเอนต์ใหม่ อินทิเกรชันที่เรียก API ของเซิร์ฟเวอร์ V1 ต้องย้ายไปใช้ API ของ V2

ใช้แพ็กเกจ `@opencode/client` เพื่อเข้าถึง API ของ V2 ที่เผยแพร่แล้ว ดู endpoint ประเภทคำขอ และการตอบกลับได้ใน[ข้อมูลอ้างอิง API](/api) ที่สร้างขึ้นโดยอัตโนมัติ

## ตรวจสอบการตั้งค่า

ตรวจสอบโมเดล ข้อมูลรับรองของผู้ให้บริการ เอเจนต์ สิทธิ์ เซิร์ฟเวอร์ MCP และปลั๊กอินในโปรเจกต์ก่อนใช้ V2 ทำงานจริงเป็นประจำ เก็บการตั้งค่า V1 ไว้จนกว่าจะยืนยันได้ว่า V2 ทำงานตามที่ต้องการ และอย่าให้ V1 ใช้การกำหนดค่าที่แปลงเป็นรูปแบบเนทีฟของ V2 แล้ว
