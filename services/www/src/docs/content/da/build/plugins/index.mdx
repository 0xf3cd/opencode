Plugins kan ændre OpenCodes adfærd og tilføje nye funktioner. Byg et [CLI-plugin](/build/plugins/cli), hvis du vil ændre
terminalbrugerfladen.

Migrerer du et eksisterende OpenCode 1-plugin? Følg [migrationsguiden til V1-plugins](/build/plugins/migrate-v1).

```ts title=".opencode/plugins/example/index.ts"
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "example",
  async setup(ctx) {
    await ctx.storage.set("loaded", true)
  },
})
```

Plugins i `.opencode/plugins/` indlæses automatisk, som det lokale eksempel ovenfor. Tilføj publicerede pakker eller
plugin-mapper fra andre placeringer til `plugins` i `opencode.json(c)` for at indlæse dem:

```jsonc title="opencode.jsonc"
{
  "$schema": "https://opencode.ai/config.json",
  "plugins": [
    "opencode-acme-plugin",
    "opencode-acme-plugin@1.2.0",
    "@acme/opencode-plugin",
    "./plugins/local",
    "../shared/plugin",
    "/absolute/path/plugin",
    "file:///home/me/plugins/local",
    {
      "package": "@acme/opencode-plugin",
      "options": {
        "agent": "reviewer",
        "strict": true,
      },
    },
  ],
}
```

Se [Konfigurer plugins](/plugins) for flere muligheder for indlæsning og konfiguration.

## Livscyklus

`setup` kører, når pluginnet indlæses. Den kan returnere en oprydningsfunktion, der kører, når pluginnet lukkes ned.

```ts
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "example",
  setup(ctx) {
    console.log(`loaded in OpenCode ${ctx.app.version}`)
    return () => console.log("unloaded")
  },
})
```

### Kontekst

Plugin-konteksten er i bund og grund en [klient til OpenCode-serveren](/build/client).
Dens læse- og handlingsmetoder bruger samme input og svar som klienten. Derudover
har den metoder, der kun findes for plugins: transformationer, runtime-hooks,
genindlæsning, registreringer og plugin-indstillinger.

```ts
setup(ctx) {
  console.log(ctx.app.version)
}
```

`ctx.location` beskriver den placering, hvor denne plugininstans er indlæst. Den
indeholder `directory`, et valgfrit `workspaceID` og `project`-metadata (`id`,
`directory` og `canonical`). Den findes i både Promise- og Effect-plugins.
Det er plugininstansens placering, ikke placeringen for alle de sessioner, den kan
tilgå, eller de hændelser, den modtager.

```ts
setup(ctx) {
  console.log(ctx.location.directory)
  console.log(ctx.location.project.canonical)
}
```

### Indstillinger

Angiv plugin-indstillinger med objektformen i `opencode.json(c)`.

```jsonc title="opencode.jsonc"
{
  "plugins": [
    {
      "package": "./plugins/company",
      "options": {
        "strict": true,
      },
    },
  ],
}
```

Læs værdierne fra `ctx.options` under `setup`.

```ts title="plugins/company/index.ts"
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "company",
  setup(ctx) {
    const strict = ctx.options.strict === true
  },
})
```

## Transformationer

Transformationer er synkrone ændringer af OpenCodes domænetilstand, og hver af dem bygger videre på tidligere
registreringer i samme domæne. Læsninger fra registret, som `ctx.model.list()`, afspejler alle registreringer indtil
nu, også under plugin-opsætningen; batching ved opstart samler kun opdateringsnotifikationer og forsinker aldrig det, en
læsning returnerer. Status-API'er for ressourcer rapporterer stadig tilstanden for kørende ressourcer: En registreret
definition betyder ikke, at dens forbindelse eller andet ressourcearbejde er afsluttet.

Kilder bidrager med udbydere og uforanderlige modeldefinitioner via `ctx.provider.transform`.

```ts title="plugins/models/index.ts"
import { Model, Plugin, Provider } from "@opencode/plugin"

export default Plugin.define({
  id: "company.models",
  async setup(ctx) {
    const providerID = Provider.ID.make("acme")
    const models = [{ ...Model.Info.default(providerID, Model.ID.make("reasoner")), name: "Acme Reasoner" }]
    await ctx.provider.transform((editor) => {
      editor.add({
        info: {
          ...Provider.Info.empty(providerID),
          name: "Acme",
          activation: "enabled",
          package: "@opencode/ai/providers/openai-compatible",
          settings: { baseURL: "http://127.0.0.1:8000/v1" },
        },
        models,
      })
    })

    const available = await ctx.model.list()
  },
})
```

Enhver registrering, fjernelse eller `reload()` markerer registret som ændret; den næste læsning genopbygger det ved at
afspille alle aktive transformationer i registreringsrækkefølge på en frisk værdi. Hold transformationer billige og
gentagelige. En værdi, du allerede har læst, ændres aldrig af senere genopbygninger.

Når udbydertransformationer og tilgængelighed er afgjort, materialiserer OpenCode de aktive udbyderes modeller og
afspiller alle modeltransformationer i rækkefølge. En modelpolitik kan undersøge hele samlingen af kandidater, også
nyligt opdaterede kilder.

```ts title="plugins/model-budget/index.ts"
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "company.model-budget",
  async setup(ctx) {
    await ctx.model.transform((editor) => {
      editor
        .list()
        .filter((model) => model.cost.some((tier) => tier.output > 20))
        .forEach((model) => {
          editor.remove(model.providerID, model.id)
        })
    })
  },
})
```

Indfangede input overvåges ikke automatisk. Indlæs eksterne data før det synkrone callback, og kald `reload()`, når
de input ændres. Her returnerer `loadFromSource()` elementer af typen
`{ info: Provider.Info, models: readonly Model.Info[] }`.

```ts title="plugins/models/index.ts"
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "company.models",
  async setup(ctx) {
    const source = { providers: await loadFromSource() }

    await ctx.provider.transform((editor) => {
      source.providers.forEach((provider) => editor.add(provider))
    })

    const refresh = async () => {
      source.providers = await loadFromSource()
      await ctx.provider.reload()
    }

    const timer = setInterval(() => void refresh().catch(console.error), 60_000)
    return () => clearInterval(timer)
  },
})
```

Udbyderændringer invaliderer hele det aktive modelresultat, så politikken for outputpris stadig filtrerer de opdaterede
modeller. Brug `ctx.model.reload()`, når kun et input, som en modeltransformation har indfanget, ændres.

## API

### Agent

Læs alle agenter, eller hent én efter ID.

```ts
const agents = await ctx.agent.list()
const build = await ctx.agent.get({ agentID: "build" })
```

Registrer en transformation for at undersøge, opdatere eller fjerne agenter eller vælge standardagenten.

```ts
await ctx.agent.transform((editor) => {
  const agents = editor.list()
  const build = editor.get("build")

  editor.default("build")
  editor.update("build", (agent) => {
    agent.description = "Builds features and fixes bugs"
  })
  editor.remove("legacy")
})
```

Genindlæs agenter, når ekstern tilstand, som en transformation bruger, ændres.

```ts
await ctx.agent.reload()
```

### Udbydere

Læs tilgængelige udbydere, eller undersøg én udbyders metadata efter ID.

```ts
const providers = await ctx.provider.list()
const provider = await ctx.provider.get({ providerID: "anthropic" })
```

Udbydertransformationer redigerer udbyderindstillinger og kildedefinitioner. Editorens læsninger omfatter inaktive
udbydere og udstiller uforanderlige definitioner; `models.update` redigerer en ejet kopi af en kildemodel.

```ts
await ctx.provider.transform((editor) => {
  editor.update("anthropic", (provider) => {
    provider.headers = { ...provider.headers, "x-company": "engineering" }
  })
  editor.models.update("anthropic", "claude-sonnet-4-5", (model) => {
    model.name = "Team Sonnet"
  })
  editor.models.remove("anthropic", "legacy-model")
  editor.remove("legacy-provider")
})
```

Erstat en udbyders kildeinventar med `models.set`, og genindlæs, når de indfangede definitioner ændres.

```ts
const source = { models: await loadModels() }
await ctx.provider.transform((editor) => {
  editor.models.set("acme", source.models)
})

source.models = await loadModels()
await ctx.provider.reload()
```

Ved kontospecifik discovery skal du angive den forbindelse, der blev brugt til at indlæse inventaret, som
`sourceConnection`. OpenCode udelader udbyderen, mens en anden forbindelse er valgt, indtil dit plugin publicerer sit
opdaterede inventar.

```ts
const connection = await ctx.integration.connection.active("acme")
if (!connection) return
const inventory = await loadInventory(connection)
await ctx.provider.transform((editor) => {
  editor.add({ info: inventory.provider, models: inventory.models, sourceConnection: connection })
})
```

Skemaer: [`Provider.Info`](/api#schema-Provider.Info), [`Model.Info`](/api#schema-Model.Info)


### Modeller

Læs tilgængelige modeller og standardvalget.

```ts
const models = await ctx.model.list()
const selected = await ctx.model.default()
```

Modeltransformationer redigerer hele samlingen af kandidater fra aktive udbydere. Deaktiverede kandidater kan stadig
redigeres, indtil alle transformationer er færdige; `update` kan kun tilføje en model under en tilgængelig udbyder.

```ts
await ctx.model.transform((editor) => {
  editor.list("anthropic").forEach((model) => {
    editor.update(model.providerID, model.id, (draft) => {
      draft.enabled = draft.capabilities.tools
    })
  })
  editor.default.set("anthropic", "claude-sonnet-4-5")
  editor.remove("anthropic", "legacy-model")
})
```

Callbacks redigerer rå modeltilsidesættelser. Udbyderens standardværdier flettes én gang, når OpenCode gemmer
resultatet; uændrede læsninger genbruger resultatet. `editor.provider` udstiller uforanderlige kildedefinitioner,
herunder inaktive skabeloner, og ikke output fra modeltransformationer.

```ts
await ctx.model.transform((editor) => {
  const source = editor.provider.get("anthropic")?.models.get("claude-sonnet-4-5")
  if (!source) return
  editor.update("anthropic", source.id, (model) => {
    model.limit.context = Math.min(model.limit.context, source.limit.context)
  })
})

await ctx.model.reload()
```

### Integrationer

Læs integrationer, og undersøg aktive legitimationsoplysninger.

```ts
const integrations = await ctx.integration.list()
const github = await ctx.integration.get({ integrationID: "github" })
const connection = await ctx.integration.connection.active("github")
const credential = connection ? await ctx.integration.connection.resolve(connection) : undefined
```

Forbind integrationer med en API-nøgle.

```ts
await ctx.integration.connect.key({
  integrationID: "github",
  key: process.env.GITHUB_TOKEN!,
})
```

Start, undersøg, fuldfør eller annuller et OAuth-forbindelsesforsøg.

```ts
const attempt = await ctx.integration.oauth.connect({ integrationID: "github", methodID: "oauth" })
const status = await ctx.integration.oauth.status({ integrationID: "github", attemptID: attempt.data.attemptID })
await ctx.integration.oauth.complete({ integrationID: "github", attemptID: attempt.data.attemptID, code })
await ctx.integration.oauth.cancel({ integrationID: "github", attemptID: attempt.data.attemptID })
```

Kommandobaserede forbindelser har det samme forløb med start, status og annullering.

```ts
const attempt = await ctx.integration.command.connect({ integrationID: "acme", methodID: "cli" })
const status = await ctx.integration.command.status({ integrationID: "acme", attemptID: attempt.data.attemptID })
await ctx.integration.command.cancel({ integrationID: "acme", attemptID: attempt.data.attemptID })
```

Registrer en transformation for at undersøge integrationer og administrere deres godkendelsesmetoder.

```ts
await ctx.integration.transform((editor) => {
  const integrations = editor.list()
  const acme = editor.get("acme")

  editor.update("acme", (integration) => {
    integration.name = "Acme"
  })
  editor.method.update({
    integrationID: "acme",
    method: { id: "cli", type: "command", label: "Sign in with Acme CLI", command: ["acme", "login"] },
  })

  const methods = editor.method.list("acme")
  const legacy = methods.find((method) => method.type === "command" && method.id === "legacy")
  if (legacy) editor.method.remove("acme", legacy)
  editor.remove("legacy")
})
```

Genindlæs integrationer, når ekstern tilstand, som en transformation bruger, ændres.

```ts
await ctx.integration.reload()
```

### MCP

List MCP-servere og deres aktuelle forbindelsestilstand.

```ts
const servers = await ctx.mcp.list()
```

Plugins administrerer kun MCP-servere via transformationer. Brug `editor.set` til at tilføje eller erstatte en server,
`editor.update` til at ændre dens konfiguration og `editor.remove` til at fjerne den. Undersøg konfigurationen med
`editor.list` og `editor.get`.

```ts
await ctx.mcp.transform((editor) => {
  const servers = editor.list()
  const docs = editor.get("docs")
  editor.set("docs", { type: "remote", url: "https://mcp.example.com" })
  editor.update("docs", (server) => {
    server.disabled = false
  })
  editor.remove("legacy")
})
```

Sæt `disabled: true` i en transformation for at deaktivere en server og afbryde forbindelsen til den, eller
`disabled: false` for at aktivere den og lade OpenCode forbinde. OpenCode afstemmer serverens livscyklus ud fra den
transformerede konfiguration.

Kald `reload()`, når ekstern tilstand, som en transformation bruger, ændres, for at anvende transformationerne igen og
afstemme serverne.

```ts
await ctx.mcp.reload()
```

```ts
const review = await ctx.generate.text({
```

### Tilladelser

Undersøg eller besvar ventende tilladelsesanmodninger.

```ts
const pending = await ctx.permission.list({ sessionID })
const request = await ctx.permission.get({ sessionID, requestID })
await ctx.permission.reply({ sessionID, requestID, reply: "once" })
```

Erstat de tilladelsesregler, der gælder for sessionen. De evalueres efter agentens regler, og den sidste regel, der
matcher, vinder. Undersessioner arver de regler, der gælder, når de oprettes.

```ts
await ctx.permission.rules({
  sessionID,
  permissions: [{ action: "edit", resource: "/path/to/original/checkout/**", effect: "deny" }],
})
```

### Sessioner

Opret eller læs en session.

```ts
const created = await ctx.session.create({ title: "Review" })
const session = await ctx.session.get({ sessionID })
const messages = await ctx.session.context({ sessionID })
```

Skift den agent eller model, som efterfølgende anmodninger bruger.

```ts
await ctx.session.switchAgent({ sessionID, agent: "build" })
await ctx.session.switchModel({ sessionID, model: { providerID: "anthropic", id: "claude-sonnet-4-5" } })
```

Send brugerprompts, midlertidige genereringsanmodninger, kommandoer eller syntetiske beskeder.

```ts
const prompt = await ctx.session.prompt({ sessionID, text: "Review the current changes" })
const generated = await ctx.session.generate({ sessionID, prompt: "Summarize this project" })
const command = await ctx.session.command({ sessionID, command: "review", arguments: "--staged" })
const synthetic = await ctx.session.synthetic({ sessionID, text: "Deployment completed" })
```

Omdøb, afbryd eller vent på en session.

```ts
await ctx.session.update({ sessionID, title: "Review" })
await ctx.session.interrupt({ sessionID, continue: false })
await ctx.session.wait({ sessionID })
```

### Værktøjer

Læs de værktøjer, der aktuelt er registreret efter alle transformationer, uden for et transformations-callback. Hvert
værktøj har et `id`, der indeholder dets effektive navn.

```ts
const tools = await ctx.tool.list()
const read = tools.find((tool) => tool.id === "read")
```

Registrer, opdater og fjern værktøjer med en synkron transformation, også i Promise-plugins. Indlæs eksterne data før
registrering eller genindlæsning. En senere gyldig registrering tilsidesætter det samme effektive værktøjsnavn.

```ts
const registration = await ctx.tool.transform((editor) => {
  editor.namespace({
    name: "acme",
    description: "Customer account tools",
  })
  editor.add({
    name: "greeting",
    description: "Create a greeting",
    input: {
      type: "object",
      properties: { name: { type: "string" } },
      required: ["name"],
      additionalProperties: false,
    },
    options: { namespace: "acme", codemode: true },
    execute: async (input, context) => {
      await context.progress({ status: "greeting" })
      return { content: `Hello ${(input as { name: string }).name}!` }
    },
  })
})
```

Promise-baserede værktøjsudførere modtager `context.signal`. Send det videre til arbejde, der kan annulleres, som
`fetch`, så den underliggende operation også stopper, når sessionen stoppes.

```ts
execute: async ({ url }, context) => {
  const response = await fetch(url, { signal: context.signal })
  return { content: await response.text() }
}
```

Kald `reload()`, når du har ændret kildedata, som callbacket har indfanget. Genindlæsning afspiller de aktive
transformationer igen uden at ændre deres rækkefølge; den kører ikke plugin-opsætningen igen.

```ts
await ctx.tool.reload()
```

Brug `list()` og `get()` til at undersøge de værktøjer, der aktuelt er i editoren. Værktøjer har et `id`, der indeholder
deres effektive navn, og `get()` returnerer `undefined`, når det ID ikke findes. Brug `update` og `remove` med det
effektive værktøjsnavn inklusive navnerummet (`acme_greeting` ovenfor). Punktummer i navnerum og ikke-understøttede tegn i
værktøjsnavne bliver til `_`. Manglende navne ignoreres; for at oprette et værktøj skal du bruge `add` med en komplet
definition. Opdateringer bevarer navn og navnerum. Tildel nye skemaer eller indstillinger for at erstatte dem i stedet
for at ændre indlejrede værdier. Ugyldige opdateringer logges, og den tidligere definition forbliver uændret.

```ts
await ctx.tool.transform((editor) => {
  editor.update("acme_greeting", (tool) => {
    tool.description = "Greet the user by name"
  })
  editor.remove("acme_obsolete")
})
```

Opdateringer og fjernelser afspilles i rækkefølge sammen med tilføjelser, også efter opdateringer af MCP-kataloget. Når
deres registrering frigives, fjernes disse ændringer, og resultatet genopbygges ud fra de resterende transformationer.

Frigiv en registrering for at fjerne dens transformation og genopbygge ud fra de resterende transformationer, så en
tidligere definition, den tilsidesatte, kommer frem igen. Frigivelse er idempotent, og når pluginnet lukkes ned,
frigives dets registreringer også.

```ts
await registration.dispose()
```

Hver modelanmodning indfanger et stabilt, eksekverbart snapshot af værktøjerne. Senere transformationer, genindlæsninger
og frigivelser påvirker fremtidige snapshots, ikke de definitioner, Code Mode-navnerumsbeskrivelser eller udførere, der
allerede er indfanget. Udførere, der lukker over muterbare plugindata, ser stadig ændringer i dem; indfang en værdi inde
i transformationen, når den skal forblive knyttet til netop den definition.

### Worktrees

Registrer en lokal worktree-strategi via den normale plugin-livscyklus. Implementeringsmodulet i dette eksempel står for
validering af indstillinger og backendens operationer `create`, `remove` og `list`.

```ts title="plugins/worktrees/index.ts"
import { Plugin } from "@opencode/plugin"
import { makeStrategy } from "./strategy"

export default Plugin.define({
  id: "company.worktrees",
  async setup(ctx) {
    const strategy = makeStrategy(ctx.options)
    await ctx.worktree.transform((editor) => {
      editor.add(strategy)
    })
  },
})
```

Indlæs pluginnet via `plugins`, og konfigurer den fælles destination separat:

```jsonc title="opencode.jsonc"
{
  "worktree": { "directory": "../worktrees" },
  "plugins": [{ "package": "./plugins/worktrees", "options": {} }],
}
```

- Når en strategi tilføjes, vælges den automatisk. Den sidste aktive registrering vinder; der kræves ingen konfiguration til valg af strategi.
- Når registreringen frigives, eller pluginnet lukkes ned, gendannes den tidligere implementering, i sidste ende den medfølgende Git-strategi.
- `reload()` afspiller transformationer igen, når indfangede input ændres; den kører ikke plugin-opsætningen igen.
- Fejl under oprettelse forsøges ikke igen via Git. Eksisterende worktrees beholder deres registrerede ejer, selv når standarden ændres.
- Strategier administrerer lokale mapper. Klargøring af eksterne arbejdsområder er ikke en del af denne grænseflade.

#### Operationer

Plugin-konteksten udstiller de samme projektbaserede worktree-operationer som klienten. Alle operationer kræver et
`projectID`. `list` læser kun det gemte inventar, herunder kendte checkouts af samme projekt; den indlæser ikke
konfiguration, starter ikke plugins og opdager ikke ændringer i filsystemet.

```ts
const projectID = ctx.location.project.id
const created = await ctx.worktree.create({ projectID, name: "task" })
const inventory = await ctx.worktree.list({ projectID })
await ctx.worktree.refresh({ projectID })
await ctx.worktree.remove({ projectID, directory: created.directory, force: false })
```

Oprettelse indlæser konfiguration og plugins fra projektets gemte `canonical`-mappe og bruger den strategi, de har valgt.
Den accepterer en valgfri overordnet `directory`, en kilde `from`, en startgren `branch` og et `name`.
Kilden er som standard den kanoniske checkout, og en `from`-tilsidesættelse skal høre til det projekt. Valget af kilde
ændrer ikke konfigurationsroden.
En angivet start-ref skal understøttes af den valgte strategi;
Rifts native snapshot-operation har for eksempel ingen mulighed for at vælge en ref.

Oprettelse og opdatering venter på, at den kanoniske checkouts plugins er aktiveret. Kald, der foretages under den
checkouts plugin-opsætning, ser de registreringer, der er foretaget indtil da, og venter ikke på deres egen aktivering.

Fjernelse indlæser den kanoniske konfiguration og aktiverer dens plugins og bruger derefter worktreens registrerede
strategi i stedet for den aktuelt valgte standard. Hvis den registrerede ejer ikke er tilgængelig, opstår der en fejl.
Worktreens destination kan ligge et andet sted:

```ts
await ctx.worktree.remove({
  directory: "/worktrees/task",
  projectID,
  force: false,
})
```

Manglende ejere får fjernelsen til at fejle i stedet for at falde tilbage til Git. En strategi kan kaste
`new Worktree.OperationError({ message: "Uncommitted changes", forceRequired: true })`, med `Worktree` importeret fra
`@opencode/plugin`, for at bede om bekræftelse af tvungen fjernelse uden at afhænge af fejl fra Core eller Git.

Opdatering indlæser den kanoniske konfiguration og beder alle tilgængelige strategier om at finde worktrees på tværs af
kendte checkout-rødder. Den samler resultaterne, bevarer registreret ejerskab og rydder manglende mapper væk. En kilde,
der fejler under discovery, logges, mens andre kilder fortsætter. Eksisterende mapper forbliver gemt, selv hvis ingen
tilgængelig strategi rapporterer dem. Lyt efter `worktree.updated`, og kald `list` igen for at læse det ændrede inventar.

```ts
await ctx.worktree.refresh({ projectID })
```

#### Reference

Implementeringer modtager en foreslået destination, efter at navngivning og navnekollisioner er håndteret. Returner den
faktiske mappe fra `create`; den kan afvige, når en backend kræver sit eget layout. OpenCode løser den returnerede sti
op og bruger den til inventaret, opstartskommandoer og API-resultatet. Den returnerede mappe skal findes.

Strategier, der vælger en anden destination, håndterer selv navnekollisioner dér. OpenCode opretter stadig den

## Hooks

Hooks griber ind i igangværende operationer. Registrer en hook på dens domæne, og frigiv
den returnerede registrering, når den ikke længere er nødvendig.

```ts
const registration = await ctx.session.hook("context", () => {})
await registration.dispose()
```

Flere plugins kan registrere samme hook. OpenCode kører dem i pluginrækkefølge,
så senere hooks ser de ændringer, tidligere hooks har foretaget.

### Sessioner

Sessionshooks griber ind i modtagelse af prompts, modelkald, native HTTP og nye forsøg.

#### Modtagelse af prompts

Grib ind i indkommende brugerprompts, før vedhæftninger og skills bliver løst, og før prompten optages varigt i inboxen:

```ts
await ctx.session.hook("prompt", (event) => {
  event.prompt.text = event.prompt.text.replaceAll("company-secret", "[redacted]")
  event.prompt.files ??= []
  event.prompt.files.push({ uri: "file:///project/policy.md" })
  event.metadata = { ...event.metadata, source: "company-policy" }
  event.delivery = "queue"
})
```

Hooken modtager en muterbar kladde, som den selv ejer:

- `prompt` indeholder `text`, `files`, agentomtaler i `agents` og valgte `skills`.
- `metadata` indeholder applikationsdefinerede metadata til modtagelsen.
- `delivery` er som standard `"steer"` og kan ændres til `"queue"`.
- Sessions- og besked-ID'er er skrivebeskyttede; en hook kan ikke omdirigere modtagelsen.

Filer og skills, som en hook tilføjer, følger den normale vej for opløsning og
validering. Hvis du omskriver teksten, skal du opdatere eller fjerne `mention`-offsets
for vedhæftninger, der ikke længere passer. Agentomtaler skifter ikke sessionens aktive agent.

Prompt-hooks kører under disse betingelser:

- Hooks kører i registreringsrækkefølge, når sessionens placeringsplugins er klar.
- Kommandoer, der sender via `session.prompt`, kører hooken.
- Syntetiske beskeder, shellbeskeder, komprimeringskontroller og flyttekontroller kører ikke hooken.
- Hooken kører én gang under modtagelsen, ikke før hvert modelkald.
- Afgrænsning til en udbyder er ikke mulig, fordi modelopløsningen sker efter modtagelsen.

Ændringerne bliver det kanoniske, gemte brugerinput. Hvis forberedelsen fejler eller
afbrydes, modtager OpenCode ikke prompten.

Gør prompt-hooks sikre ved gentagne forsøg. De er ikke en grænse for bivirkninger, der sker præcis én gang:

- Et nyt forsøg med et ID, der allerede venter eller er leveret, returnerer den oprindelige modtagelse uden at køre hooks igen.
- Samtidige indsendelser kan køre hooks mere end én gang, men kun den første vellykkede modtagelse vinder.
- Prompt-hooks transformerer input og udstiller ikke et typet API til afvisning.

#### Modelanmodninger

Rediger de samlede systeminstruktioner, beskeder, værktøjer eller anmodningsindstillinger umiddelbart før modellen
kaldes. Hver type anmodning, en session sender, har sin egen hook, så et plugin kan behandle agentløkken og
hjælpeanmodninger forskelligt:

- `context` kører for agentløkken, også fortsættelser drevet af værktøjer.
- `compaction` kører for checkpoint-resuméer. `messages` er det transskript, der opsummeres; OpenCode tilføjer sin
  resuméprompt, efter at hooks har kørt. Sæt `result` for selv at registrere komprimeringen og springe modelkaldet over;
  det tager de samme felter som en færdig komprimeringsbesked.
- `generate` kører for midlertidige `ctx.session.generate`-kald.
- `title` kører for generering af titler. Den har ingen `agent` eller `tools`. Sæt `result` for selv at levere titlen.

```ts
await ctx.session.hook("context", (event) => {
  event.system.push({ type: "text", text: "Keep the review focused on correctness." })
  delete event.tools.write
  event.options.temperature = 0.2
  event.options.maxTokens = 8_000
})

await ctx.session.hook("compaction", async (event) => {
  event.result = { summary: await summarize(event.messages) }
})
```

Ændringerne påvirker kun det udgående modelkald, ikke gemt historik eller konfiguration. En hook, der skal gælde for
alle anmodninger, skal registreres for hver type.

Tilsidesættelser af anmodninger følger disse regler:

- `options` starter tom for hvert modelkald; den indeholder ikke de opløste modelindstillinger.
- Typede nøgler er genereringsindstillinger; alle andre nøgler sendes til den valgte protokol som udbyderindstilling.
- Hooks kører i registreringsrækkefølge og ser tilsidesættelser fra tidligere hooks.
- Tilsidesættelser af anmodninger har forrang for modellens standardværdier, som har forrang for rutens standardværdier.
- Objekter med udbyderindstillinger flettes rekursivt; arrays og skalarværdier erstatter tidligere værdier.
- Hvis du sletter en tilsidesættelse eller sætter den til `undefined`, falder den tilbage til de konfigurerede standardværdier; standardværdierne fjernes ikke.
- Rå HTTP-body-overlays anvendes efter protokolomsætningen og kan tilsidesætte de resulterende felter.

#### Udbyderindstillinger

Udbyderindstillinger bruger den valgte protokols semantiske indstillingsnavne, ikke rå felter i HTTP-bodyen. Afgræns
udbyderspecifikke indstillinger til den matchende udbyder. OpenAI Responses bruger for eksempel `reasoningEffort`:

```ts
await ctx.session.hook(
  "context",
  (event) => {
    event.options.reasoningEffort = "high"
  },
  { providerID: "openai" },
)
```

Genereringsindstillinger afhænger af den valgte protokol og model:

- `maxTokens` er den semantiske grænse for output-tokens.
- Gemini understøtter `topK`; OpenAI Responses udstiller den ikke.

#### Modelanmodning

Rediger indstillinger for modelanmodninger, og afgræns eventuelt hooken til én udbyder. Hændelsen har den samme `kind`
som HTTP-hooks nedenfor.

```ts
await ctx.session.hook(
  "model.request",
  (event) => {
    event.headers["x-plugin"] = "review"
  },
  { providerID: "anthropic" },
)
```

#### Native HTTP

Rediger native anmodninger til eller svar fra udbydere. Deres bodies er streams, der kun kan læses én gang; klon eller
erstat en body, før du læser den.

Begge hooks kører for alle anmodninger, en session sender. `event.kind` angiver, hvilket forløb der sendte den:
`"primary"` for agentløkken, `"compaction"` for checkpoint-resuméer, `"title"` for generering af titler og `"generate"`
for midlertidige `ctx.session.generate`-kald. Brug den i stedet for agent-ID'et til at skelne hjælpeanmodninger fra
hinanden.

```ts
await ctx.session.hook("http.request", (event) => {
  event.request.headers.set("x-session-id", event.sessionID)
  if (event.kind === "title") event.request.headers.set("x-priority", "background")
})

await ctx.session.hook("http.response", (event) => {
  event.response = new Response(event.response.body, {
    status: event.response.status,
    headers: { ...Object.fromEntries(event.response.headers), "x-plugin": "review" },
  })
})
```

#### Native WebSocket (eksperimentel)

Udbydere, der streamer over en WebSocket, åbner én forbindelse pr. session og genbruger den på tværs af anmodninger, så
`http.request` og `http.response` ser aldrig den trafik. Hooken `experimental.ws.handshake` kører én gang pr. modelkald,
før forbindelsen vælges. Den har de samme `sessionID`, `agent`, `model` og `kind` som HTTP-hooks plus forbindelsens
`url` og `headers`. Ændringer af `url` eller `headers` afgør, hvilken socket anmodningen bruger, så et roteret
bearer-token åbner forbindelsen igen.

HTTP-hooks kører stadig for alle HTTP-anmodninger, også den anmodning, en WebSocket-rute falder tilbage til.

```ts
await ctx.session.hook(
  "experimental.ws.handshake",
  async (event) => {
    event.headers.authorization = `Bearer ${await mintToken(event.url)}`
    delete event.headers["api-key"]
  },
  { providerID: "azure" },
)
```

`experimental.ws.send` og `experimental.ws.receive` udstiller selve rammerne, WebSocket-modstykket til at redigere
bodyen i en HTTP-anmodning eller et HTTP-svar. `send` kører, efter at udbyderdriveren har bygget en udgående ramme, og
før den skrives; `receive` kører på hver indgående ramme, før driveren ser den. Begge har rammen som en streng og sender
det, `frame` indeholder, når hooken returnerer.

OpenCode validerer ikke omskrevne rammer. Driveren holder styr på tilstanden ud fra udbyderens svar, så en omskrivning,
der ændrer protokollens betydning, er pluginnets ansvar, ligesom ved en omskrevet HTTP-body.

```ts
await ctx.session.hook(
  "experimental.ws.send",
  (event) => {
    const body = JSON.parse(event.frame)
    if (body.type === "response.create") body.metadata = { ...body.metadata, session: event.sessionID }
    event.frame = JSON.stringify(body)
  },
  { providerID: "openai" },
)

await ctx.session.hook("experimental.ws.receive", (event) => {
  if (event.frame.includes('"type":"error"')) console.error(event.frame)
})
```

Disse hooks er eksperimentelle, og deres navne eller former kan ændre sig.

#### Politik for nye forsøg

Tilsidesæt beslutningen om nye forsøg ved en udbyderfejl, eller erstat forsinkelsen i millisekunder. Hooken kører, efter
at OpenCode har klassificeret fejlen og foreslået sin politik, men før et nyt forsøg planlægges. Den viser ikke, hvordan
OpenCode internt udfører det næste forsøg.

```ts
await ctx.session.hook("retry", (event) => {
  if (event.error.status === 429) {
    event.decision = { retry: true, delay: 10_000 }
    return
  }
  if (event.error.type === "provider.invalid-request" && event.attempt === 2) {
    event.decision = { retry: true, delay: 0 }
    return
  }
  if (event.attempt >= 3) event.decision = { retry: false }
})
```

Retry-hooks kan ændre OpenCodes oprindelige `decision` ved at gøre en endelig fejl
til en, der kan forsøges igen, eller ved at afvise et foreslået nyt forsøg.

Beslutninger om nye forsøg følger disse regler:

- Flere hooks kører i registreringsrækkefølge, og senere hooks ser den aktuelle beslutning.
- Det indbyggede maksimale antal forsøg er stadig en fast grænse.
- `attempt` er det fysiske forsøg, der overvejes. Den første anmodning er `1`, så det første nye forsøg er `2`.
- Ugyldige forsinkelser som `NaN`, uendelig eller negative værdier falder tilbage til den beregnede forsinkelse.
- Genopretning efter kontekstoverløb er adskilt, fordi den komprimerer samtalen i stedet for at gentage samme anmodning.

### Tilladelser

Gennemgå tilladelsesbeslutninger, efter at de konfigurerede regler er evalueret, og før
en handling kører, eller en tilladelsesprompt publiceres.

```ts
await ctx.permission.hook("evaluate", async (event) => {
  if (event.action === "read") return

  const messages = await ctx.session.context({ sessionID: event.sessionID })
  const review = await ctx.generate.text({
    model: { providerID: "anthropic", id: "claude-sonnet-4-6" },
    prompt: buildSafetyPrompt({ messages, action: event.action, resources: event.resources }),
  })
  const decision = parseDecision(review.text)

  event.effect = decision.effect
  event.message = decision.reason
})
```

Tilladelseshooks følger disse regler:

- Hooks kører for beslutningerne `allow` og `ask`.
- Et eksplicit konfigureret `deny` er endeligt og kalder ikke hooken.
- En hook kan ændre `effect` til `allow`, `ask` eller `deny`.
- `message` vises i en eskaleret tilladelsesanmodning eller bliver begrundelsen for afvisningen.

## Publicer

Et pakkeplugin bruger den samme default-eksport som et lokalt plugin. Et minimalt
manifest ser sådan ud:

```json title="package.json"
{
  "name": "opencode-acme-plugin",
  "version": "1.0.0",
  "type": "module",
  "exports": {
    ".": "./src/index.ts",
    "./rpc": "./src/rpc.ts"
  },
  "dependencies": {
    "@opencode/plugin": "latest"
  }
}
```

Eksporten `./rpc` er valgfri; medtag den, når du publicerer en fælles
[RPC-kontrakt](/build/plugins/rpc), som andre plugins og klienter kan importere
uden at indlæse din implementering.

Brug versioner, der er kompatible med den OpenCode-udgivelse, du er rettet mod, og test den
installerede pakke, ikke kun en kopi, der er linket i arbejdsområdet. Publicer en kompatibel
pluginopdatering, når du tager en nyere API-kontrakt i brug.

## Understøt V1

Et plugin kan understøtte V1 og V2 fra samme indgangspunkt i pakken. Lav en default-eksport
af ét objekt med en V1-funktion `server()` og en V2-funktion `setup()`:

```ts title="src/index.ts"
import { Plugin } from "@opencode/plugin"

export default {
  ...Plugin.define({
    id: "example",
    async setup(ctx) {
      await ctx.tool.hook("execute.before", () => {
        console.log("A tool is about to run")
      })
    },
  }),
  async server() {
    return {
      "tool.execute.before": async () => {
        console.log("A tool is about to run")
      },
    }
  },
}
```

- V1 kalder `server()` og bruger de returnerede hooks.
- V2 læser default-eksportens `id` og `setup()` (eller `effect()` for Effect-plugins) og ignorerer `server()`.
- Hold hver implementering på sit eget API; en fælles eksport oversætter ikke V1-hooks til V2-hooks.
- Spred `Plugin.define(...)` ind i det eksporterede objekt, så V2-definitionen typetjekkes separat fra `server()`.

Objektformen i V1 understøttes i OpenCode `1.18.29`. Ældre V1-udgivelser kan
forvente funktionseksporter i stedet; test den installerede pakke med den ældste V1-udgivelse,
du vil understøtte, og med V2.
