---
title: 故障排除
---

<Callout type="tip">
  你可以让 OpenCode 自己调试自己。描述问题，并让它参考本故障排除页面；它可以阅读下面的步骤，检查自身的服务和日志，帮你找出问题所在。
</Callout>

OpenCode 采用客户端-服务器架构。会话、插件、权限以及其他应用状态都由一个后台服务器管理。排查问题时，先判断问题出在客户端、共享服务器，还是某个特定项目。

## 检查后台服务

查看当前服务器信息：

```bash
opencode service status
```

确认其 API 运行正常：

```bash
opencode api get /api/info
```

如果服务卡住或状态异常，请重启它：

```bash
opencode service restart
```

也可以显式地停止再启动：

```bash
opencode service stop
opencode service start
```

<Callout type="note">
  OpenCode 通常会自动发现或启动共享的后台服务。只有在诊断服务的生命周期问题时，才需要用到这些 service 命令。
</Callout>

## 允许浏览器来源

如果其他来源的浏览器客户端因为 CORS 无法连接，请将该客户端的来源添加到服务配置中：

```bash
opencode service set cors http://192.168.1.10:3001
opencode service get cors
```

请使用精确的 HTTP 或 HTTPS 来源，必要时带上端口，不要包含路径或末尾斜杠。如需允许多个来源，请将它们用逗号分隔后作为一个参数传入，每个来源两侧的空白会被自动去除：

```bash
opencode service set cors "http://192.168.1.10:3001, https://app.example.com"
```

`service get cors` 会输出一个 JSON 数组。使用以下命令删除已配置的列表：

```bash
opencode service unset cors
```

设置或取消设置服务配置都会停止后台服务。服务下次启动时会应用新配置；也可以用 `opencode service start` 显式启动它。

对于前台服务器，每多允许一个来源，就重复传入一次 `--cors`：

```bash
opencode serve --cors http://192.168.1.10:3001 --cors https://app.example.com
```

使用 `serve --service` 时，传入的 `--cors` 参数会覆盖该进程的已保存列表；不传这些参数时，服务模式会使用已保存的列表。CORS 不会改变监听地址，也不会绕过服务器身份验证。

## 检查 API

`api` 命令会使用本地的服务发现和身份验证流程。它既可以接受 HTTP 方法加路径，也可以接受 OpenAPI 操作 ID。

所有端点和操作 ID 请参阅 [API 参考](/api)。

使用 `--data` 或 `-d` 传入 JSON 请求体，使用 `--header` 或 `-H` 添加请求头。

<Callout type="warning">
  如果当前没有可用的兼容且健康的服务，运行 `opencode api` 可能会启动后台服务。
</Callout>

## 查看日志

正式安装的版本会将日志写入：

```text
~/.local/share/opencode/log/opencode.log
```

复现问题时实时跟踪日志：

```bash
tail -f ~/.local/share/opencode/log/opencode.log
```

每一行都包含进程的 `run` ID 和 `role` 字段。会话、提供商、插件、权限和工具相关的活动，请筛选 `role=server`。

```bash
grep 'role=server' ~/.local/share/opencode/log/opencode.log
grep 'run=8fc3b1d5' ~/.local/share/opencode/log/opencode.log
```

## 采集 CPU 和内存分析数据

在 macOS 和 Linux 上，你可以向正在运行的 OpenCode 进程发送信号来采集诊断数据。先通过健康检查端点获取后台服务器的 PID：

```bash
opencode api get /api/info
```

使用响应中的 `pid`，发送以下信号之一：

- `SIGPROF` 会采集 10 秒的 CPU 性能分析数据：

  ```bash
  kill -SIGPROF <pid>
  ```

  结果会以 `cpu-<pid>-<timestamp>.cpuprofile` 的文件名写入日志目录。

- `SIGUSR1` 会采集内存（堆）快照：

  ```bash
  kill -SIGUSR1 <pid>
  ```

  结果会以 `heap-<pid>-<timestamp>.heapsnapshot` 的文件名写入日志目录。

打开文件之前，请等待 `opencode.log` 中出现 `CPU profile written` 或 `heap snapshot written`，对应的日志条目中包含文件的完整路径。这两种文件都可以在 Chrome DevTools 中查看。

<Callout type="note">
  Windows 不支持通过信号触发的性能分析。写入堆快照可能会让进程暂停，并暂时增加其内存占用。
</Callout>

## 服务文件

共享服务器会在以下位置注册自身：

```text
~/.local/state/opencode/service.json
```

其私有服务配置单独存放在：

```text
~/.config/opencode/service.json
```

数据库通常位于：

```text
~/.local/share/opencode/opencode.db
```

可以用 `OPENCODE_DB` 覆盖数据库位置。

<Callout type="warning">
  排查问题时，不要删除或编辑服务文件和数据库。请使用 service 命令管理守护进程；如需用外部工具检查持久化数据，请先做好备份。
</Callout>

## 反馈问题

反馈可复现的问题时，请附上以下信息：

- `opencode --version` 的输出
- `opencode service status` 的输出
- 能复现问题的最少操作步骤
- 问题影响的是共享服务、某个特定客户端，还是某个项目
- 相关的日志行，包括其中的 `run` 和 `role` 字段

分享日志之前，请删除 API 密钥、授权请求头、提示词、文件内容以及其他敏感数据。

请在 [GitHub Issues](https://github.com/anomalyco/opencode/issues) 中提交可复现的问题。
