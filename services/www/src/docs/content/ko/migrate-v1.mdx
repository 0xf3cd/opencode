title: "V1에서 마이그레이션"
---

OpenCode 1과 OpenCode 2는 모두 `opencode` 명령을 사용하며, 이제 기본적으로 나란히 설치되지 않습니다. V2를 설치하기 전에
패키지 관리자로 설치한 V1을 제거하세요. V2 curl 설치 프로그램은 V1 바이너리를 대체합니다.

## 호환성이 깨지는 변경 사항

V2에는 의도적으로 호환성을 깨뜨린 변경 사항이 세 가지 있습니다.

- [플러그인](/build/plugins/migrate-v1)은 새로운 플러그인 API를 사용합니다.
- [서버 API와 클라이언트](#server-api-and-clients)의 계약이 새로워졌습니다.
- [터미널 클라이언트 구성](/cli/config)이 여러 계층의 `tui.json(c)` 파일에서 하나의 전역 `cli.json` 파일로
  바뀝니다(자동 마이그레이션).

이 영역 외에 지원되는 V1 기능은 V1과 호환되도록 유지하는 것이 목표입니다. V1 스키마에서 허용했지만 V2에 대응하는 기능이
없는 일부 필드는 의도적으로 무시되며, [허용되지만 지원되지 않는 필드](#accepted-but-unsupported-fields)에 정리되어
있습니다.

기존에 지원되던 서버 구성 필드, 에이전트 정의, 명령 정의, 스킬, `.opencode/`의 기타 파일은 변경 없이 계속 동작해야
합니다. 이 가이드에서 지원한다고 설명한 동작이 V2에서 작동하지 않는다면, 예상된 마이그레이션 요구 사항이 아니라 호환성
버그로 간주하세요.

<Callout type="tip">
  지원되는 V1 기능이 V2에서 작동하지 않으면 [문제 해결](/troubleshooting)의 이슈 보고 안내에 따라 호환성 이슈를
  등록하세요.
</Callout>

## V2 설치

[터미널 시작 가이드](/cli)에 따라 V2 터미널 클라이언트를 설치하세요.

V2를 시작하기 전에 모든 것을 다시 작성할 필요는 없습니다. 현실적인 마이그레이션 순서는 다음과 같습니다.

1. 기존 구성과 파일 기반 정의를 그대로 둡니다.
2. V2를 시작하고 모델, 자격 증명, 에이전트, 권한, MCP 서버를 확인합니다.
3. V1 플러그인 구현은 V2에서 실행되지 않으므로 플러그인을 포팅합니다.
4. 서버 API를 호출하는 통합을 포팅합니다.
5. 준비가 되면 구성을 네이티브 V2 형식으로 변환합니다. 이 단계는 선택 사항입니다.

마이그레이션을 검증하는 동안 V1 설정의 사본을 보관하세요. V1과 V2는 같은 구성 위치를 사용하므로, V2 전용 네이티브 형식으로
변환한 파일을 V1에서 사용하지 마세요.

## 구성

이 섹션에서는 JSON/JSONC 구성과 `.opencode/` 아래의 파일 기반 정의를 모두 다룹니다.

### 기존 구성 사용

V2는 기존 시스템, 전역, 프로젝트 구성을 V1과 같은 위치에서 읽습니다.

```text
/Library/Application Support/opencode/opencode.json(c)
/etc/opencode/opencode.json(c)
%ProgramData%\opencode\opencode.json(c)
/Library/Managed Preferences/<user>/ai.opencode.managed.plist
/Library/Managed Preferences/ai.opencode.managed.plist
~/.config/opencode/opencode.json(c)
<project>/opencode.json(c)
<project>/.opencode/opencode.json(c)
```

V2는 원본 파일을 다시 쓰지 않고, 지원되는 V1 필드와 네이티브 V2 필드를 메모리에서 정규화합니다. 지원되는 기존 V1 구성은
계속 동작하도록 설계되었으므로, V2를 사용해 보거나 도입하기 위해 구성을 변환할 필요는 없습니다.

V1과 마찬가지로 시스템 구성과 macOS 관리형 환경설정은 우선순위가 가장 높아 전역 파일과 프로젝트 파일의 설정을
재정의합니다. 마이그레이션된 `enabled_providers`와 `disabled_providers`를 포함한 이들의 [정책](/policies#precedence)도
전역 정책과 프로젝트 정책보다 우선합니다. 설정을 재정의하는 것만으로는 사용자가 제공자, MCP 서버, 에이전트, 플러그인을
추가하는 것을 막을 수 없으므로, 관리자가 강제하는 제한은 `permissions` 같은 일반 설정이 아니라 `policies`로 표현하세요.

### OpenCode에 마이그레이션 요청

V1 구성 형식은 계속 지원됩니다. 네이티브 V2 형식은 선택 사항이며, 여러 설정을 더 명시적이고 사용하기 편하게 만들어
줍니다.

권장하는 마이그레이션 방법은 OpenCode에 구성 업데이트를 요청하는 것입니다.

```text
Migrate my OpenCode configuration, including file-based definitions, from the V1 format to the native V2 format.
Preserve its behavior and all unrelated settings.
```

OpenCode는 파일 전체를 살펴보고 아래의 관련 변경 사항을 적용하며, 바꿀 필요가 없는 설정은 다시 쓰지 않습니다. 변환을 한
번에 끝낼 필요는 없습니다. 지원되는 V1 필드와 네이티브 V2 필드는 최상위 수준에서 함께 사용할 수 있습니다. 두 형식이 같은
정식 값을 설정하면 JSON 키 순서와 관계없이 유효한 네이티브 V2 값이 우선 적용됩니다.

중첩된 수준에서 형식을 섞는 것은 의도적으로 제한됩니다. OpenCode는 `mcp`, `compaction`, `experimental` 안에서는 V1과 V2
멤버가 섞여 있어도 인식하지만, 개별 에이전트, 제공자, 명령, 모델 안에서는 형식을 재귀적으로 추론하지 않습니다. 이러한
중첩 항목은 각각 하나의 형식으로만 작성하세요. 지원되는 V1 구문만으로는 경고가 표시되지 않지만, 잘못된 값, 지원되지
않는 레거시 필드, 서로 충돌하는 V1/V2 값은 경고를 표시하며, 관련 없는 유효한 설정은 계속 로드됩니다.

### 공유

지원 중단된 V1 `autoshare` 불리언은 명시적인 `share` 정책으로 바뀝니다.

```jsonc
// V1
{ "autoshare": true }

// V2
{ "share": "auto" }
```

`"manual"`, `"auto"`, `"disabled"` 중 하나를 사용하세요. V1 파일에서 이미 `share`를 사용하고 있다면 변경할 필요가
없습니다.

### 권한과 도구

V1은 권한 효과를 도구별로 묶습니다. V2는 순서가 있는 하나의 `permissions` 배열을 사용하므로 우선순위와 예외가
명확해집니다.

```jsonc
// V1
{
  "permission": {
    "bash": {
      "git push *": "ask"
    },
    "edit": "allow"
  },
  "tools": {
    "websearch": false
  }
}

// V2
{
  "permissions": [
    { "action": "shell", "resource": "git push *", "effect": "ask" },
    { "action": "edit", "resource": "*", "effect": "allow" },
    { "action": "websearch", "resource": "*", "effect": "deny" }
  ]
}
```

권한 작업 이름도 바뀌었습니다. `bash`는 `shell`, `task`는 `subagent`가 되었고, `write`와 `patch`는 `edit`이
되었습니다. 순서가 있는 V2 규칙 형식은 [권한](/permissions)을 참고하세요.

### 에이전트와 모드

단수형 `agent` 맵과 지원 중단된 `mode` 맵은 `agents`가 됩니다. 에이전트 필드는 V2 구성의 다른 부분과 더 일관된 형태로
바뀝니다.

```jsonc
// V1
{
  "agent": {
    "reviewer": {
      "prompt": "Review for correctness and missing tests.",
      "model": "anthropic/claude-sonnet-4-5",
      "variant": "high",
      "disable": false,
      "permission": {
        "edit": "deny"
      }
    }
  }
}

// V2
{
  "agents": {
    "reviewer": {
      "system": "Review for correctness and missing tests.",
      "model": "anthropic/claude-sonnet-4-5#high",
      "disabled": false,
      "permissions": [
        { "action": "edit", "resource": "*", "effect": "deny" }
      ]
    }
  }
}
```

`prompt`는 `system`, `disable`은 `disabled`가 되며, 별도의 `variant`는 `#` 뒤에 붙어 모델 참조에 합쳐집니다.
`temperature`, `top_p`, 제공자별 `options`는 `request.body` 아래로 이동합니다. `maxSteps`는 `steps`가 됩니다. 기존
`mode` 맵의 항목은 주 에이전트(primary agent)가 됩니다.

### 스냅샷

단수형 `snapshot` 필드의 이름을 `snapshots`로 바꾸세요. 불리언 값은 그대로입니다.

```jsonc
// V1
{ "snapshot": false }

// V2
{ "snapshots": false }
```

### 미디어

단수형 `attachment` 객체의 이름을 `media`로 바꾸세요. 중첩된 이미지 설정의 이름은 그대로입니다.

```jsonc
// V1
{ "attachment": { "image": { "auto_resize": true } } }

// V2
{ "media": { "image": { "auto_resize": true } } }
```

### MCP 서버

V2는 서버를 `mcp.servers` 아래에 묶고, `enabled`를 반대 의미의 `disabled`로 바꾸며, 타임아웃을 용도별로 나눕니다.

```jsonc
// V1
{
  "mcp": {
    "playwright": {
      "type": "local",
      "command": ["npx", "@playwright/mcp"],
      "enabled": true,
      "timeout": 30000
    }
  }
}

// V2
{
  "mcp": {
    "servers": {
      "playwright": {
        "type": "local",
        "command": ["npx", "@playwright/mcp"],
        "disabled": false,
        "timeout": {
          "catalog": 30000,
          "execution": 30000
        }
      }
    }
  }
}
```

원격 OAuth 필드는 스네이크 케이스를 사용합니다. `clientId`는 `client_id`, `clientSecret`은 `client_secret`,
`callbackPort`는 `callback_port`, `redirectUri`는 `redirect_uri`가 됩니다. V1의 `experimental.mcp_timeout` 값은
`mcp.timeout.catalog`와 `mcp.timeout.execution`의 기본값이 됩니다. [MCP 서버](/mcp-servers)를 참고하세요.

### 컨텍스트 압축

V2는 유지할 컨텍스트의 토큰 예산을 `keep` 아래에 묶고, 예약 공간에 더 명확한 이름을 붙입니다.

```jsonc
// V1
{
  "compaction": {
    "preserve_recent_tokens": 8000,
    "reserved": 20000
  }
}

// V2
{
  "compaction": {
    "keep": {
      "tokens": 8000
    },
    "buffer": 20000
  }
}
```

`auto`는 이름이 그대로입니다. V2에는 네이티브 `tail_turns`나 `prune` 필드가 없으며, 두 레거시 필드는 경고와 함께
무시됩니다. 대신 최근 컨텍스트는 토큰 예산을 기준으로 유지됩니다. [컨텍스트 압축](/compaction)을 참고하세요.

### 스킬

V1은 추가 스킬 경로와 URL을 따로 지정합니다. V2는 둘을 순서가 있는 하나의 배열로 합칩니다.

```jsonc
// V1
{
  "skills": {
    "paths": ["./team-skills"],
    "urls": ["https://example.com/skills/"]
  }
}

// V2
{
  "skills": ["./team-skills", "https://example.com/skills/"]
}
```

기존 스킬 파일과 `.opencode/skills/` 자동 탐색은 바뀌지 않습니다. [스킬](/skills)을 참고하세요.

### 명령

단수형 `command` 맵의 이름을 `commands`로, `subtask`를 `subagent`로 바꾸세요. 별도의 모델 `variant`는 모델 참조에
합칩니다.

```jsonc
// V1
{
  "command": {
    "review": {
      "template": "Review the current changes.",
      "model": "anthropic/claude-sonnet-4-5",
      "variant": "high",
      "subtask": true
    }
  }
}

// V2
{
  "commands": {
    "review": {
      "template": "Review the current changes.",
      "model": "anthropic/claude-sonnet-4-5#high",
      "subagent": true
    }
  }
}
```

`template`, `description`, `agent`는 이름이 그대로입니다. 레거시 `subtask`도 계속 허용됩니다. 위임된 명령은 이제
백그라운드에서 자동으로 실행되고 결과를 상위 세션에 보고합니다. 기존 Markdown 명령 정의도 계속 지원됩니다.
[명령](/commands)을 참고하세요.

### 디렉터리 참조

지원 중단된 단수형 `reference` 맵의 이름을 `references`로 바꾸세요.

```jsonc
// V1
{ "reference": { "docs": "../docs" } }

// V2
{ "references": { "docs": "../docs" } }
```

V1도 이미 `references`를 허용하므로, 파일에서 이를 사용하고 있다면 변경할 필요가 없습니다. 참조 항목의 형식은
그대로입니다. [디렉터리 참조](/references)를 참고하세요.

### 제공자

단수형 `provider` 맵의 이름을 `providers`로 바꾸세요. V2는 런타임 패키지, 엔드포인트, 요청 설정을 분리합니다.

```jsonc
// V1
{
  "provider": {
    "acme": {
      "npm": "@ai-sdk/openai-compatible",
      "api": "https://llm.example.com/v1",
      "options": {
        "apiKey": "{env:ACME_API_KEY}"
      }
    }
  }
}

// V2
{
  "providers": {
    "acme": {
      "package": "aisdk:@ai-sdk/openai-compatible",
      "settings": {
        "baseURL": "https://llm.example.com/v1",
        "apiKey": "{env:ACME_API_KEY}"
      }
    }
  }
}
```

V1의 `npm`은 `package`가 되며, AI SDK 패키지에는 `aisdk:` 접두사가 붙습니다. `api`는 `settings.baseURL`이 됩니다.
제공자 `options`는 요청에서의 역할에 따라 `settings`, `headers`, `body`로 나뉩니다. `options.setCacheKey`는 제공자의
`compatibility.supportsPromptCacheKey`가 됩니다. [제공자](/providers)를 참고하세요.

V2는 두 가지 레거시 제공자 네임스페이스를 통합했습니다.

| V1 제공자 ID               | 정식 V2 제공자 ID        |
| -------------------------- | ------------------------ |
| `azure-cognitive-services` | `azure`                  |
| `google-vertex-anthropic`  | `google-vertex`          |

모호하지 않은 V1 제공자, 에이전트, 명령, 제공자 필터 필드를 마이그레이션할 때는 이 정식 ID를 사용합니다. 공통 최상위
`model` 필드는 같은 구문이 네이티브 V2 구성에서도 유효하기 때문에 제공자 ID를 그대로 유지합니다. 레거시 기본 제공
제공자를 마이그레이션할 때는 이 필드를 정식 ID로 직접 업데이트하세요.

### 모델과 변형

모델은 여전히 제공자 아래에 중첩되지만, 몇몇 모델 필드가 더 명시적으로 바뀝니다.

- `id`는 `modelID`가 됩니다.
- `tool_call`과 `modalities`는 `capabilities.tools`, `capabilities.input`, `capabilities.output`이 됩니다.
- `status`가 `"deprecated"`이면 `disabled: true`가 됩니다.
- 캐시 비용은 `cache_read`, `cache_write`에서 `cache.read`, `cache.write`로 이동합니다.
- 제공자별 `options`는 `settings`가 됩니다.
- V1의 variants 객체는 각 항목에 `id`가 있는 V2 배열이 됩니다.

```jsonc
// V1
{
  "variants": {
    "high": {
      "reasoningEffort": "high"
    }
  }
}

// V2
{
  "variants": [
    {
      "id": "high",
      "settings": {
        "reasoningEffort": "high"
      }
    }
  ]
}
```

네이티브 모델 형식 전체는 [모델](/models)을 참고하세요.

### 네이티브로 직접 대응하는 필드가 없는 지원 필드

`shell`, `model`, `default_agent`, `watcher`, `formatter`, `instructions`, `enterprise`, `tool_output`처럼 형식이
그대로인 대부분의 필드는 마이그레이션이 필요하지 않습니다.

V2는 `lsp` 구성을 허용하고 보존하지만, 언어 서버를 실행하거나 LSP 도구를 제공하거나 LSP 진단을 생성하지는 않습니다.
이러한 기능에 의존하는 워크플로는 프로젝트의 린트, 타입 검사, 컴파일러 명령으로 대체하세요.

V1 제공자 필터에는 일대일로 대응하는 네이티브 V2 구성 필드가 없지만, 동작은 [정책](/policies)을 통해 계속 지원됩니다.

- `enabled_providers`는 기본적으로 모든 제공자를 거부한 다음 나열된 제공자를 허용하는 내부 제공자 정책이 됩니다.
- `disabled_providers`는 나열된 제공자를 거부하는 내부 정책이 됩니다.
- `autoupdate`는 `update`가 됩니다. `false`는 `"disable"`, `"notify"`는 `"notify"`, `true`는 `"auto"`에 대응합니다.
- `small_model`은 기본 제공 `title` 에이전트의 `model` 선택이 됩니다. 네이티브 V2 구성에서는 대신
  `agents.title.model`을 사용하세요.

이 필드들은 V1 구문으로 그대로 두어도 됩니다. OpenCode가 경고 없이 정규화합니다.

### 허용되지만 지원되지 않는 필드

V1 스키마는 V2에서 지원하는 동작이 없는 필드도 허용했습니다. V2는 이러한 값을 무시하고, 활성 구성으로 오해하지 않도록
경고를 표시합니다.

- `logLevel`: OpenCode를 시작할 때 `OPENCODE_LOG_LEVEL`을 사용하세요.
- `server`: V2 서비스와 명시적인 서버 옵션을 사용하세요. 서버 API는 의도적으로 호환성을 깨뜨린 변경 사항입니다.
- 최상위 `subagent_depth`: 대신 `experimental.subagent_depth`를 사용하세요.
- `compaction.tail_turns`와 `compaction.prune`: V2는 대신 `compaction.keep.tokens`와 체크포인트 기반 압축을
  사용합니다.
- V1 JSON 구성 안의 에이전트 `name`.
- `type` 없이 enabled만 지정한 V1 MCP 항목.
- V1 실험적 필드 `batch_tool`, `openTelemetry`, `primary_tools`, `continue_loop_on_deny`.
- V1 제공자 필드 `id`, `whitelist`, `blacklist`.
- V1 제공자 모델 필드 `release_date`, `attachment`, `reasoning`, `temperature`, `experimental`, `deprecated`가 아닌
  `status`, 불리언 `interleaved`.

이 필드를 무시하는 것은 의도된 동작이며 호환성 회귀가 아닙니다. 이 가이드의 다른 부분에서 지원한다고 명시한 동작이
V2에서 유지되지 않는다면 [문제 해결](/troubleshooting)의 이슈 보고 안내를 따르세요.

### 에이전트 파일

V1 에이전트 파일은 `agent/`, `agents/`, `mode/`, `modes/`를 사용할 수 있습니다. V2도 네 디렉터리를 모두 탐색합니다. V2에서
권장하는 위치는 다음과 같습니다.

```text
.opencode/agents/<name>.md
```

V1의 `mode/` 또는 `modes/` 디렉터리 아래 파일은 주 에이전트를 나타냅니다. 이러한 파일을 `agents/`로 옮길 때는
프런트매터에 `mode: primary`를 추가하세요. `agent/` 아래 파일은 경로에서 파생된 ID를 바꾸지 않고 `agents/`로 옮길 수
있습니다.

프런트매터를 네이티브 V2 필드로 변환할 때는 다음을 따르세요.

- Markdown 본문은 에이전트의 시스템 지침으로 유지합니다.
- JSON 구성에 `prompt`가 있으면 `system`으로 이름을 바꿉니다. 파일 본문에는 `system` 필드가 필요하지 않습니다.
- `disable`은 `disabled`로, `permission`은 `permissions`로 이름을 바꿉니다.
- `model`과 `variant`를 `provider/model#variant` 형태로 합칩니다.
- `temperature`, `top_p`, 제공자별 옵션을 `request.body` 아래로 옮깁니다.

V2는 레거시 에이전트 프런트매터를 자동으로 변환하므로 이러한 수정은 선택 사항입니다. [에이전트](/agents)를 참고하세요.

### 명령 파일

V1 명령 파일은 `command/` 또는 `commands/`를 사용할 수 있습니다. V2는 둘 다 탐색합니다. 권장 위치는 다음과 같습니다.

```text
.opencode/commands/<name>.md
```

명령 이름을 유지하려면 `command/`의 파일을 `commands/` 아래 같은 상대 경로로 옮기세요. Markdown 본문은 그대로 명령
템플릿이 되고, 프런트매터의 `description`과 `agent`도 이름이 그대로입니다. 백그라운드 위임의 네이티브 이름을 사용하려면
`subtask`를 `subagent`로 바꾸세요. 프런트매터에 `model`과 `variant` 필드가 따로 있다면 변형을 모델 뒤에 붙이고
`variant`를 제거하세요.

```yaml
# V1
model: anthropic/claude-sonnet-4-5
variant: high
subtask: true

# V2
model: anthropic/claude-sonnet-4-5#high
subagent: true
```

[명령](/commands)을 참고하세요.

### 스킬 파일

V2는 `.opencode/skill/`과 `.opencode/skills/` 모두에서 스킬을 탐색합니다. 권장 구조는 다음과 같습니다.

```text
.opencode/skills/<skill-id>/SKILL.md
```

상대 경로로 참조하는 스크립트, 참고 자료, 기타 보조 파일을 계속 사용할 수 있도록 `SKILL.md`만이 아니라 스킬 디렉터리
전체를 옮기세요. 스킬 ID를 유지하려면 디렉터리 이름을 바꾸지 마세요. 기존 스킬 프런트매터와 Markdown 본문은 V2용으로 다시
작성할 필요가 없습니다. [스킬](/skills)을 참고하세요.

### 지침 파일

기존 `AGENTS.md` 파일은 그대로 둡니다. V2는 전역 `~/.config/opencode/AGENTS.md`와, 현재 디렉터리부터 홈 디렉터리까지의
주변 `AGENTS.md` 파일을 탐색합니다. 홈 디렉터리 밖에 있는 프로젝트는 프로젝트 루트에서 탐색을 멈춥니다.

V1 설정에서 `CLAUDE.md` 폴백에 의존했다면 해당 지침을 적절한 `AGENTS.md`로 옮기세요. V2는 현재 `AGENTS.md`만
탐색합니다. API 외의 V1 동작은 호환성을 유지하는 것이 목표이므로, 영향을 받는 프로젝트 정보와 함께 호환성 이슈도
등록하세요. [지침](/instructions)을 참고하세요.

## 터미널 클라이언트 구성

V2는 여러 계층으로 된 V1 `tui.json(c)` 파일을 하나의 전역 터미널 클라이언트 구성 파일로 대체합니다.

```text
~/.config/opencode/cli.json
```

이 파일은 터미널 클라이언트가 관리하며, 백그라운드 서비스는 이 파일을 로드하지 않습니다. `cli.json`이 없으면 V2 터미널
클라이언트를 처음 시작할 때 지원되는 전역 `tui.json` 설정과 저장된 환경설정을 마이그레이션하며, V1 파일은 변경하지
않습니다. V2 클라이언트 구성은 전역이므로 프로젝트 로컬 클라이언트 구성은 마이그레이션되지 않습니다. 현재 클라이언트 설정
레퍼런스는 [CLI 설정](/cli/config)을 참고하세요.

## 플러그인

`plugin`의 이름을 `plugins`로 바꾸세요. 패키지와 옵션으로 이루어진 튜플은 객체로 바꿉니다.

```jsonc
// V1
{
  "plugin": ["opencode-example-plugin", ["./plugin/local.ts", { "enabled": true }]]
}

// V2
{
  "plugins": [
    "opencode-example-plugin",
    {
      "package": "./plugin/local.ts",
      "options": { "enabled": true }
    }
  ]
}
```

V2는 `.opencode/plugin/`과 `.opencode/plugins/` 모두에서 로컬 플러그인을 탐색합니다. V2 파일에는 `.opencode/plugins/`를
사용하세요.

<Callout type="warning">
  V1 플러그인 구현은 V2에서 실행되지 않습니다. 파일을 옮기거나 구성 항목 이름을 바꾸는 것만으로는 충분하지 않습니다.
</Callout>

진입점, 훅, 도구, 이벤트, 패키지 내보내기는 전용 [플러그인 마이그레이션 가이드](/build/plugins/migrate-v1)에 따라
포팅하세요.

## 서버 API와 클라이언트

OpenCode 2는 더 사용하기 편하게 개선된 서버 API와 새로운 클라이언트 세트를 제공합니다. V1 서버 API를 호출하는 통합은
V2 API로 마이그레이션해야 합니다.

릴리스된 V2 API에 접근하려면 `@opencode/client` 패키지를 사용하세요. 엔드포인트, 요청 유형, 응답은 생성된
[API 레퍼런스](/api)를 참고하세요.

## 설정 확인

일상적인 작업에 V2를 사용하기 전에 프로젝트에서 모델, 제공자 자격 증명, 에이전트, 권한, MCP 서버, 플러그인을
확인하세요. 필요한 V2 동작을 확인할 때까지 V1 설정을 보관하고, 네이티브 V2 형식으로 변환한 구성을 V1에서 사용하지
마세요.
