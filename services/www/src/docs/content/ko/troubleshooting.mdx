<Callout type="tip">
  OpenCode에게 스스로 디버깅하도록 요청할 수 있습니다. 문제를 설명하고 이 문제 해결 페이지를 활용하라고 요청하면, 아래
  단계를 읽고 서비스와 로그를 살펴보며 문제를 찾는 데 도움을 줍니다.
</Callout>

OpenCode는 클라이언트-서버 아키텍처를 사용합니다. 백그라운드 서버가 세션, 플러그인, 권한, 기타 애플리케이션 상태를
관리합니다. 먼저 문제가 클라이언트, 공유 서버, 특정 프로젝트 중 어디에 있는지 파악하세요.

## 백그라운드 서비스 확인

현재 서버 정보를 표시합니다.

```bash
opencode service status
```

API가 정상인지 확인합니다.

```bash
opencode api get /api/info
```

서비스가 멈췄거나 비정상이면 다시 시작하세요.

```bash
opencode service restart
```

명시적으로 중지했다가 시작할 수도 있습니다.

```bash
opencode service stop
opencode service start
```

<Callout type="note">
  OpenCode는 보통 공유 백그라운드 서비스를 자동으로 찾거나 시작합니다. 서비스 명령은 서비스의 수명 주기를 진단할 때만
  필요합니다.
</Callout>

## 브라우저 출처 허용

다른 출처(origin)의 브라우저 클라이언트가 CORS 때문에 연결되지 않는다면, 클라이언트의 출처를 서비스 구성에 추가하세요.

```bash
opencode service set cors http://192.168.1.10:3001
opencode service get cors
```

경로나 후행 슬래시 없이 정확한 HTTP 또는 HTTPS 출처를 사용하고, 필요하면 포트도 포함하세요. 여러 출처를 허용하려면
쉼표로 구분한 목록을 하나의 인수로 전달하세요. 각 출처 앞뒤의 공백은 제거됩니다.

```bash
opencode service set cors "http://192.168.1.10:3001, https://app.example.com"
```

`service get cors`는 JSON 배열을 출력합니다. 구성된 목록은 다음 명령으로 제거합니다.

```bash
opencode service unset cors
```

서비스 구성을 설정하거나 해제하면 백그라운드 서비스가 중지됩니다. 다음에 서비스가 시작될 때 새 구성이 적용되며,
`opencode service start`로 직접 시작할 수도 있습니다.

포그라운드 서버에서는 허용할 출처마다 `--cors`를 반복해서 지정하세요.

```bash
opencode serve --cors http://192.168.1.10:3001 --cors https://app.example.com
```

`serve --service`에서 `--cors` 플래그를 지정하면 해당 프로세스에서는 저장된 목록 대신 플래그 값이 사용됩니다. 플래그가
없으면 서비스 모드는 저장된 목록을 사용합니다. CORS는 수신 주소를 바꾸거나 서버 인증을 우회하지 않습니다.

## API 살펴보기

`api` 명령은 로컬 서비스 탐색과 인증 흐름을 사용합니다. HTTP 메서드와 경로, 또는 OpenAPI 작업 ID를 받습니다.

모든 엔드포인트와 작업 ID는 [API 레퍼런스](/api)를 참고하세요.

JSON 요청 본문은 `--data` 또는 `-d`로 전달하고, 헤더는 `--header` 또는 `-H`로 추가하세요.

<Callout type="warning">
  호환되는 정상 서비스가 없으면 `opencode api`를 실행할 때 백그라운드 서비스가 시작될 수 있습니다.
</Callout>

## 로그 읽기

설치된 빌드는 다음 위치에 로그를 기록합니다.

```text
~/.local/share/opencode/log/opencode.log
```

문제를 재현하는 동안 로그를 실시간으로 확인하세요.

```bash
tail -f ~/.local/share/opencode/log/opencode.log
```

각 줄에는 프로세스 `run` ID와 `role` 필드가 포함됩니다. 세션, 제공자, 플러그인, 권한, 도구 활동은 `role=server`로
확인하세요.

```bash
grep 'role=server' ~/.local/share/opencode/log/opencode.log
grep 'run=8fc3b1d5' ~/.local/share/opencode/log/opencode.log
```

## CPU 및 메모리 프로필 수집

macOS와 Linux에서는 실행 중인 OpenCode 프로세스에 시그널을 보내 진단 데이터를 수집할 수 있습니다. 상태 확인
엔드포인트에서 백그라운드 서버의 PID를 확인하세요.

```bash
opencode api get /api/info
```

응답의 `pid`에 다음 시그널 중 하나를 보내세요.

- `SIGPROF`는 10초 동안의 CPU 프로필을 수집합니다.

  ```bash
  kill -SIGPROF <pid>
  ```

  결과는 로그 디렉터리에 `cpu-<pid>-<timestamp>.cpuprofile`로 기록됩니다.

- `SIGUSR1`은 메모리(힙) 스냅샷을 수집합니다.

  ```bash
  kill -SIGUSR1 <pid>
  ```

  결과는 로그 디렉터리에 `heap-<pid>-<timestamp>.heapsnapshot`으로 기록됩니다.

파일을 열기 전에 `opencode.log`에 `CPU profile written` 또는 `heap snapshot written`이 기록될 때까지 기다리세요. 해당
로그 항목에 파일의 전체 경로가 포함됩니다. 두 파일 형식 모두 Chrome DevTools에서 살펴볼 수 있습니다.

<Callout type="note">
  시그널로 프로필을 수집하는 기능은 Windows에서 사용할 수 없습니다. 힙 스냅샷을 기록하는 동안 프로세스가 일시
  중지되고 메모리 사용량이 일시적으로 늘어날 수 있습니다.
</Callout>

## 서비스 파일

공유 서버는 다음 위치에 자신을 등록합니다.

```text
~/.local/state/opencode/service.json
```

비공개 서비스 구성은 다음 위치에 따로 저장됩니다.

```text
~/.config/opencode/service.json
```

데이터베이스는 보통 다음 위치에 있습니다.

```text
~/.local/share/opencode/opencode.db
```

`OPENCODE_DB`로 데이터베이스 위치를 재정의할 수 있습니다.

<Callout type="warning">
  문제를 해결하는 동안 서비스 파일이나 데이터베이스를 삭제하거나 편집하지 마세요. 데몬은 서비스 명령으로 관리하고,
  외부 도구로 영구 데이터를 살펴보기 전에는 백업을 만드세요.
</Callout>

## 이슈 보고

재현 가능한 문제를 보고할 때는 다음 내용을 포함하세요.

- `opencode --version` 출력
- `opencode service status` 출력
- 문제를 재현하는 최소한의 단계
- 문제가 공유 서비스, 특정 클라이언트, 하나의 프로젝트 중 어디에 영향을 주는지
- `run`과 `role` 필드를 포함한 관련 로그 줄

로그를 공유하기 전에 API 키, 인증 헤더, 프롬프트, 파일 내용 등 민감한 데이터를 제거하세요.

재현 가능한 문제는 [GitHub Issues](https://github.com/anomalyco/opencode/issues)에 등록하세요.
