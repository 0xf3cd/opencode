title: "Устранение неполадок"
---

<Callout type="tip">
  OpenCode может отладить сам себя. Опишите проблему и попросите его воспользоваться этой страницей: он прочитает
  описанные ниже шаги, проверит свой сервис и логи и поможет найти причину.
</Callout>

OpenCode построен по клиент-серверной архитектуре. Фоновый сервер управляет сессиями, плагинами, разрешениями и другим
состоянием приложения. Для начала определите, где возникает проблема: в клиенте, в общем сервере или в конкретном
проекте.

## Проверка фонового сервиса

Выведите информацию о текущем сервере:

```bash
opencode service status
```

Убедитесь, что его API работает:

```bash
opencode api get /api/info
```

Если сервис завис или работает некорректно, перезапустите его:

```bash
opencode service restart
```

Его также можно явно остановить и запустить:

```bash
opencode service stop
opencode service start
```

<Callout type="note">
  Обычно OpenCode сам находит или запускает общий фоновый сервис. Команды `service` нужны только для диагностики его
  жизненного цикла.
</Callout>

## Разрешение источника для браузера

Если браузерный клиент с другого источника (origin) не может подключиться из-за CORS, добавьте источник клиента в
конфигурацию сервиса:

```bash
opencode service set cors http://192.168.1.10:3001
opencode service get cors
```

Указывайте точный HTTP- или HTTPS-источник, при необходимости с портом, без пути и завершающей косой черты. Чтобы
разрешить несколько источников, передайте их одним аргументом через запятую; пробелы вокруг каждого источника
отбрасываются:

```bash
opencode service set cors "http://192.168.1.10:3001, https://app.example.com"
```

`service get cors` выводит JSON-массив. Удалить настроенный список можно так:

```bash
opencode service unset cors
```

Изменение или удаление параметра конфигурации сервиса останавливает фоновый сервис. При следующем запуске он применит
новую конфигурацию; чтобы запустить его явно, используйте `opencode service start`.

Для сервера на переднем плане укажите `--cors` отдельно для каждого разрешенного источника:

```bash
opencode serve --cors http://192.168.1.10:3001 --cors https://app.example.com
```

В режиме `serve --service` переданные флаги `--cors` переопределяют сохраненный список для этого процесса. Без этих
флагов в режиме сервиса используется сохраненный список. CORS не меняет адрес, на котором слушает сервер, и не
отменяет аутентификацию на сервере.

## Работа с API

Команда `api` использует локальное обнаружение сервиса и аутентификацию. Она принимает либо HTTP-метод и путь, либо ID
операции OpenAPI.

Все эндпоинты и ID операций перечислены в [справочнике по API](/api).

Тело запроса в JSON передается через `--data` или `-d`, заголовки — через `--header` или `-H`.

<Callout type="warning">
  Если совместимого работающего сервиса нет, `opencode api` может запустить фоновый сервис.
</Callout>

## Логи

Установленные сборки пишут логи в файл:

```text
~/.local/share/opencode/log/opencode.log
```

Следите за логом, пока воспроизводите проблему:

```bash
tail -f ~/.local/share/opencode/log/opencode.log
```

Каждая строка содержит ID процесса `run` и поле `role`. Активность сессий, провайдеров, плагинов, разрешений и
инструментов отмечена как `role=server`.

```bash
grep 'role=server' ~/.local/share/opencode/log/opencode.log
grep 'run=8fc3b1d5' ~/.local/share/opencode/log/opencode.log
```

## Профилирование CPU и памяти

В macOS и Linux можно отправить сигнал работающему процессу OpenCode, чтобы собрать диагностические данные. PID
фонового сервера можно узнать через эндпоинт health-проверки:

```bash
opencode api get /api/info
```

Используйте `pid` из ответа с одним из сигналов:

- `SIGPROF` записывает CPU-профиль за десять секунд:

  ```bash
  kill -SIGPROF <pid>
  ```

  Результат сохраняется в каталог логов как `cpu-<pid>-<timestamp>.cpuprofile`.

- `SIGUSR1` записывает снимок памяти (кучи):

  ```bash
  kill -SIGUSR1 <pid>
  ```

  Результат сохраняется в каталог логов как `heap-<pid>-<timestamp>.heapsnapshot`.

Прежде чем открывать файл, дождитесь в `opencode.log` сообщения `CPU profile written` или `heap snapshot written`. В
этой записи лога указан полный путь к файлу. Оба типа файлов можно открыть в Chrome DevTools.

<Callout type="note">
  Профилирование по сигналам недоступно в Windows. Запись снимка кучи может приостановить процесс и временно увеличить
  потребление памяти.
</Callout>

## Файлы сервиса

Общий сервер регистрирует себя в файле:

```text
~/.local/state/opencode/service.json
```

Его закрытая конфигурация хранится отдельно:

```text
~/.config/opencode/service.json
```

База данных обычно находится здесь:

```text
~/.local/share/opencode/opencode.db
```

Расположение базы данных можно переопределить с помощью `OPENCODE_DB`.

<Callout type="warning">
  При устранении неполадок не удаляйте и не редактируйте файлы сервиса и базу данных. Управляйте демоном с помощью
  команд `service`, а прежде чем изучать сохраненные данные сторонними инструментами, сделайте резервную копию.
</Callout>

## Сообщение о проблеме

Сообщая о воспроизводимой проблеме, приложите:

- вывод `opencode --version`;
- вывод `opencode service status`;
- минимальную последовательность шагов для воспроизведения;
- сведения о том, затрагивает ли проблема общий сервис, конкретный клиент или один проект;
- относящиеся к делу строки лога вместе с полями `run` и `role`.

Перед тем как делиться логами, удалите из них API-ключи, заголовки авторизации, промпты, содержимое файлов и другие
конфиденциальные данные.

О воспроизводимых проблемах сообщайте в [GitHub Issues](https://github.com/anomalyco/opencode/issues).
