title: "Переход с V1"
---

OpenCode 1 и OpenCode 2 используют одну и ту же команду `opencode`, поэтому по умолчанию их больше нельзя установить
параллельно. Перед установкой V2 удалите V1, если он установлен через пакетный менеджер; установщик V2 через curl
заменяет бинарный файл V1.

## Несовместимые изменения

В V2 есть три намеренных несовместимых изменения:

- [Плагины](/build/plugins/migrate-v1) используют новый API плагинов.
- У [API сервера и клиентов](#server-api-and-clients) новые контракты.
- [Конфигурация терминального клиента](/cli/config) переносится из многоуровневых файлов `tui.json(c)` в один глобальный
  файл `cli.json` (миграция выполняется автоматически).

Остальная поддерживаемая функциональность V1 должна оставаться совместимой. Некоторые поля, которые принимала схема V1,
никогда не имели аналога в V2 и намеренно игнорируются; они перечислены в разделе
[Принимаемые, но неподдерживаемые поля](#accepted-but-unsupported-fields).

Существующие поддерживаемые поля конфигурации сервера, определения агентов и команд, навыки и другие файлы в
`.opencode/` должны работать без изменений. Если поддерживаемое поведение, описанное в этом руководстве, перестало
работать в V2, считайте это ошибкой совместимости, а не ожидаемым шагом миграции.

<Callout type="tip">
  Если поддерживаемая функциональность V1 не работает в V2, сообщите об ошибке совместимости, следуя рекомендациям в
  разделе [Устранение неполадок](/troubleshooting).
</Callout>

## Установка V2

Установите терминальный клиент V2 по [руководству по запуску в терминале](/cli).

Переписывать все перед запуском V2 не обязательно. Практичный порядок миграции:

1. Оставьте существующую конфигурацию и определения в файлах.
2. Запустите V2 и проверьте модели, учетные данные, агентов, разрешения и MCP-серверы.
3. Перенесите плагины: реализации плагинов V1 в V2 не работают.
4. Перенесите интеграции, которые вызывают API сервера.
5. Когда будете готовы, преобразуйте конфигурацию в нативный формат V2. Этот шаг необязателен.

Пока проверяете миграцию, сохраните копию настроек V1. V1 и V2 используют одни и те же расположения конфигурации, поэтому
не направляйте V1 на файлы, которые уже преобразованы в нативный формат, поддерживаемый только V2.

## Конфигурация

В этом разделе описаны и конфигурация в JSON/JSONC, и определения в файлах внутри `.opencode/`.

### Использование существующей конфигурации

V2 читает существующую системную, глобальную и проектную конфигурацию из тех же расположений, что и V1:

```text
/Library/Application Support/opencode/opencode.json(c)
/etc/opencode/opencode.json(c)
%ProgramData%\opencode\opencode.json(c)
/Library/Managed Preferences/<user>/ai.opencode.managed.plist
/Library/Managed Preferences/ai.opencode.managed.plist
~/.config/opencode/opencode.json(c)
<project>/opencode.json(c)
<project>/.opencode/opencode.json(c)
```

V2 нормализует поддерживаемые поля V1 и нативные поля V2 в памяти, не перезаписывая исходный файл. Существующая
поддерживаемая конфигурация V1 должна продолжать работать, так что ее не нужно преобразовывать, чтобы попробовать V2 или
перейти на него.

Как и в V1, системная конфигурация и управляемые настройки macOS имеют наивысший приоритет, поэтому их значения
переопределяют глобальные и проектные файлы. Их [политики](/policies#precedence), включая перенесенные
`enabled_providers` и `disabled_providers`, также важнее глобальных и проектных политик. Переопределение настройки не
запрещает пользователям добавлять провайдеры, MCP-серверы, агентов или плагины, поэтому ограничения, которые должен
обеспечивать администратор, задавайте через `policies`, а не через обычные настройки вроде `permissions`.

### Миграция с помощью OpenCode

Формат конфигурации V1 по-прежнему поддерживается. Нативный формат V2 необязателен: он делает ряд настроек более явными
и удобными.

Рекомендуемый способ миграции — попросить OpenCode обновить конфигурацию за вас:

```text
Migrate my OpenCode configuration, including file-based definitions, from the V1 format to the native V2 format.
Preserve its behavior and all unrelated settings.
```

OpenCode изучит файл целиком, внесет нужные изменения из перечисленных ниже и не будет переписывать настройки, которые
менять не нужно. Преобразовывать все сразу не обязательно: на верхнем уровне поддерживаемые поля V1 и нативные поля V2
могут сосуществовать. Если обе формы задают одно и то же каноническое значение, приоритет имеет корректное нативное
значение V2 независимо от порядка ключей в JSON.

Смешивание форматов во вложенных объектах намеренно ограничено. OpenCode распознает смесь полей V1 и V2 внутри `mcp`,
`compaction` и `experimental`, но не определяет формат рекурсивно внутри отдельных агентов, провайдеров, команд или
моделей. Каждую такую вложенную запись держите целиком в одном формате. Сам по себе поддерживаемый синтаксис V1
предупреждений не вызывает; некорректные значения, неподдерживаемые устаревшие поля и конфликтующие значения V1/V2
приводят к предупреждениям, а остальные корректные настройки загружаются как обычно.

### Общий доступ

Устаревший логический параметр V1 `autoshare` превращается в явную политику `share`:

```jsonc
// V1
{ "autoshare": true }

// V2
{ "share": "auto" }
```

Используйте `"manual"`, `"auto"` или `"disabled"`. Если в файле V1 уже используется `share`, ничего менять не нужно.

### Разрешения и инструменты

В V1 эффекты разрешений сгруппированы по инструментам. В V2 используется один упорядоченный массив `permissions`, в
котором приоритет и исключения заданы явно:

```jsonc
// V1
{
  "permission": {
    "bash": {
      "git push *": "ask"
    },
    "edit": "allow"
  },
  "tools": {
    "websearch": false
  }
}

// V2
{
  "permissions": [
    { "action": "shell", "resource": "git push *", "effect": "ask" },
    { "action": "edit", "resource": "*", "effect": "allow" },
    { "action": "websearch", "resource": "*", "effect": "deny" }
  ]
}
```

Изменились и действия разрешений: `bash` теперь называется `shell`, `task` — `subagent`, а `write` и `patch` — `edit`.
Формат упорядоченных правил V2 описан в разделе [Разрешения](/permissions).

### Агенты и режимы

Объекты `agent` (в единственном числе) и устаревший `mode` заменяются на `agents`. Поля агентов становятся более
единообразными с остальной конфигурацией V2:

```jsonc
// V1
{
  "agent": {
    "reviewer": {
      "prompt": "Review for correctness and missing tests.",
      "model": "anthropic/claude-sonnet-4-5",
      "variant": "high",
      "disable": false,
      "permission": {
        "edit": "deny"
      }
    }
  }
}

// V2
{
  "agents": {
    "reviewer": {
      "system": "Review for correctness and missing tests.",
      "model": "anthropic/claude-sonnet-4-5#high",
      "disabled": false,
      "permissions": [
        { "action": "edit", "resource": "*", "effect": "deny" }
      ]
    }
  }
}
```

`prompt` становится `system`, `disable` — `disabled`, а отдельный `variant` добавляется к ссылке на модель после `#`.
`temperature`, `top_p` и специфичные для провайдера `options` переносятся в `request.body`. `maxSteps` становится
`steps`. Записи из старого объекта `mode` становятся основными агентами.

### Снимки

Переименуйте поле `snapshot` в `snapshots`. Его логическое значение не меняется:

```jsonc
// V1
{ "snapshot": false }

// V2
{ "snapshots": false }
```

### Медиафайлы

Переименуйте объект `attachment` в `media`. Вложенные настройки изображений сохраняют прежние имена:

```jsonc
// V1
{ "attachment": { "image": { "auto_resize": true } } }

// V2
{ "media": { "image": { "auto_resize": true } } }
```

### MCP-серверы

В V2 серверы сгруппированы в `mcp.servers`, вместо `enabled` используется обратный по смыслу `disabled`, а тайм-ауты
разделены по назначению:

```jsonc
// V1
{
  "mcp": {
    "playwright": {
      "type": "local",
      "command": ["npx", "@playwright/mcp"],
      "enabled": true,
      "timeout": 30000
    }
  }
}

// V2
{
  "mcp": {
    "servers": {
      "playwright": {
        "type": "local",
        "command": ["npx", "@playwright/mcp"],
        "disabled": false,
        "timeout": {
          "catalog": 30000,
          "execution": 30000
        }
      }
    }
  }
}
```

Поля OAuth для удаленных серверов записываются в snake_case: `clientId` становится `client_id`, `clientSecret` —
`client_secret`, `callbackPort` — `callback_port`, а `redirectUri` — `redirect_uri`. Значение V1
`experimental.mcp_timeout` также становится значением по умолчанию для `mcp.timeout.catalog` и
`mcp.timeout.execution`. Подробнее — в разделе [MCP-серверы](/mcp-servers).

### Сжатие контекста

В V2 бюджет токенов сохраняемого контекста сгруппирован в `keep`, а у резерва более понятное имя:

```jsonc
// V1
{
  "compaction": {
    "preserve_recent_tokens": 8000,
    "reserved": 20000
  }
}

// V2
{
  "compaction": {
    "keep": {
      "tokens": 8000
    },
    "buffer": 20000
  }
}
```

`auto` сохраняет свое имя. Нативных полей `tail_turns` и `prune` в V2 нет; оба устаревших поля игнорируются с
предупреждением. Недавний контекст теперь сохраняется по бюджету токенов. Подробнее — в разделе
[Сжатие контекста](/compaction).

### Навыки

В V1 дополнительные пути и URL навыков задаются раздельно. В V2 они объединены в один упорядоченный массив:

```jsonc
// V1
{
  "skills": {
    "paths": ["./team-skills"],
    "urls": ["https://example.com/skills/"]
  }
}

// V2
{
  "skills": ["./team-skills", "https://example.com/skills/"]
}
```

Существующие файлы навыков и автоматическое обнаружение в `.opencode/skills/` не меняются. Подробнее — в разделе
[Навыки](/skills).

### Команды

Переименуйте объект `command` в `commands`, а `subtask` — в `subagent`. Отдельный `variant` модели добавьте к ссылке на
модель:

```jsonc
// V1
{
  "command": {
    "review": {
      "template": "Review the current changes.",
      "model": "anthropic/claude-sonnet-4-5",
      "variant": "high",
      "subtask": true
    }
  }
}

// V2
{
  "commands": {
    "review": {
      "template": "Review the current changes.",
      "model": "anthropic/claude-sonnet-4-5#high",
      "subagent": true
    }
  }
}
```

`template`, `description` и `agent` сохраняют свои имена. Устаревшее поле `subtask` по-прежнему принимается;
делегированные команды теперь автоматически выполняются в фоне и сообщают результаты родительской сессии. Существующие
определения команд в Markdown по-прежнему поддерживаются. Подробнее — в разделе [Команды](/commands).

### Внешние каталоги

Переименуйте устаревший объект `reference` в `references`:

```jsonc
// V1
{ "reference": { "docs": "../docs" } }

// V2
{ "references": { "docs": "../docs" } }
```

V1 уже принимает `references`, поэтому, если файл использует это поле, ничего менять не нужно. Формат записей не
меняется. Подробнее — в разделе [Внешние каталоги](/references).

### Провайдеры

Переименуйте объект `provider` в `providers`. В V2 пакет среды выполнения, эндпоинт и параметры запросов разделены:

```jsonc
// V1
{
  "provider": {
    "acme": {
      "npm": "@ai-sdk/openai-compatible",
      "api": "https://llm.example.com/v1",
      "options": {
        "apiKey": "{env:ACME_API_KEY}"
      }
    }
  }
}

// V2
{
  "providers": {
    "acme": {
      "package": "aisdk:@ai-sdk/openai-compatible",
      "settings": {
        "baseURL": "https://llm.example.com/v1",
        "apiKey": "{env:ACME_API_KEY}"
      }
    }
  }
}
```

Поле V1 `npm` становится `package`, а пакеты AI SDK получают префикс `aisdk:`. `api` становится `settings.baseURL`.
`options` провайдера распределяются по `settings`, `headers` и `body` в зависимости от их роли в запросе.
`options.setCacheKey` становится полем провайдера `compatibility.supportsPromptCacheKey`. Подробнее — в разделе
[Провайдеры](/providers).

В V2 объединены два устаревших пространства имен провайдеров:

| ID провайдера в V1         | Канонический ID провайдера в V2 |
| -------------------------- | ------------------------------- |
| `azure-cognitive-services` | `azure`                         |
| `google-vertex-anthropic`  | `google-vertex`                 |

При миграции однозначных полей V1 — провайдеров, агентов, команд и фильтров провайдеров — используются эти канонические
ID. Общее поле верхнего уровня `model` сохраняет ID провайдера как есть, потому что тот же синтаксис допустим и в
нативной конфигурации V2. При миграции устаревшего встроенного провайдера замените ID в этом поле на канонический.

### Модели и варианты

Модели по-прежнему вложены в своего провайдера, но некоторые поля моделей становятся более явными:

- `id` становится `modelID`.
- `tool_call` и `modalities` становятся `capabilities.tools`, `capabilities.input` и `capabilities.output`.
- `status` со значением `"deprecated"` становится `disabled: true`.
- Стоимость кэша переносится из `cache_read` и `cache_write` в `cache.read` и `cache.write`.
- Специфичные для провайдера `options` становятся `settings`.
- Объект вариантов V1 становится массивом V2, в котором у каждого элемента есть `id`.

```jsonc
// V1
{
  "variants": {
    "high": {
      "reasoningEffort": "high"
    }
  }
}

// V2
{
  "variants": [
    {
      "id": "high",
      "settings": {
        "reasoningEffort": "high"
      }
    }
  ]
}
```

Полный нативный формат модели описан в разделе [Модели](/models).

### Поддерживаемые поля без прямых нативных аналогов

Большинство полей, формат которых не изменился, — включая `shell`, `model`, `default_agent`, `watcher`, `formatter`,
`instructions`, `enterprise` и `tool_output`, — не требуют миграции.

V2 принимает и сохраняет конфигурацию `lsp`, но не запускает языковые серверы, не предоставляет LSP-инструменты и не
выдает LSP-диагностику. Если ваши сценарии зависят от этих возможностей, замените их командами линтера, проверки типов
или компилятора вашего проекта.

У фильтров провайдеров V1 нет прямых нативных полей в конфигурации V2, но их поведение по-прежнему поддерживается через
[политики](/policies):

- `enabled_providers` превращается во внутреннюю политику провайдеров, которая по умолчанию запрещает все, а затем
  разрешает перечисленные провайдеры.
- `disabled_providers` превращается во внутренние запрещающие политики для перечисленных провайдеров.
- `autoupdate` становится `update`: `false` соответствует `"disable"`, `"notify"` — `"notify"`, а `true` — `"auto"`.
- `small_model` становится выбором `model` для встроенного агента `title`. В нативной конфигурации V2 используйте вместо
  этого `agents.title.model`.

Эти поля можно оставить в синтаксисе V1. OpenCode нормализует их без предупреждений.

### Принимаемые, но неподдерживаемые поля

Схема V1 принимала и поля, у которых нет поддерживаемого поведения в V2. V2 игнорирует эти значения и выводит
предупреждение, чтобы их не приняли за действующую конфигурацию:

- `logLevel`: при запуске OpenCode используйте `OPENCODE_LOG_LEVEL`.
- `server`: используйте сервис V2 и явные параметры сервера; API сервера — намеренное несовместимое изменение.
- `subagent_depth` на верхнем уровне: используйте вместо него `experimental.subagent_depth`.
- `compaction.tail_turns` и `compaction.prune`: в V2 вместо них используются `compaction.keep.tokens` и сжатие на основе
  контрольных точек.
- `name` агента внутри JSON-конфигурации V1.
- Запись MCP из V1, содержащая только `enabled` и не содержащая `type`.
- Экспериментальные поля V1 `batch_tool`, `openTelemetry`, `primary_tools` и `continue_loop_on_deny`.
- Поля провайдеров V1 `id`, `whitelist` и `blacklist`.
- Поля моделей провайдеров V1 `release_date`, `attachment`, `reasoning`, `temperature`, `experimental`, `status` со
  значением, отличным от `deprecated`, и логическое `interleaved`.

Эти поля игнорируются намеренно, и это не регрессия совместимости. Если V2 не сохраняет поведение, которое в других
частях этого руководства указано как поддерживаемое, следуйте рекомендациям по сообщению об ошибках в разделе
[Устранение неполадок](/troubleshooting).

### Файлы агентов

Файлы агентов V1 могут находиться в `agent/`, `agents/`, `mode/` или `modes/`. V2 по-прежнему находит все четыре
каталога. Предпочтительное расположение в V2:

```text
.opencode/agents/<name>.md
```

Файлы в каталогах V1 `mode/` или `modes/` описывают основных агентов. При переносе такого файла в `agents/` добавьте во
frontmatter `mode: primary`. Файлы из `agent/` можно перенести в `agents/`, не меняя ID, который определяется путем.

При преобразовании frontmatter в нативные поля V2:

- Оставьте тело Markdown в качестве системных инструкций агента.
- Переименуйте `prompt` в `system`, если поле задано в JSON-конфигурации; телу файла поле `system` не нужно.
- Переименуйте `disable` в `disabled`, а `permission` — в `permissions`.
- Объедините `model` и `variant` в `provider/model#variant`.
- Перенесите `temperature`, `top_p` и специфичные для провайдера параметры в `request.body`.

V2 автоматически преобразует устаревший frontmatter агентов, поэтому эти правки необязательны. Подробнее — в разделе
[Агенты](/agents).

### Файлы команд

Файлы команд V1 могут находиться в `command/` или `commands/`. V2 находит оба каталога. Предпочтительное расположение:

```text
.opencode/commands/<name>.md
```

Чтобы сохранить имена команд, перенесите файлы из `command/` по тому же относительному пути в `commands/`. Тело
Markdown остается шаблоном команды, а поля frontmatter `description` и `agent` сохраняют свои имена. Переименуйте
`subtask` в `subagent`, чтобы использовать нативное имя для фонового делегирования. Если во frontmatter есть отдельные
поля `model` и `variant`, добавьте вариант к модели и удалите `variant`:

```yaml
# V1
model: anthropic/claude-sonnet-4-5
variant: high
subtask: true

# V2
model: anthropic/claude-sonnet-4-5#high
subagent: true
```

Подробнее — в разделе [Команды](/commands).

### Файлы навыков

V2 находит навыки как в `.opencode/skill/`, так и в `.opencode/skills/`. Предпочтительная структура:

```text
.opencode/skills/<skill-id>/SKILL.md
```

Переносите каталог навыка целиком, а не только `SKILL.md`, чтобы скрипты, справочные материалы и другие
вспомогательные файлы по относительным путям оставались доступными. Не меняйте имя каталога, чтобы сохранить ID навыка.
Существующие frontmatter и тела Markdown навыков переписывать для V2 не нужно. Подробнее — в разделе [Навыки](/skills).

### Файлы инструкций

Существующие файлы `AGENTS.md` остаются на своих местах. V2 находит глобальный `~/.config/opencode/AGENTS.md` и
окружающие файлы `AGENTS.md` — от текущего каталога вверх до домашнего. Для проектов вне домашнего каталога поиск
останавливается на корне проекта.

Если настройка V1 полагалась на резервный файл `CLAUDE.md`, перенесите эти указания в соответствующий `AGENTS.md`. Пока
V2 находит только `AGENTS.md`. Поскольку поведение V1, не связанное с API, должно оставаться совместимым, также
сообщите об ошибке совместимости и укажите данные затронутого проекта. Подробнее — в разделе
[Инструкции](/instructions).

## Конфигурация терминального клиента

Вместо многоуровневых файлов V1 `tui.json(c)` в V2 используется один глобальный файл конфигурации терминального
клиента:

```text
~/.config/opencode/cli.json
```

Этим файлом управляет терминальный клиент; фоновый сервис его не загружает. Если `cli.json` нет, при первом запуске
терминального клиента V2 поддерживаемые глобальные настройки из `tui.json` и сохраненные предпочтения переносятся
автоматически, а файлы V1 остаются без изменений. Локальная конфигурация клиента на уровне проекта не переносится,
потому что в V2 конфигурация клиента глобальная. Актуальный справочник по настройкам клиента — в разделе
[Настройки CLI](/cli/config).

## Плагины

Переименуйте `plugin` в `plugins`. Кортеж из пакета и параметров замените объектом:

```jsonc
// V1
{
  "plugin": ["opencode-example-plugin", ["./plugin/local.ts", { "enabled": true }]]
}

// V2
{
  "plugins": [
    "opencode-example-plugin",
    {
      "package": "./plugin/local.ts",
      "options": { "enabled": true }
    }
  ]
}
```

V2 находит локальные плагины как в `.opencode/plugin/`, так и в `.opencode/plugins/`; для файлов V2 используйте
`.opencode/plugins/`.

<Callout type="warning">
  Реализации плагинов V1 в V2 не работают. Недостаточно просто переместить файл или переименовать запись в конфигурации.
</Callout>

Перенесите точки входа, хуки, инструменты, события и экспорты пакета с помощью отдельного
[руководства по миграции плагинов](/build/plugins/migrate-v1).

## API сервера и клиенты

В OpenCode 2 переработанный, более удобный API сервера и новый набор клиентов. Интеграции, которые вызывают API сервера
V1, нужно перевести на API V2.

Для доступа к выпущенному API V2 используйте пакет `@opencode/client`. Его эндпоинты, типы запросов и ответы описаны в
сгенерированном [справочнике по API](/api).

## Проверка настройки

Прежде чем использовать V2 в повседневной работе, проверьте на проекте модель, учетные данные провайдера, агентов,
разрешения, MCP-серверы и плагины. Сохраняйте настройки V1, пока не убедитесь, что V2 ведет себя так, как вам нужно, и
не направляйте V1 на конфигурацию, преобразованную в нативный формат V2.
