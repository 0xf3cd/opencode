Los plugins pueden modificar el comportamiento de OpenCode y añadir funciones nuevas. Para cambiar la interfaz de
terminal, crea un [plugin de la CLI](/build/plugins/cli).

¿Vas a migrar un plugin existente de OpenCode 1? Sigue la [guía de migración de plugins de V1](/build/plugins/migrate-v1).

```ts title=".opencode/plugins/example/index.ts"
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "example",
  async setup(ctx) {
    await ctx.storage.set("loaded", true)
  },
})
```

Los plugins de `.opencode/plugins/` se cargan automáticamente, como el ejemplo local anterior. Para cargar paquetes
publicados o directorios de plugins de otras ubicaciones, añádelos a `plugins` en `opencode.json(c)`:

```jsonc title="opencode.jsonc"
{
  "$schema": "https://opencode.ai/config.json",
  "plugins": [
    "opencode-acme-plugin",
    "opencode-acme-plugin@1.2.0",
    "@acme/opencode-plugin",
    "./plugins/local",
    "../shared/plugin",
    "/absolute/path/plugin",
    "file:///home/me/plugins/local",
    {
      "package": "@acme/opencode-plugin",
      "options": {
        "agent": "reviewer",
        "strict": true,
      },
    },
  ],
}
```

Consulta [Configurar plugins](/plugins) para ver más opciones de carga y configuración.

## Ciclo de vida

`setup` se ejecuta cuando se carga el plugin. Puede devolver una función de limpieza que se ejecuta cuando el plugin se
descarga.

```ts
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "example",
  setup(ctx) {
    console.log(`loaded in OpenCode ${ctx.app.version}`)
    return () => console.log("unloaded")
  },
})
```

### Contexto

El contexto del plugin es, en esencia, un [cliente del servidor de OpenCode](/build/client). Sus métodos de lectura y de
acción usan las mismas entradas y respuestas que el cliente. Además, añade métodos exclusivos de los plugins para
transformaciones, hooks en tiempo de ejecución, recargas, registros y opciones del plugin.

```ts
setup(ctx) {
  console.log(ctx.app.version)
}
```

`ctx.location` describe la ubicación donde está cargada esta instancia del plugin. Incluye `directory`, un `workspaceID`
opcional y los metadatos de `project` (`id`, `directory` y `canonical`). Está disponible tanto en plugins de Promise como
de Effect. Es la ubicación de la instancia del plugin, no la de todas las sesiones a las que puede acceder ni la de los
eventos que recibe.

```ts
setup(ctx) {
  console.log(ctx.location.directory)
  console.log(ctx.location.project.canonical)
}
```

### Opciones

Pasa las opciones del plugin con la forma de objeto en `opencode.json(c)`.

```jsonc title="opencode.jsonc"
{
  "plugins": [
    {
      "package": "./plugins/company",
      "options": {
        "strict": true,
      },
    },
  ],
}
```

Lee esos valores desde `ctx.options` durante `setup`.

```ts title="plugins/company/index.ts"
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "company",
  setup(ctx) {
    const strict = ctx.options.strict === true
  },
})
```

## Transformaciones

Las transformaciones son ediciones síncronas del estado de un dominio de OpenCode, y cada una se aplica sobre los
registros anteriores de su dominio. Las lecturas, como `ctx.model.list()`, reflejan todos los registros hechos hasta el
momento, también durante el `setup` del plugin; la agrupación durante el arranque solo combina las
notificaciones de actualización y nunca retrasa lo que devuelve una lectura. Las APIs de estado de recursos siguen
informando del estado de los recursos en ejecución: que una definición esté registrada no significa que su conexión u
otro trabajo del recurso haya terminado.

Las fuentes aportan proveedores y definiciones de modelos inmutables mediante `ctx.provider.transform`.

```ts title="plugins/models/index.ts"
import { Model, Plugin, Provider } from "@opencode/plugin"

export default Plugin.define({
  id: "company.models",
  async setup(ctx) {
    const providerID = Provider.ID.make("acme")
    const models = [{ ...Model.Info.default(providerID, Model.ID.make("reasoner")), name: "Acme Reasoner" }]
    await ctx.provider.transform((editor) => {
      editor.add({
        info: {
          ...Provider.Info.empty(providerID),
          name: "Acme",
          activation: "enabled",
          package: "@opencode/ai/providers/openai-compatible",
          settings: { baseURL: "http://127.0.0.1:8000/v1" },
        },
        models,
      })
    })

    const available = await ctx.model.list()
  },
})
```

Cualquier registro, eliminación o `reload()` marca el estado del dominio como modificado; la siguiente lectura lo
reconstruye reproduciendo todas las transformaciones activas, en orden de registro, sobre un valor nuevo. Mantén las
transformaciones ligeras y repetibles. Las reconstrucciones posteriores nunca modifican un valor que ya hayas leído.

Una vez resueltas las transformaciones de proveedores y su disponibilidad, OpenCode materializa los modelos de los
proveedores activos y reproduce en orden todas las transformaciones de modelos. Una política de modelos puede examinar la
colección completa de candidatos, incluidas las fuentes recién actualizadas.

```ts title="plugins/model-budget/index.ts"
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "company.model-budget",
  async setup(ctx) {
    await ctx.model.transform((editor) => {
      editor
        .list()
        .filter((model) => model.cost.some((tier) => tier.output > 20))
        .forEach((model) => {
          editor.remove(model.providerID, model.id)
        })
    })
  },
})
```

Las entradas capturadas no se vigilan automáticamente. Carga los datos externos antes del callback síncrono y llama a
`reload()` cuando esas entradas cambien. Aquí, `loadFromSource()` devuelve entradas
`{ info: Provider.Info, models: readonly Model.Info[] }`.

```ts title="plugins/models/index.ts"
import { Plugin } from "@opencode/plugin"

export default Plugin.define({
  id: "company.models",
  async setup(ctx) {
    const source = { providers: await loadFromSource() }

    await ctx.provider.transform((editor) => {
      source.providers.forEach((provider) => editor.add(provider))
    })

    const refresh = async () => {
      source.providers = await loadFromSource()
      await ctx.provider.reload()
    }

    const timer = setInterval(() => void refresh().catch(console.error), 60_000)
    return () => clearInterval(timer)
  },
})
```

Los cambios de proveedores invalidan todo el resultado de modelos activos, así que la política de precio de salida sigue
filtrando los modelos actualizados. Usa `ctx.model.reload()` cuando solo cambie una entrada capturada por una
transformación de modelos.

## API

### Agentes

Lee todos los agentes u obtén uno por su ID.

```ts
const agents = await ctx.agent.list()
const build = await ctx.agent.get({ agentID: "build" })
```

Registra una transformación para examinar, actualizar o eliminar agentes, o para seleccionar el agente predeterminado.

```ts
await ctx.agent.transform((editor) => {
  const agents = editor.list()
  const build = editor.get("build")

  editor.default("build")
  editor.update("build", (agent) => {
    agent.description = "Builds features and fixes bugs"
  })
  editor.remove("legacy")
})
```

Recarga los agentes cuando cambie el estado externo que usa una transformación.

```ts
await ctx.agent.reload()
```

Esquema: [`Agent.Info`](/api#schema-Agent.Info)

### Proveedores

Lee los proveedores disponibles o consulta los metadatos de un proveedor por su ID.

```ts
const providers = await ctx.provider.list()
const provider = await ctx.provider.get({ providerID: "anthropic" })
```

Las transformaciones de proveedores editan los ajustes de los proveedores y las definiciones de origen. Las lecturas del
editor incluyen los proveedores inactivos y exponen definiciones inmutables; `models.update` edita una copia propia de un
modelo de origen.

```ts
await ctx.provider.transform((editor) => {
  editor.update("anthropic", (provider) => {
    provider.headers = { ...provider.headers, "x-company": "engineering" }
  })
  editor.models.update("anthropic", "claude-sonnet-4-5", (model) => {
    model.name = "Team Sonnet"
  })
  editor.models.remove("anthropic", "legacy-model")
  editor.remove("legacy-provider")
})
```

Sustituye el inventario de origen de un proveedor con `models.set` y recarga cuando cambien las definiciones
capturadas.

```ts
const source = { models: await loadModels() }
await ctx.provider.transform((editor) => {
  editor.models.set("acme", source.models)
})

source.models = await loadModels()
await ctx.provider.reload()
```

Si el descubrimiento depende de la cuenta, pasa como `sourceConnection` la conexión usada para cargar el inventario.
OpenCode excluye ese proveedor mientras haya otra conexión seleccionada, hasta que tu plugin publique su inventario
actualizado.

```ts
const connection = await ctx.integration.connection.active("acme")
if (!connection) return
const inventory = await loadInventory(connection)
await ctx.provider.transform((editor) => {
  editor.add({ info: inventory.provider, models: inventory.models, sourceConnection: connection })
})
```

#### Referencia

Esquemas: [`Provider.Info`](/api#schema-Provider.Info), [`Model.Info`](/api#schema-Model.Info)

```ts
interface ProviderDomain extends ProviderApi {

}

}

interface ProviderEditor {

  add(input: { info: Provider.Info; models: readonly Model.Info[]; sourceConnection?: ConnectionInfo }): void

    set(providerID: string, models: readonly Model.Info[]): void
    update(providerID: string, modelID: string, update: (model: DeepMutable<Model.Info>) => void): void

}
```

### Modelos

Lee los modelos disponibles y la selección predeterminada.

```ts
const models = await ctx.model.list()
const selected = await ctx.model.default()
```

Las transformaciones de modelos editan toda la colección de candidatos de los proveedores activos. Los candidatos
desactivados siguen siendo editables hasta que terminan todas las transformaciones; `update` solo puede añadir un modelo
bajo un proveedor disponible.

```ts
await ctx.model.transform((editor) => {
  editor.list("anthropic").forEach((model) => {
    editor.update(model.providerID, model.id, (draft) => {
      draft.enabled = draft.capabilities.tools
    })
  })
  editor.default.set("anthropic", "claude-sonnet-4-5")
  editor.remove("anthropic", "legacy-model")
})
```

Los callbacks editan las sobrescrituras sin procesar de los modelos. Los valores predeterminados del proveedor se
combinan una sola vez cuando OpenCode confirma el resultado; las lecturas sin cambios reutilizan ese resultado.
`editor.provider` expone las definiciones de origen inmutables, incluidas las plantillas inactivas, y no la salida de las
transformaciones de modelos.

```ts
await ctx.model.transform((editor) => {
  const source = editor.provider.get("anthropic")?.models.get("claude-sonnet-4-5")
  if (!source) return
  editor.update("anthropic", source.id, (model) => {
    model.limit.context = Math.min(model.limit.context, source.limit.context)
  })
})

await ctx.model.reload()
```

### Integraciones

Lee las integraciones y consulta las credenciales activas.

```ts
const integrations = await ctx.integration.list()
const github = await ctx.integration.get({ integrationID: "github" })
const connection = await ctx.integration.connection.active("github")
const credential = connection ? await ctx.integration.connection.resolve(connection) : undefined
```

Conecta integraciones con una clave de API.

```ts
await ctx.integration.connect.key({
  integrationID: "github",
  key: process.env.GITHUB_TOKEN!,
})
```

Inicia, consulta, completa o cancela un intento de conexión OAuth.

```ts
const attempt = await ctx.integration.oauth.connect({ integrationID: "github", methodID: "oauth" })
const status = await ctx.integration.oauth.status({ integrationID: "github", attemptID: attempt.data.attemptID })
await ctx.integration.oauth.complete({ integrationID: "github", attemptID: attempt.data.attemptID, code })
await ctx.integration.oauth.cancel({ integrationID: "github", attemptID: attempt.data.attemptID })
```

Las conexiones basadas en comandos exponen el mismo flujo de inicio, estado y cancelación.

```ts
const attempt = await ctx.integration.command.connect({ integrationID: "acme", methodID: "cli" })
const status = await ctx.integration.command.status({ integrationID: "acme", attemptID: attempt.data.attemptID })
await ctx.integration.command.cancel({ integrationID: "acme", attemptID: attempt.data.attemptID })
```

Registra una transformación para examinar las integraciones y gestionar sus métodos de autenticación.

```ts
await ctx.integration.transform((editor) => {
  const integrations = editor.list()
  const acme = editor.get("acme")

  editor.update("acme", (integration) => {
    integration.name = "Acme"
  })
  editor.method.update({
    integrationID: "acme",
    method: { id: "cli", type: "command", label: "Sign in with Acme CLI", command: ["acme", "login"] },
  })

  const methods = editor.method.list("acme")
  const legacy = methods.find((method) => method.type === "command" && method.id === "legacy")
  if (legacy) editor.method.remove("acme", legacy)
  editor.remove("legacy")
})
```

Recarga las integraciones cuando cambie el estado externo que usa una transformación.

```ts
await ctx.integration.reload()
```

### MCP

Lista los servidores MCP y su estado de conexión actual.

```ts
const servers = await ctx.mcp.list()
```

Los plugins gestionan los servidores MCP únicamente mediante transformaciones. Usa `editor.set` para añadir o reemplazar
un servidor, `editor.update` para cambiar su configuración y `editor.remove` para eliminarlo. Consulta la configuración
con `editor.list` y `editor.get`.

```ts
await ctx.mcp.transform((editor) => {
  const servers = editor.list()
  const docs = editor.get("docs")
  editor.set("docs", { type: "remote", url: "https://mcp.example.com" })
  editor.update("docs", (server) => {
    server.disabled = false
  })
  editor.remove("legacy")
})
```

Define `disabled: true` en una transformación para desactivar un servidor y desconectarlo, o `disabled: false` para
activarlo y permitir que OpenCode se conecte. OpenCode concilia el ciclo de vida de los servidores a partir de la
configuración transformada.

Llama a `reload()` cuando cambie el estado externo que usa una transformación para volver a aplicar las
transformaciones y conciliar los servidores.

```ts
await ctx.mcp.reload()
```

```ts
const review = await ctx.generate.text({
```

### Permisos

Consulta o resuelve las solicitudes de permiso pendientes.

```ts
const pending = await ctx.permission.list({ sessionID })
const request = await ctx.permission.get({ sessionID, requestID })
await ctx.permission.reply({ sessionID, requestID, reply: "once" })
```

Sustituye las reglas de permisos de la sesión. Se evalúan después de las reglas del agente, y prevalece la última regla
que coincida. Las sesiones hijas heredan las reglas vigentes en el momento de crearse.

```ts
await ctx.permission.rules({
  sessionID,
  permissions: [{ action: "edit", resource: "/path/to/original/checkout/**", effect: "deny" }],
})
```

### Sesiones

Crea o lee una sesión.

```ts
const created = await ctx.session.create({ title: "Review" })
const session = await ctx.session.get({ sessionID })
const messages = await ctx.session.context({ sessionID })
```

Cambia el agente o el modelo que usarán las solicitudes posteriores.

```ts
await ctx.session.switchAgent({ sessionID, agent: "build" })
await ctx.session.switchModel({ sessionID, model: { providerID: "anthropic", id: "claude-sonnet-4-5" } })
```

Envía prompts de usuario, solicitudes de generación transitorias, comandos o mensajes sintéticos.

```ts
const prompt = await ctx.session.prompt({ sessionID, text: "Review the current changes" })
const generated = await ctx.session.generate({ sessionID, prompt: "Summarize this project" })
const command = await ctx.session.command({ sessionID, command: "review", arguments: "--staged" })
const synthetic = await ctx.session.synthetic({ sessionID, text: "Deployment completed" })
```

Renombra o interrumpe una sesión, o espera a que termine.

```ts
await ctx.session.update({ sessionID, title: "Review" })
await ctx.session.interrupt({ sessionID, continue: false })
await ctx.session.wait({ sessionID })
```

Elimina una sesión temporal con `remove`. La eliminación detiene la ejecución activa y borra recursivamente las
sesiones hijas.

```ts
await ctx.session.remove({ sessionID })
```

Solicita la compactación con `compact`. Devuelve el elemento admitido en la bandeja de entrada, no un resumen terminado;

### Herramientas

Lee las herramientas registradas actualmente, tras aplicar todas las transformaciones, fuera de un callback de
transformación. Cada herramienta tiene un `id` que contiene su nombre efectivo.

```ts
const tools = await ctx.tool.list()
const read = tools.find((tool) => tool.id === "read")
```

Registra, actualiza y elimina herramientas con una transformación síncrona, también en los plugins de Promise. Carga los
datos externos antes de registrar o recargar. Un registro válido posterior sobrescribe la herramienta con el mismo nombre
efectivo.

```ts
const registration = await ctx.tool.transform((editor) => {
  editor.namespace({
    name: "acme",
    description: "Customer account tools",
  })
  editor.add({
    name: "greeting",
    description: "Create a greeting",
    input: {
      type: "object",
      properties: { name: { type: "string" } },
      required: ["name"],
      additionalProperties: false,
    },
    options: { namespace: "acme", codemode: true },
    execute: async (input, context) => {
      await context.progress({ status: "greeting" })
      return { content: `Hello ${(input as { name: string }).name}!` }
    },
  })
})
```

Los ejecutores de herramientas de Promise reciben `context.signal`. Pásalo al trabajo cancelable, como `fetch`, para que
al detener la sesión también se detenga la operación subyacente.

```ts
execute: async ({ url }, context) => {
  const response = await fetch(url, { signal: context.signal })
  return { content: await response.text() }
}
```

Llama a `reload()` después de cambiar los datos de origen capturados por el callback. La recarga reproduce las
transformaciones activas sin cambiar su orden; no vuelve a ejecutar el `setup` del plugin.

```ts
await ctx.tool.reload()
```

Usa `list()` y `get()` para examinar las herramientas que hay en el editor. Las herramientas tienen un `id` que contiene
su nombre efectivo, y `get()` devuelve `undefined` si ese ID no existe. Usa `update` y `remove` con el nombre efectivo de
la herramienta, incluido su espacio de nombres (`acme_greeting` en el ejemplo anterior). Los puntos de los espacios de
nombres y los caracteres no admitidos en los nombres de herramientas se convierten en `_`. Los nombres inexistentes se
ignoran; para crear una herramienta hace falta `add` con una definición completa. Las actualizaciones conservan el
nombre y el espacio de nombres. Para reemplazar esquemas u opciones, asigna valores nuevos en lugar de mutar los valores
anidados. Las actualizaciones no válidas se registran en el log y dejan intacta la definición anterior.

```ts
await ctx.tool.transform((editor) => {
  editor.update("acme_greeting", (tool) => {
    tool.description = "Greet the user by name"
  })
  editor.remove("acme_obsolete")
})
```

Las actualizaciones y eliminaciones se reproducen en orden junto con las adiciones, también después de que se actualice
el catálogo MCP. Al desechar su registro, esos cambios se eliminan y el resultado se reconstruye a partir de las
transformaciones restantes.

Desecha un registro para eliminar su transformación y reconstruir a partir de las transformaciones restantes, lo que
vuelve a dejar visible cualquier definición anterior que sobrescribiera. Desechar es idempotente, y al descargar el plugin
también se desechan sus registros.

```ts
await registration.dispose()
```

Cada solicitud al modelo captura una instantánea estable y ejecutable de las herramientas. Las transformaciones,
recargas y desechos posteriores afectan a las instantáneas futuras, no a las definiciones, las descripciones de espacios
de nombres de Code Mode ni los ejecutores ya capturados. Los ejecutores que encierran datos mutables del plugin siguen
viendo esos datos; captura un valor dentro de la transformación cuando deba quedar ligado a esa definición.

```ts
    name: "Custom VCS",
```

llamarlo, OpenCode comprueba que el directorio existe y no contiene ningún repositorio, y después vuelve a descubrir el
proyecto. Los formatos de repositorio nuevos siguen necesitando compatibilidad con el descubrimiento, además de este
callback.

### Worktrees

Registra una estrategia de worktrees locales mediante el ciclo de vida normal del plugin. En este ejemplo, el módulo de
implementación se encarga de validar las opciones y de las operaciones `create`, `remove` y `list` del backend.

```ts title="plugins/worktrees/index.ts"
import { Plugin } from "@opencode/plugin"
import { makeStrategy } from "./strategy"

export default Plugin.define({
  id: "company.worktrees",
  async setup(ctx) {
    const strategy = makeStrategy(ctx.options)
    await ctx.worktree.transform((editor) => {
      editor.add(strategy)
    })
  },
})
```

Carga el plugin mediante `plugins` y configura el destino común por separado:

```jsonc title="opencode.jsonc"
{
  "worktree": { "directory": "../worktrees" },
  "plugins": [{ "package": "./plugins/worktrees", "options": {} }],
}
```

- Al añadir una estrategia, se selecciona automáticamente. Prevalece el último registro activo; no hace falta
  configurar qué estrategia usar.
- Al desechar su registro o descargar el plugin se restaura la implementación anterior y, en último término, la
  estrategia de Git incluida.
- `reload()` reproduce las transformaciones cuando cambian las entradas capturadas; no vuelve a ejecutar el `setup` del
  plugin.
- Si la creación falla, no se reintenta con Git. Los worktrees existentes conservan su propietario registrado aunque
  cambie la estrategia predeterminada.
- Las estrategias gestionan directorios locales. El aprovisionamiento de espacios de trabajo remotos no forma parte de
  esta interfaz.

#### Operaciones

El contexto del plugin expone las mismas operaciones de worktrees por proyecto que el cliente. Todas las operaciones
requieren un `projectID`. `list` solo lee el inventario guardado, incluidas las copias conocidas del mismo proyecto; no
carga la configuración, no inicia plugins ni detecta cambios en el sistema de archivos.

```ts
const projectID = ctx.location.project.id
const created = await ctx.worktree.create({ projectID, name: "task" })
const inventory = await ctx.worktree.list({ projectID })
await ctx.worktree.refresh({ projectID })
await ctx.worktree.remove({ projectID, directory: created.directory, force: false })
```

La creación carga la configuración y los plugins desde el directorio `canonical` guardado del proyecto y usa la
estrategia que seleccionan. Acepta, de forma opcional, un `directory` padre, un origen `from`, una rama inicial `branch` y
un nombre `name`. De forma predeterminada, el origen es la copia canónica, y un `from` alternativo debe pertenecer a ese
proyecto. Elegir un origen no cambia la raíz de la configuración. La estrategia seleccionada debe admitir la referencia
inicial que se indique; la operación nativa de instantáneas de Rift, por ejemplo, no tiene opción para elegir la
referencia.

La creación y la actualización esperan a que se activen los plugins de la copia canónica. Las llamadas que se hacen
durante el `setup` de los plugins de esa copia ven los registros hechos hasta ese momento y no esperan a su propia
activación.

La eliminación carga la configuración canónica y activa sus plugins, y después usa la estrategia registrada del worktree
en lugar de la predeterminada actual. Si el propietario registrado no está disponible, se produce un error. El destino
del worktree puede estar en otro lugar:

```ts
await ctx.worktree.remove({
  directory: "/worktrees/task",
  projectID,
  force: false,
})
```

Si falta el propietario, la eliminación falla en lugar de recurrir a Git. Una estrategia puede lanzar `new Worktree.OperationError({
message: "Uncommitted changes", forceRequired: true })`, importando `Worktree` desde `@opencode/plugin`, para pedir una
confirmación forzada sin depender de errores de Core o de Git.

La actualización carga la configuración canónica y pide a todas las estrategias disponibles que busquen worktrees en las
raíces de las copias conocidas. Combina los resultados, conserva los propietarios registrados y elimina los directorios
que ya no existen. Si una fuente de descubrimiento falla, se registra en el log y las demás continúan. Los directorios
existentes siguen guardados aunque ninguna estrategia disponible los indique. Escucha `worktree.updated` y vuelve a
llamar a `list` para leer el inventario modificado.

```ts
await ctx.worktree.refresh({ projectID })
```

#### Referencia

Las implementaciones reciben un destino sugerido una vez resueltos el nombre y las colisiones. Devuelve desde `create` el
directorio real; puede ser distinto si un backend requiere su propia estructura. OpenCode resuelve la ruta devuelta y la
usa para el inventario, los comandos de inicio y el resultado de la API. El directorio devuelto debe existir.

Las estrategias que eligen otro destino gestionan allí las colisiones de nombres. Aun así, OpenCode crea el directorio
padre sugerido antes de llamar a la estrategia. `list` solo debe indicar los directorios que pertenecen a la estrategia,
además de las raíces de repositorio.

```ts
interface WorktreeDefinition {
  readonly id: string
  create(
    input: { sourceDirectory: string; directory: string; branch?: string },
    context: { signal: AbortSignal },
  ): Promise<{ directory: string }>
  remove(input: { directory: string; force: boolean }, context: { signal: AbortSignal }): Promise<void>
  list(
    sourceDirectory: string,
    context: { signal: AbortSignal },
  ): Promise<readonly { directory: string; type: "root" | "worktree" }[]>
}

interface WorktreeEditor {
  add(definition: WorktreeDefinition): void
}

interface WorktreeDomain extends WorktreeApi {
  transform(callback: (editor: WorktreeEditor) => void): Promise<Registration>
  reload(): Promise<void>
}
```

Los callbacks de Promise deben respetar la cancelación mediante `signal`. Los callbacks de Effect devuelven Effects y usan
en su lugar la interrupción de Effect. Los registros siguen delimitados al entorno de ejecución del plugin; las
operaciones de proyecto usan el catálogo de estrategias de la copia canónica. Los adaptadores de configuración de Core
alimentan ese catálogo con los ajustes de directorio.

## Hooks

Los hooks interceptan operaciones en curso. Registra cada hook en su dominio y desecha el registro devuelto cuando ya no
lo necesites.

```ts
const registration = await ctx.session.hook("context", () => {})
await registration.dispose()
```

Varios plugins pueden registrar el mismo hook. OpenCode los ejecuta en el orden de los plugins, así que los hooks
posteriores ven los cambios hechos por los anteriores.

### Sesiones

Los hooks de sesión interceptan la admisión de prompts, las llamadas al modelo, el HTTP nativo y los reintentos.

#### Admisión de prompts

Intercepta los prompts entrantes del usuario antes de resolver los adjuntos y las skills y antes de su admisión
duradera en la bandeja de entrada:

```ts
await ctx.session.hook("prompt", (event) => {
  event.prompt.text = event.prompt.text.replaceAll("company-secret", "[redacted]")
  event.prompt.files ??= []
  event.prompt.files.push({ uri: "file:///project/policy.md" })
  event.metadata = { ...event.metadata, source: "company-policy" }
  event.delivery = "queue"
})
```

El hook recibe un borrador propio y mutable:

- `prompt` contiene `text`, `files`, las menciones a agentes en `agents` y las `skills` seleccionadas.
- `metadata` contiene metadatos de admisión definidos por la aplicación.
- `delivery` es `"steer"` de forma predeterminada y se puede cambiar a `"queue"`.
- Los IDs de sesión y de mensaje son de solo lectura; un hook no puede redirigir la admisión.

Los archivos y las skills que añade un hook siguen el proceso normal de resolución y validación. Si reescribes el texto,
actualiza o elimina los desplazamientos `mention` de los adjuntos que ya no coincidan. Las menciones a agentes no cambian
el agente activo de la sesión.

Los hooks de prompt se ejecutan en estas condiciones:

- Los hooks se ejecutan en orden de registro cuando los plugins de la ubicación de la sesión están listos.
- Los comandos que envían mediante `session.prompt` ejecutan el hook.
- Los mensajes sintéticos, los mensajes de shell y los controles de compactación y de movimiento no lo ejecutan.
- El hook se ejecuta una vez durante la admisión, no antes de cada llamada al modelo.
- No se puede limitar a un proveedor, porque el modelo se resuelve después de la admisión.

Las ediciones pasan a ser la entrada canónica del usuario que se guarda. Si la preparación falla o se interrumpe,
OpenCode no admite el prompt.

Haz que los hooks de prompt toleren reintentos. No garantizan que los efectos secundarios ocurran exactamente una vez:

- Reintentar con un ID ya pendiente o entregado devuelve la admisión original sin volver a ejecutar los hooks.
- Los envíos simultáneos pueden ejecutar los hooks más de una vez, pero solo prevalece la primera admisión correcta.
- Los hooks de prompt transforman la entrada y no exponen una API tipada para rechazarla.

#### Solicitudes al modelo

Modifica las instrucciones del sistema ya ensambladas, los mensajes, las herramientas o las opciones de la solicitud
justo antes de enviarla al modelo. Cada tipo de solicitud que emite una sesión tiene su propio hook, así que un plugin
puede tratar de forma distinta el bucle del agente y las solicitudes auxiliares:

- `context` se ejecuta para el bucle del agente, incluidas las continuaciones tras llamadas a herramientas.
- `compaction` se ejecuta para los resúmenes de punto de control. `messages` es la transcripción que se resume; OpenCode
  añade su prompt de resumen después de ejecutar los hooks. Define `result` para registrar tú mismo la compactación y
  omitir la llamada al modelo; admite los mismos campos que un mensaje de compactación completado.
- `generate` se ejecuta para las llamadas transitorias a `ctx.session.generate`.
- `title` se ejecuta para la generación de títulos. No tiene `agent` ni `tools`. Define `result` para proporcionar tú
  mismo el título.

```ts
await ctx.session.hook("context", (event) => {
  event.system.push({ type: "text", text: "Keep the review focused on correctness." })
  delete event.tools.write
  event.options.temperature = 0.2
  event.options.maxTokens = 8_000
})

await ctx.session.hook("compaction", async (event) => {
  event.result = { summary: await summarize(event.messages) }
})
```

Los cambios solo afectan a la llamada saliente al modelo, no al historial guardado ni a la configuración. Un hook que
deba aplicarse a todas las solicitudes tiene que registrarse para cada tipo.

Las sobrescrituras de la solicitud siguen estas reglas:

- `options` empieza vacío en cada llamada al modelo; no contiene los ajustes resueltos del modelo.
- Las claves tipadas son ajustes de generación; cualquier otra clave se pasa al protocolo seleccionado como opción del
  proveedor.
- Los hooks se ejecutan en orden de registro y ven las sobrescrituras hechas por los hooks anteriores.
- Las sobrescrituras de la solicitud tienen prioridad sobre los valores predeterminados del modelo, que a su vez tienen
  prioridad sobre los de la ruta.
- Los objetos de opciones del proveedor se combinan de forma recursiva; los arrays y los valores escalares reemplazan a
  los anteriores.
- Eliminar una sobrescritura o asignarle `undefined` hace que se recurra a los valores predeterminados configurados, en
  lugar de eliminarlos.
- Las capas sobre el cuerpo HTTP sin procesar se aplican después de la conversión al protocolo y pueden sobrescribir los
  campos resultantes.

#### Opciones del proveedor

Las opciones del proveedor usan los nombres semánticos de opción del protocolo seleccionado, no los campos sin procesar
del cuerpo HTTP. Limita los ajustes específicos de un proveedor a ese proveedor. Por ejemplo, OpenAI Responses usa
`reasoningEffort`:

```ts
await ctx.session.hook(
  "context",
  (event) => {
    event.options.reasoningEffort = "high"
  },
  { providerID: "openai" },
)
```

Las opciones de generación dependen del protocolo y el modelo seleccionados:

- `maxTokens` es el límite semántico de tokens de salida.
- Gemini admite `topK`; OpenAI Responses no lo expone.

#### Solicitud al modelo

Modifica los ajustes de la solicitud al modelo y, opcionalmente, limita el hook a un proveedor. El evento lleva el mismo
`kind` que los hooks HTTP que se describen a continuación.

```ts
await ctx.session.hook(
  "model.request",
  (event) => {
    event.headers["x-plugin"] = "review"
  },
  { providerID: "anthropic" },
)
```

#### HTTP nativo

Modifica las solicitudes o respuestas nativas del proveedor. Sus cuerpos son streams de un solo uso; clona o reemplaza un
cuerpo antes de leerlo.

Ambos hooks se ejecutan para cada solicitud que emite una sesión. `event.kind` indica qué flujo la emitió: `"primary"`
para el bucle del agente, `"compaction"` para los resúmenes de punto de control, `"title"` para la generación de títulos
y `"generate"` para las llamadas transitorias a `ctx.session.generate`. Úsalo en lugar del ID del agente para distinguir
las solicitudes auxiliares.

```ts
await ctx.session.hook("http.request", (event) => {
  event.request.headers.set("x-session-id", event.sessionID)
  if (event.kind === "title") event.request.headers.set("x-priority", "background")
})

await ctx.session.hook("http.response", (event) => {
  event.response = new Response(event.response.body, {
    status: event.response.status,
    headers: { ...Object.fromEntries(event.response.headers), "x-plugin": "review" },
  })
})
```

#### WebSocket nativo (experimental)

Los proveedores que hacen streaming por WebSocket abren una conexión por sesión y la reutilizan entre solicitudes, así
que `http.request` y `http.response` nunca ven ese tráfico. El hook `experimental.ws.handshake` se ejecuta una vez por
llamada al modelo, antes de seleccionar la conexión. Lleva los mismos `sessionID`, `agent`, `model` y `kind` que los
hooks HTTP, además de la `url` y los `headers` de la conexión. Cambiar `url` o `headers` cambia el socket que usa la
solicitud, de modo que un token bearer rotado vuelve a abrir la conexión.

Los hooks HTTP se siguen ejecutando para cada solicitud HTTP, incluida la solicitud a la que recurre una ruta WebSocket
como alternativa.

```ts
await ctx.session.hook(
  "experimental.ws.handshake",
  async (event) => {
    event.headers.authorization = `Bearer ${await mintToken(event.url)}`
    delete event.headers["api-key"]
  },
  { providerID: "azure" },
)
```

`experimental.ws.send` y `experimental.ws.receive` exponen los propios frames; son el equivalente en WebSocket a editar
el cuerpo de una solicitud o respuesta HTTP. `send` se ejecuta después de que el driver del proveedor construya un frame
de salida y antes de escribirlo; `receive` se ejecuta con cada frame entrante antes de que el driver lo procese. Ambos
llevan el frame como cadena y envían lo que contenga `frame` cuando el hook termina.

OpenCode no valida los frames reescritos. El driver sigue el estado a partir de las respuestas del proveedor, así que una
reescritura que cambie el significado del protocolo es responsabilidad del plugin, igual que un cuerpo HTTP reescrito.

```ts
await ctx.session.hook(
  "experimental.ws.send",
  (event) => {
    const body = JSON.parse(event.frame)
    if (body.type === "response.create") body.metadata = { ...body.metadata, session: event.sessionID }
    event.frame = JSON.stringify(body)
  },
  { providerID: "openai" },
)

await ctx.session.hook("experimental.ws.receive", (event) => {
  if (event.frame.includes('"type":"error"')) console.error(event.frame)
})
```

Estos hooks son experimentales y sus nombres o su forma pueden cambiar.

#### Política de reintentos

Sobrescribe la decisión de reintento ante un fallo del proveedor o sustituye su retardo en milisegundos. El hook se
ejecuta después de que OpenCode clasifique el fallo y proponga su política, pero antes de programar cualquier reintento.
No expone cómo realiza OpenCode internamente el siguiente intento.

```ts
await ctx.session.hook("retry", (event) => {
  if (event.error.status === 429) {
    event.decision = { retry: true, delay: 10_000 }
    return
  }
  if (event.error.type === "provider.invalid-request" && event.attempt === 2) {
    event.decision = { retry: true, delay: 0 }
    return
  }
  if (event.attempt >= 3) event.decision = { retry: false }
})
```

Los hooks de reintento pueden cambiar la `decision` inicial de OpenCode, haciendo que un fallo definitivo se pueda
reintentar o vetando un reintento propuesto.

Las decisiones de reintento siguen estas reglas:

- Si hay varios hooks, se ejecutan en orden de registro y los posteriores ven la decisión actual.
- El número máximo de intentos integrado sigue siendo un límite estricto.
- `attempt` es el intento real que se está evaluando. La solicitud inicial es `1`, así que el primer reintento es `2`.
- Los retardos no válidos, como `NaN`, infinito o valores negativos, se sustituyen por el retardo calculado.
- La recuperación por desbordamiento de contexto es independiente, porque compacta la conversación en lugar de
  reintentar la misma solicitud.

### Permisos

Revisa las decisiones de permisos después de evaluar las reglas configuradas y antes de que se ejecute una acción o se
publique una solicitud de permiso.

```ts
await ctx.permission.hook("evaluate", async (event) => {
  if (event.action === "read") return

  const messages = await ctx.session.context({ sessionID: event.sessionID })
  const review = await ctx.generate.text({
    model: { providerID: "anthropic", id: "claude-sonnet-4-6" },
    prompt: buildSafetyPrompt({ messages, action: event.action, resources: event.resources }),
  })
  const decision = parseDecision(review.text)

  event.effect = decision.effect
  event.message = decision.reason
})
```

Los hooks de permisos siguen estas reglas:

- Los hooks se ejecutan para las decisiones `allow` y `ask`.
- Un `deny` configurado explícitamente es definitivo y no invoca el hook.
- Un hook puede cambiar `effect` a `allow`, `ask` o `deny`.
- `message` aparece en la solicitud de permiso escalada o se convierte en el motivo de la denegación.

#### Referencia

```ts
interface PermissionEvaluation {
  readonly sessionID: string
  readonly agent?: string
  readonly action: string
  readonly resources: readonly string[]
  readonly metadata?: Record<string, unknown>
  readonly source?: { type: "tool"; messageID: string; id: string }
  effect: "allow" | "ask" | "deny"
  message?: string
}
```

### Herramientas


## Publicar

Un plugin publicado como paquete usa la misma exportación por defecto que un plugin local. Un manifiesto mínimo es:

```json title="package.json"
{
  "name": "opencode-acme-plugin",
  "version": "1.0.0",
  "type": "module",
  "exports": {
    ".": "./src/index.ts",
    "./rpc": "./src/rpc.ts"
  },
  "dependencies": {
    "@opencode/plugin": "latest"
  }
}
```

La exportación `./rpc` es opcional; inclúyela si publicas un [contrato RPC](/build/plugins/rpc) compartido para que otros
plugins y clientes lo importen sin cargar tu implementación.

Usa versiones compatibles con la versión de OpenCode a la que te diriges y prueba el paquete instalado, no solo una copia
enlazada en el espacio de trabajo. Publica una actualización compatible del plugin cuando adoptes un contrato de API más
reciente.

## Compatibilidad con V1

Un plugin puede ser compatible con V1 y V2 desde el mismo punto de entrada del paquete. Exporta por defecto un objeto con
una función `server()` para V1 y una función `setup()` para V2:

```ts title="src/index.ts"
import { Plugin } from "@opencode/plugin"

export default {
  ...Plugin.define({
    id: "example",
    async setup(ctx) {
      await ctx.tool.hook("execute.before", () => {
        console.log("A tool is about to run")
      })
    },
  }),
  async server() {
    return {
      "tool.execute.before": async () => {
        console.log("A tool is about to run")
      },
    }
  },
}
```

- V1 llama a `server()` y usa los hooks devueltos.
- V2 lee el `id` y `setup()` de la exportación por defecto (o `effect()` en los plugins de Effect) e ignora `server()`.
- Mantén cada implementación en su propia API; compartir una exportación no traduce los hooks de V1 a hooks de V2.
- Expande `Plugin.define(...)` dentro del objeto exportado para que compruebe los tipos de la definición de V2 por
  separado de `server()`.

La forma de objeto de V1 se admite en OpenCode `1.18.29`. Las versiones anteriores de V1 pueden esperar
exportaciones de funciones; prueba el paquete instalado con la versión de V1 más antigua que quieras admitir y con V2.
